# MoQ Transport implementation notes

Behaviour that the Rust (`crates/moqt`) and TypeScript (`packages/moqt`) implementations must share, where `draft-ietf-moq-transport-18` is silent, contradicts itself, or leaves a choice. Both implementations follow this table; a change here is made in both in the same pull request.

Items marked **provisional** depend on an [open question](open-questions.md).

| Case | Behaviour | Basis |
|---|---|---|
| Request that the draft defines and XmoQ does not implement, opened by the peer (FETCH, TRACK_STATUS, SUBSCRIBE_NAMESPACE, SUBSCRIBE_TRACKS) | Answer with REQUEST_ERROR `NOT_SUPPORTED` (`0x3`); the session stays open | §10.6.2 provides the code. Closing the session would drop every other track for one unsupported request. A FETCH is decoded whole before it is refused, in both implementations, so one that is malformed (a Fetch Type other than 1, 2 and 3, a parameter §10.2 does not list for FETCH) closes the session with `PROTOCOL_VIOLATION` (§10.12, §10.2.1); of the other three only the Request ID is read. The Rust session now hands a FETCH to its caller (rows on FETCH below); the relay serves a FETCH (rows in the relay's table), and the Rust client refuses every FETCH with `NOT_SUPPORTED`, until it serves one. `@xmoq/moqt` hands a Standalone FETCH to its application where the application asked for that (`serve({ fetch })`), and refuses one with `NOT_SUPPORTED` where it did not. It serves no Joining FETCH: one that names a SUBSCRIBE of the peer that waits for its answer or was accepted is refused with `NOT_SUPPORTED`, and so is one that names a Request ID of the peer that is yet to come; one that names neither is refused with `INVALID_JOINING_REQUEST_ID` (row below, and `fixtures/joining-request-id/`). The Rust session hands the first two kinds to its caller, and the Rust client refuses them with the same code. `fixtures/peer-fetch/opened.tsv` has the FETCHes both implementations read, each with what comes of it. Between a REQUEST_UPDATE that was refused and the PUBLISH_DONE that follows, the Rust session still takes the SUBSCRIBE as open; `@xmoq/moqt` sends both at once, and a Joining FETCH behind them gets `INVALID_JOINING_REQUEST_ID`. |
| SUBSCRIBE, PUBLISH or PUBLISH_NAMESPACE opened by the peer, received by an implementation that has no responder side (the clients) | Same answer: REQUEST_ERROR `NOT_SUPPORTED`. **A SUBSCRIBE is the exception in both clients.** The Rust client answers one for a track it announced. `@xmoq/moqt` hands one to the application once the application has said how it serves requests (`MoqtConnection.serve`), and refuses it with `NOT_SUPPORTED` until then; a SUBSCRIBE for a track this endpoint sent PUBLISH for gets `DUPLICATE_SUBSCRIPTION` either way (row below). A SUBSCRIBE is decoded whole before it is refused, so one that does not decode closes the session with `PROTOCOL_VIOLATION`, with or without `serve` | A client that does not serve a kind of request says so; the relay serves them |
| REQUEST_UPDATE for an Established subscription that the receiver publishes to (on the stream of the peer's SUBSCRIBE, or of its own PUBLISH) | **With no parameter but delivery timeouts (SUBGROUP_DELIVERY_TIMEOUT, OBJECT_DELIVERY_TIMEOUT): REQUEST_OK, and the subscription goes on.** The relay acts on the Subgroup's timeout (next row); nobody acts on the Object's, in an update as in a SUBSCRIBE; the two clients act on no delivery timeout and change nothing. With any other parameter, also next to a timeout: the first such update is answered with REQUEST_ERROR `NOT_SUPPORTED`, then the subscription ends with PUBLISH_DONE `UPDATE_FAILED` (`0x8`); further REQUEST_UPDATEs that arrive before the subscription has ended get no reply. The session stays open. The parameters of every REQUEST_UPDATE are still checked against §10.2.1 first, and a parameter that is not allowed there is a `PROTOCOL_VIOLATION` | §10.9 requires exactly one REQUEST_OK or REQUEST_ERROR in reply, has "If a parameter previously set on the request is not present in REQUEST_UPDATE, its value remains unchanged", so an update without a parameter has nothing to refuse, and §13.6.1 names "REQUEST_UPDATE with no modified Message Parameters" as a way to keep a session from idling out. When the update is unsuccessful the publisher MUST also terminate the subscription with `UPDATE_FAILED`; §10.9.1: when coalesced updates fail, "only a single REQUEST_ERROR will be sent". WHY OBJECT_DELIVERY_TIMEOUT is accepted, where nothing acts on it: a SUBSCRIBE that sets it is accepted the same way, and a parameter that is taken at first and ends the subscription when it is sent again would be the worse of the two (known shortcomings, delivery timeouts). WHY the other parameters are refused and not accepted without effect: a REQUEST_OK for a filter or a Forward State that then does not change would have the subscriber wait for Objects that do not come, or get ones it asked to stop. **The draft does not say which**: nothing in §10.9 tells a publisher that cannot apply a parameter whether to fail the update or to leave it. `moqtail`'s relay (0.15.0) answers REQUEST_OK to every update of a subscription and writes the parameters over the ones it has (`update_subscription`); nothing in its code of a subscription reads a delivery timeout (`subscription.rs` and `subscribe_handler.rs` at the tag `relay@0.15.0`, read on 2026-10-12) |
| A SUBGROUP_DELIVERY_TIMEOUT that a REQUEST_UPDATE changes, in the relay | The new time holds for every subgroup stream towards that subscriber that the relay learns the end of (the FIN of the publisher's stream) after the update, the ones that were open when it came included. **A stream whose timer runs keeps the time it was finished with**, also where the new one is shorter or none. 0 takes the timeout away; an update without the parameter leaves it. `--delivery-patience-ms` goes on as before: the smaller of the two. Never sent upstream. **Provisional** | §8 starts the timer "once it becomes aware that all of the objects on the subgroup have been published" with the SUBGROUP_DELIVERY_TIMEOUT there is, and says nothing of one that changes while a timer runs. §10.9.1 has, of a filter, "it might still receive Objects outside the new range if the publisher sent them before the update was processed", which is the same leaning: what was under way stays. §10.2.3: SHOULD NOT be forwarded upstream |
| REQUEST_UPDATE on any other request stream of a client | `PROTOCOL_VIOLATION` | §10.9 lets only the sender of a request, or the subscriber of a subscription created by PUBLISH, send it. A client's own SUBSCRIBE or PUBLISH_NAMESPACE stream cannot carry one from the peer |
| A request stream of the peer that ends with a FIN inside its first message | The session is closed with `PROTOCOL_VIOLATION`, whatever the request. A stream that ends without a byte is no request and nothing happens; a reset is no error either. **The two differ in what they send first**: `@xmoq/moqt` refuses a request it does not serve as soon as its Request ID is read, so a peer whose stream ends later inside that message has got REQUEST_ERROR `NOT_SUPPORTED` before the session closes, where the Rust implementation decodes the whole message first and only closes. A FETCH is decoded whole by both. `@xmoq/moqt` decodes what follows on the stream of a SUBSCRIBE it handed to the application, also after the application rejected it, after a REQUEST_UPDATE ended it, and after PUBLISH_DONE: a REQUEST_UPDATE there uses up its Request ID, and bytes that do not decode close the session. It stops when this endpoint has stopped or reset the stream: when its wait after PUBLISH_DONE is over, and after the subscriber's reset or STOP_SENDING. What follows a request the session refused by itself is still dropped without being decoded. The Rust reader decodes everything on a request stream, so bytes that do not decode close the session there in every one of these cases; the relay and the Rust client give the session what follows only after their own PUBLISH_DONE, so a REQUEST_UPDATE after a rejection uses up no Request ID there. §10.1 has every REQUEST_UPDATE consume a Request ID without a condition, which is the reading of `@xmoq/moqt`; the two are not made one yet | §10: "If the length does not match the length of the Message Payload, the receiver MUST close the session with a PROTOCOL_VIOLATION". A stream that ends inside a message is read as a length its payload does not match |
| Other message or stream type that the draft defines and XmoQ does not implement (GOAWAY and other messages that have no reply) | Close the session with `INTERNAL_ERROR` | There is no per-request answer to give. The peer follows the draft, so it is not a violation. FETCH_OK is decoded, in both implementations; one that arrives on a request stream that carries no FETCH of the receiver is a response nobody asked for and closes the session with `PROTOCOL_VIOLATION`, as any response that answers no request does. A fetch stream is read in both implementations (rows on FETCH below) and is not of this row |
| A FETCH whose End Location is before its Start Location, received (Standalone) | REQUEST_ERROR `INVALID_RANGE`; the session stays open. The session answers by itself, and its caller does not see the request. An End Location with Object 0 is the end of its Group for the comparison. The sender's side refuses to send such a FETCH | §10.12.3: "End Location MUST specify the same or a larger Location than Start Location for Standalone and Absolute Joining Fetches", without a consequence. The range is this request's alone, and §10.6.2 has the code for a range that is not valid; closing the session would end every other request for it. The `moqtail` relay 0.15.0 treats it as a protocol violation (`resolve_standalone_fetch_range` in its `fetch_handler.rs`) |
| The Joining Request ID of a Joining FETCH, received | It has to be a SUBSCRIBE of the peer in the same session that is Pending or Established, or a Request ID whose request is yet to come: the Rust session hands a FETCH that names such an ID to its caller, and says which of the two it is (row on a Joining FETCH that names a Request ID the peer has not used yet). Anything else is answered with REQUEST_ERROR `INVALID_JOINING_REQUEST_ID` by the session itself | §10.12.2: "a subscription in the same session in the Established or Pending (subscriber) states" and "it MUST return a REQUEST_ERROR with error code INVALID_JOINING_REQUEST_ID". The definition of the code in §10.6.2 has "the referenced Request ID is not an Established Subscription", which leaves Pending out; the section on the request is followed, since it also says what to do with a Pending one ("buffers the pending Joining Fetch"). A subscription made by a PUBLISH is a known gap (below) |
| A Joining FETCH whose SUBSCRIBE is Pending, or is over when the FETCH is to be answered | The Rust session does not make a FETCH_OK for it. While the SUBSCRIBE is Pending its caller holds the FETCH; when the SUBSCRIBE was rejected or ended, its caller rejects the FETCH | §10.12.2: "if that subscription has not yet been established, the Publisher receiving the Joining Fetch buffers the pending Joining Fetch until either the Subscription is established or the request times out". The range of a Joining FETCH is counted from the subscription's Joining Location (§10.12.2.1), which a subscription that is not Established does not have |
| How long the sender of a FETCH keeps the request | Until it was rejected, until it was cancelled, or until both its FETCH_OK came and its fetch stream ended. A FETCH whose stream ended and whose answer never comes stays open, and takes up one of the sender's requests, until the caller cancels it: the session has no clock | §5.2 has "A subscriber keeps FETCH state until it cancels the request, receives REQUEST_ERROR, or the FETCH data stream receives a FIN or is reset". §10.12.3 has "The FETCH_OK or REQUEST_ERROR can come at any time relative to object delivery", so a FETCH_OK can come after the FIN, and by the letter of §5.2 it would then answer a request that is gone, which closes the session |
| A fetch stream whose Request ID is no open FETCH of the receiver | For a request of the receiver that is over, of whatever kind: the stream is stopped, and the session stays open. For an ID the receiver never gave a request, for an open request that is no FETCH, and for a second stream of an open FETCH: `PROTOCOL_VIOLATION`. No list of ended FETCHes is kept | The draft has none of these cases. §5.2: "some Objects could be received even if the FETCH results in error", so a stream for a FETCH that just ended is no fault of the peer. §10.12.3: "The Objects in the response are delivered on a single unidirectional stream". WHY any ended request and not a list of the FETCHes that ended: a list has an end, and a stream for a FETCH that fell off it would close the session. In the relay that session is a publisher's, shared by every subscriber of it, and one subscriber that sends a FETCH and cancels it over and over could make the relay drop another subscriber's cancelled FETCH from the list while its stream is on the way. The price is that a second stream for a FETCH that is over, and a fetch stream for a SUBSCRIBE that is over, are stopped and not found out |
| The End Location of a FETCH_OK that is before the Start Location of the FETCH | `PROTOCOL_VIOLATION`, for a Standalone and an Absolute Joining FETCH. Not checked for a Relative Joining FETCH | §10.13: "If End Location is smaller than the Start Location in the corresponding FETCH the receiver MUST close the session with a PROTOCOL_VIOLATION". The Start Location of a Relative Joining FETCH is {Joining Location.Group - Joining Start, 0} (§10.12.2.1), and the sender of the FETCH need not know the Joining Location when the FETCH_OK comes |
| A FETCH_OK whose Track Properties hold a Mandatory Track Property | The FETCH is over: its sender cancels the request stream and stops the fetch stream. The session stays open | §2.5.1, as for SUBSCRIBE_OK: no Mandatory Track Property is understood |
| REQUEST_UPDATE for a FETCH, received | Accepted with REQUEST_OK, and nothing of the FETCH changes, when it carries no parameter or only ones the draft lets an update of a FETCH carry: SUBSCRIBER_PRIORITY, AUTHORIZATION_TOKEN, OBJECT_DELIVERY_TIMEOUT, SUBGROUP_DELIVERY_TIMEOUT. With FORWARD, a Subscription Filter or NEW_GROUP_REQUEST: `PROTOCOL_VIOLATION`. One that comes before the FETCH is answered gets its REQUEST_OK after the FETCH_OK. If the FETCH is rejected instead, it gets no answer, and neither does one that arrives after the REQUEST_ERROR was sent; the session stays open. **`@xmoq/moqt` does the same from the FETCH to its answer and after a refusal by its application; `fixtures/peer-fetch/updates.tsv` has the rows both implementations read. Two things differ.** The updates that wait for the answer are at most 64 in `@xmoq/moqt` and in the relay, and one more refuses the FETCH with `EXCESSIVE_LOAD`, with no answer to any of them; the Rust session counts them and leaves the limit to its caller. And where this endpoint ended its direction of the request stream with a reset, both stop the peer's direction with it. `@xmoq/moqt` forgets the request there, and the Request ID of a REQUEST_UPDATE that crossed the reset does not count as used. The relay does the same where it gives the FETCH up before its fetch stream opened and where the subscriber fell behind or left; where it resets an answered FETCH whose stream it was passing on or writing, the request is kept until the stream is reported gone, and an update that is still read uses up its ID (run in the relay's core with the two orders of events; not with real streams). A stopped direction need not deliver its bytes, so the sender's count and the receiver's can differ here whatever a receiver does, and the two are left as they are. What comes after a refusal, and after the fetch stream of an answered FETCH has ended, is the same in both (row on what still comes on the stream of a request of the peer that was refused) | An update of a subscription is refused (row above), and a FETCH is not, because of what a refusal costs here: §10.9.1 has "When a REQUEST_UPDATE fails for a FETCH, the publisher MUST reset the FETCH data stream", so a subscriber that meant to change a priority would lose the fetch. Which parameters: §10.2.7 has "REQUEST_UPDATE (for a subscription or FETCH)"; §10.2.2, §10.2.3 and §10.2.4 name REQUEST_UPDATE without a request; §10.2.12, §10.2.9 and §10.2.13 have "REQUEST_UPDATE (for a subscription)", read as a limit to subscriptions, and §10.2.1 closes the session for a parameter in a message it is not listed for. None of the four that are let through is used (known gaps below). Responses carry no Request ID, so a REQUEST_OK before the FETCH_OK would be read as the answer to the FETCH; after a REQUEST_ERROR the request is over (§5.2), and what was sent before the peer saw it is no fault of the peer |
| A fetch stream that ends before its FETCH_HEADER is complete | With a FIN: `PROTOCOL_VIOLATION`. With a reset: nothing, as for a stream cancelled before its type. Not completed within the time a stream has to say what it is: the stream is stopped (row below) | §10.12.3 has the FETCH_HEADER on every fetch stream, also one without Objects. §11.4.1 for a reset |
| A publisher that answers a Standalone FETCH from what it published (the Rust client with `--answer-fetch`) | Nothing published, or a Start Location after the Largest Object: `INVALID_RANGE`. Else FETCH_OK with End Of Track 0 and the End Location that was asked for, or {Largest.Group, Largest.Object + 1} where that is beyond the Largest Object; then the Objects of the range in the Group Order that was asked for, Ascending without the parameter. An Object that does not exist is left out, with no indicator. Where Objects the client published and no longer keeps lie in the range (it keeps 1,024 Objects and 4 MiB of payload, the newest; **provisional**), one End of Unknown Range indicator covers them. **The rule, which `@xmoq/msf` keeps too:** the indicator names the last Location in the range that the publisher published and no longer keeps, and stands before the Objects; in Descending order it names the first such Location and stands after them (row on where a publisher puts that indicator). This client publishes one Object a Group, so that Location is Object 0 of a Group; for a publisher with several Objects a Group it is the last Object ID it published in that Group, or the first in Descending order, and never an Object ID it did not publish. No indicator is written where no such Location lies in the range. [`fixtures/published-fetch/`](../fixtures/published-fetch/README.md) has the ranges and their answers as rows; the Rust client reads them in a test. In Ascending order the indicator has no near end, so Groups of the range before the first one the client published read as unknown as well. An Object counts as published from the moment the client begins to send it. FILL_TIMEOUT is not looked at: the original publisher has nothing to wait for. A Joining FETCH: `NOT_SUPPORTED`; another track: `DOES_NOT_EXIST`; a 33rd FETCH while 32 are answered: `EXCESSIVE_LOAD` (32 as in `@xmoq/moqt`, and twice the 16 the relay asks one publisher for, which stops counting a FETCH before the client has heard of its end). **The streams, as `@xmoq/moqt` has them but for two things below:** written to the end, the fetch stream is finished, and the client's direction of the request stream after the subscriber's has ended or 3 seconds have passed (row on the request stream of a FETCH that was served to its end). A subscriber that resets the request stream, or sends STOP_SENDING for it, gets both streams reset with `CANCELLED` (§5.2); so does one that sends STOP_SENDING for the fetch stream alone, which is read as the FETCH given up. When the client resets its direction of the request stream it stops the subscriber's as well, with the same code, as the relay does. A subscriber that only finishes its direction has given nothing up. A REQUEST_UPDATE gets its REQUEST_OK while the FETCH is answered, and nothing after (row on what still comes on the stream of a request that was refused). Written to its end, the client's direction of the request stream is not finished with the fetch stream but left for the subscriber to end its own first (row on the request stream of a FETCH that was served to its end). The two things: `@xmoq/moqt` stops the subscriber's direction of the request stream 3 seconds after it finished its own, and the Rust client leaves it open until the subscriber ends it or the session is over (a tool for the interop runs, which end its sessions); and a fetch stream the client cannot write is reset with the code of the request stream, `INTERNAL_ERROR`, where `@xmoq/moqt` takes the code from its application. `FETCH_SERVED request_id=N how=… code=… objects=N` is printed once for every FETCH that was accepted. `@xmoq/moqt` keeps no Objects: its application writes the stream, and the indicators | §10.12.3: "If no Objects have been published for the track or Start Location is greater than the Largest Object (Section 10.7) the publisher MUST return REQUEST_ERROR with error code INVALID_RANGE", "Any gaps in the Group and Object IDs in the response stream indicate objects that do not exist", "If omitted from FETCH, the receiver uses Ascending" (§10.2.8). §10.13 for the End Location. §11.4.4.2: "A publisher SHOULD NOT use End of Non-Existent Range in a FETCH response except to split a range of Objects that will not be serialized into those that are known not to exist and those with unknown status". WHY published from the moment it is begun: §5.1.2 has "Largest Object updates when the first byte of an Object with a Location larger than the previous value is published", and the relay counts an Object when it has read it; a Joining FETCH the client answers while the Object is under way would otherwise end before it, and the subscription begin after it. WHY unknown for what was let go of: those Objects were published, so leaving them out, or End of Non-Existent Range, would say something false. The draft writes of unknown status for a relay that has not asked upstream (§10.12.3) and says nothing of an original publisher that no longer has its Objects; it does not forbid the indicator there. WHY End Of Track 0: the client answers while it publishes. WHY the fetch stream alone being stopped ends the FETCH, where §5.2 names the request stream: nothing more can be delivered, and the relay reads its own subscribers that way ([record](experiments/2026-10-11-rust-client-answers-a-fetch.md)) |
| A unidirectional stream of the peer that ends with a FIN inside its Stream Type | `PROTOCOL_VIOLATION`, in both implementations. A stream that ends without a byte, and one that is reset inside its type, carried nothing | The draft has no rule for it. It is read like a stream that ends inside an Object (§11.4) and like a request stream that ends inside its first message; §11.4.1 for the reset |
| A peer that sends no SETUP | The session is closed with `CONTROL_MESSAGE_TIMEOUT` (`0x11`) after 10 seconds, by the three clients: `@xmoq/moqt` (`setupTimeoutMs`, counted from when it begins to connect its session), the Rust client and the terminal viewer (both counted from when their own SETUP was written). **The relay does the same to a client that sends none**: 10 seconds from when it took the session (`--setup-timeout-ms`), then `CONTROL_MESSAGE_TIMEOUT` with the reason `no SETUP in time`. WHY the relay as well: anybody can connect, and a session that says nothing kept its place among the relay's sessions for as long as its connection lived (run before the limit was there: such a client was still connected after 25 seconds). **Provisional**. Run in `mise run interop` (`quiet peer:`) for all three, against a peer that sends no SETUP, and for the relay, against a client that sends none, with a wait of 1.5 seconds: the other end received the code | §3.5: "CONTROL_MESSAGE_TIMEOUT (0x11): The session was closed because the peer took too long to respond to a control message." Nothing can go on without the SETUP, so the session is what ends, where a request that is not answered is given up alone (row below) |
| A session that holds nothing, at the relay | Closed with `NO_ERROR` (`0x0`) and the reason `the session held nothing`, 30 seconds after it came to hold nothing (`--idle-session-ms`). It holds something while a request of its own is open or held by the relay (a SUBSCRIBE, also one that waits for the publisher that was asked; a PUBLISH; a namespace it announced, with or without a subscriber; a FETCH), or the relay has a request open on it. The time begins when the SETUP has come, and anew when the last such request has gone. The 256 sessions the relay serves are as before. **The own clients do not come to it in what they do**: a publisher announces as soon as it is connected and holds that; a viewer subscribes at once, and where its SUBSCRIBE is refused or its subscription ends it closes its session and connects again (`keepPlaying`) or leaves (the Rust client, the terminal viewer); the demo's pages and the terminal viewer with a room connect when the room has a broadcast. A client that wants a session and nothing on it would have to connect again; none of the own does. **Provisional** | No requirement of the draft, and no code of §3.5 for it: "NO_ERROR (0x0): The session is being terminated without an error", and the peer did nothing wrong. §13.6.1 speaks of the connection under a session that "can close due to idle timeout if no data is exchanged", and has a client "Accept that idle connections can close and implement reconnection logic when needed". WHY a limit: anybody can connect, and as many sessions that ask for nothing as the relay serves keep every viewer and publisher out; the keep-alives of the two ends keep such a connection alive. WHY 30 seconds, where a client that sends no SETUP has 10 (row "A peer that sends no SETUP"): one that has sent its SETUP may be about to announce, or between two broadcasts. Run before the limit was there (such a client was still connected after 25 seconds) and in `mise run interop` (`quiet peer:`) with a wait of 1.5 seconds; the demo's pages were left for 40 seconds each as a viewer without a broadcast, with one, and after it had gone, and none was closed for it |
| How often a session may announce (PUBLISH_NAMESPACE), at the relay | **Five at once, and one more each second** (`--announce-at-once`, `--announce-every-ms`; provisional). A request beyond that is refused with `EXCESSIVE_LOAD` (`0x9`) and the time one takes to come back as its Retry Interval (1,001: after a second); the session is not closed, and its other requests are answered as before. Counted are the requests, whatever their namespace and whether they are accepted, withdrawn or refused for another reason; one that is refused for this takes nothing. WHY these and no other request: an announcement has the relay send that session a SUBSCRIBE for each track of the namespace that is subscribed to or waited for, up to 64, and 100 announcements a second took 0.87 of a core. WHY NOT a limit on requests of every kind: 100 a second is no more than a viewer may send. WHY NOT close the session: the draft has a code for a responder that has too much to do, and nothing that makes many requests an error of the session. | §10.6.2: "EXCESSIVE_LOAD: The responder is overloaded and cannot process the request at this time. The sender SHOULD use the Retry Interval to indicate when the request can be retried." and "Most codepoints have identical meanings for various request types". §10.15 names no code of its own for a PUBLISH_NAMESPACE that is refused. §13.1 has the code for "excessive subscriptions", and does not speak of announcements |
| The Retry Interval of a REQUEST_ERROR | **Read**: 0 is "do not retry", 1 "at once", and any other value that many milliseconds less one. `@xmoq/moqt` hands it on with the error (`RequestFailedError.retryInterval`, and `retryWaitMs`: the wait as a timer takes it, no more than 2,147,483,647 ms, `undefined` for 0), the Rust session with `RequestEvent::Rejected` (`RequestError::retry_after_ms`, `retry_wait_ms`). **Neither library waits or asks again by itself**, and neither keeps a caller from asking again sooner or after a 0: the draft has SHOULD and SHOULD NOT there, and no MUST. `@xmoq/media` asks again on the session (`stay`) after the wait a refusal names, no sooner than 100 ms, and after its own second where the refusal names none or says 0. **Made up by a session of either implementation**: 1,001 with `EXCESSIVE_LOAD` (after a second; provisional), 0 with every other code. **Made up by the relay**: 1 with `TIMEOUT` (what ran out is the relay's own wait, and the same request begins it anew), 1,001 with `EXCESSIVE_LOAD` and with `DOES_NOT_EXIST` (nobody publishes the track now, and the relay cannot know when somebody will; provisional), the time one announcement takes to come back for a PUBLISH_NAMESPACE that came too often, and 0 with the others (`INTERNAL_ERROR`, `NOT_SUPPORTED`, `INVALID_RANGE`, `DUPLICATE_SUBSCRIPTION`, `INVALID_JOINING_REQUEST_ID`, `UNSUPPORTED_EXTENSION`, `UNINTERESTED`). A publisher's own value is passed on as before (row on the publisher's answer). WHY NOT 0 with `DOES_NOT_EXIST`: "SHOULD NOT be retried" would be said to a viewer that came before the broadcast. **Not randomized**, which the draft allows against "synchronized retry storms": every requester that is refused at the same moment is told the same time. The peers give no example: the relay and libraries of moqtail 0.15.0 and moqtransport 0.14.0 send 0 in every REQUEST_ERROR they make | §10.6.2: "Retry Interval: The minimum time (in milliseconds) before the request SHOULD be sent again, plus one. If the value is 0, the request SHOULD NOT be retried."; "If a request is retryable with the same parameters at a later time, the sender of REQUEST_ERROR includes a non-zero Retry Interval in the message. To minimize the risk of synchronized retry storms, the sender can apply randomization to each retry interval so that retries are spread out over time. ## Known gaps against the draft

These are requirements of draft 18 that the implementations do not meet yet. Each has a `FIXME:` at the place in the code where it belongs.

**The four that can do the most harm**, looked at on 2026-10-12 against the code as it was after the limits of that day (a SETUP that does not come, a request that is not answered or has no stream, a Subgroup that has no stream). Each is in the list below, or in the rows it names; the order is by who is hurt: other viewers first, then the relay, then the one session.

1. **One subscriber can keep every other from fetching from a publisher** (below, under the relay). Any client that reaches the relay opens 16 FETCHes for tracks of one publisher and reads them slowly. Every other viewer's FETCH for that publisher is refused with `EXCESSIVE_LOAD` for as long as it likes; a viewer reads its catalog with a Joining FETCH, so a new viewer of that broadcast has no catalog until the publisher sends one again (derived from how the catalog is read; the refusal itself was run).
2. **Any client can be a further source of a track** (the two gaps on several publishers, and authorization). Without a key the relay takes a PUBLISH for a track that is being broadcast from anybody, up to 4 sources, and passes on each Subgroup from whichever source sends it first: a client that sends its own Subgroups under the Group IDs to come would have them passed on to every viewer in place of the publisher's (derived from the rule; not run with a source that sends other content). With a key, only a holder of a token for that namespace can.
3. **A fetch stream the relay writes from its cache is bounded by no time as a whole** (below, under the relay). A viewer that reads its 16 FETCHes slowly keeps up to 8 MiB alive for each after the cache has moved on, 128 MiB a session, for as long as it reads.
4. **A session could announce a namespace as often as it liked.** Limited on 2026-10-13: five `PUBLISH_NAMESPACE` requests at once for a session, and one more each second (row "How often a session may announce"). Before that, one session that announced and withdrew 100 times a second, with 64 tracks or more of the namespace held or subscribed to, had the relay send 6,400 SUBSCRIBEs a second and use 0.87 of a core; with the limit the same session costs 0.02 to 0.03 of a core, and 0.14 at 1,000 a second. The Objects of the sessions beside it were not late in either case (11 cores). What is left: each session has its own allowance, so 256 sessions have 256 times as much, which was not run (`docs/experiments/2026-10-13-a-session-that-announces-a-namespace-again-and-again.md`).

A fifth was found that day and closed the same day: a session that sent its SETUP and then held nothing kept its place among the relay's 256 for as long as its connection lived (row "A session that holds nothing"). Not among them, though they stall something: the connection's flow control (a session that does not read stalls itself, not others), a subgroup stream of the peer that stays open (64 of them stop that session's own later streams), and the STOP_SENDING Chromium does not always report (a request the page believes open, on the page).

- **A subgroup stream of the peer that stays open after its header.** No requirement of the draft, and a hole in a limit, in both implementations: it holds its place among the streams read at once for as long as the peer likes, and 64 of them keep every later stream of that kind from being read. It is left so: a time would end a Group that is sent slowly, which is a way to publish. A request stream no longer does the same: once this endpoint has finished its own direction (a refusal, a FETCH that was served, PUBLISH_DONE), the peer has 3 seconds in `@xmoq/moqt` and 2 in the relay to end its direction, and is stopped then (row on what still comes on the stream of a request of the peer that was refused). The Rust client has no such time: it runs once and ends.
- **A subscription a page accepted holds a place for as long as it lasts.** No requirement of the draft. An accepted SUBSCRIBE of the peer keeps its request stream open, which is one of the 64 bidirectional streams `@xmoq/moqt` reads at once. Nothing ends a subscription whose subscriber neither ends it nor is sent anything; that is a subscription that goes on, not a stream that fails to end.
- **A STOP_SENDING for a stream the peer opened that arrives before the page has taken the stream is not always reported by Chromium** (13 of 120, [record](experiments/2026-10-11-write-abort-in-chromium.md)). A peer that cancels a request that way, without resetting its own direction, can leave `@xmoq/moqt` with a request, or an accepted subscription, it believes open. The own relay and the moqtail relay reset their direction as well when they cancel (the latter by its source, not run), and the reset is seen.
- **The relay takes a WebTransport session only from a peer that sends the older token in its CONNECT.** `web-transport-proto` 0.6.2, under `web-transport-quinn` 0.13.2, wants `:protocol` to be `webtransport` and sends that itself; a peer that sends `webtransport-h3`, the token of `draft-ietf-webtrans-http3-15` §3.2, is turned away during the handshake (`HANDSHAKE_FAILED … expected webtransport, got: Some("webtransport-h3")`). `moqlivemock`'s clients send the newer token, and connect only with one line changed ([`interop/peers/moqlivemock/`](../interop/peers/moqlivemock/README.md)). Against `moqtail`'s relay the unchanged subscriber failed as well (`http3: parsing frame failed: EOF` on its side); the relay's side was not looked at, so whether for the same reason is not known. Chromium 156 connects, so it sends the older token; its CONNECT was not looked at. When a browser changes the token, the relay stops taking it until the library does.
- **`@xmoq/moqt` and `@xmoq/msf` report a failure of a handler with the global `reportError`, unguarded.** In a runtime without it the call throws: a handler's failure is then an unhandled rejection, and `end` of a catalog publisher rejects. Not run in such a runtime.
- **`@xmoq/moqt` has one limit on the payload of an Object for the whole connection** (`limits.maxObjectPayloadLength`, 16 MiB by default); a subscription cannot have a smaller one. A reader of a track whose Objects are small, as `@xmoq/msf` is for a catalog (1 MiB), gets an Object of a subscription whole, up to that limit, before it can refuse it. A fetch stream is decoded by its reader, which can give a smaller limit, and `@xmoq/msf` does. The same will hold for media tracks.
- **`@xmoq/moqt` remembers no Object it sent.** A page answers the FETCH the relay sends it for a viewer's Joining FETCH only through its application (`serve({ fetch })`), which has to have kept the Objects. §10.2.11 has "If Objects have been published on this Track the Publisher MUST include" LARGEST_OBJECT in SUBSCRIBE_OK; the library does not know, so the application has to pass it (`accept`). Without it the relay refuses a viewer's Joining FETCH for that subscription with `INVALID_RANGE`.
- **A FETCH of the peer that `@xmoq/moqt` accepted and that the subscriber neither reads nor gives up holds its two streams, and its place among `limits.maxPeerFetches`, for the session.** Behind the own relay this does not happen: the relay gives up on a subscriber that does not read and cancels upstream.
- **Through `moqtail`'s relay, what a page answers a FETCH with does not reach the viewer.** That relay sends the viewer a fetch stream that carries the Request ID of its own FETCH to the publisher, which no FETCH of the viewer has ([record](experiments/2026-10-11-a-page-answers-a-fetch.md)). The own relay writes the viewer's Request ID.
- **Authorization token structure (§10.2.2).** The token is carried as opaque bytes, so the alias types (REGISTER, USE_ALIAS, DELETE) and the rules for them in SETUP are not enforced. Left until authentication is decided.
- **Datagrams (§11).** Neither implementation reads datagrams, so an OBJECT_DATAGRAM is dropped without notice and the rule "an endpoint that receives an unknown datagram type MUST close the session" is not met. Datagram delivery is outside the Phase 0b scope.
- **Connection flow control for control streams first (§11.4.2, MUST: "endpoints MUST allocate connection flow control to the control streams before allocating it to any data streams").** Not met by any of the three implementations. As receivers: the relay bounds the connection's receive window (4 MiB), and subgroup streams whose readers are held back can take all of it, so the request streams of that session wait too; the clients leave the window at their stack's default. As senders, if the sentence means them as well (it goes on: "while the sender waits for flow control to send the message"): which stream uses the connection's credit is the QUIC stack's choice, and neither Rust nor TypeScript sets a stream priority or send order. The deadlock the draft names does not arise at the relay, because a stream with an unknown Track Alias is read and held within limits and not left unread. **A deadlock of the same kind was seen in the browser client**, for request streams where the draft speaks of control messages: the client reads 64 unidirectional streams of the peer at once and leaves the rest with the browser. With a subscription the page did not read and one Object of 100,000 bytes a stream, the relay's PUBLISH_DONE for it did not reach the page, and after the relay had ended that subscription its SUBSCRIBE_OK for another track of the same session did not arrive either (3 of 3), until the page read again. With 57-byte Objects and with 30 Objects a stream both arrived, and without the limit the second request was answered while the page held everything that was sent ([record](experiments/2026-10-10-subscription-backlog-in-chromium.md)). The likely cause, not verified with a capture, is that the streams the page has not taken hold the connection's credit. An application that reads, however slowly, frees it; one that never reads can stall its own session. Whether the client should end such a subscription itself is in [open questions](open-questions.md).
- **Stream error codes on reserved codepoints (`draft-ietf-webtrans-http3-16` §4.4, §9.5), in Rust.** The WebTransport range has codepoints of the form `0x1f * N + 0x21` that are not WebTransport codes. `web-transport-proto` 0.6.2 checks the range only, so a reset with `0x52e4a40fa8f9` is reported with the code `0x1e` where it should be a reset without a code. XmoQ gets the decoded value and cannot tell. The same goes for the code of a STOP_SENDING, which the relay and the Rust client print. A peer that maps its codes as §4.4 says never sends such a codepoint.
- **The code of a STOP_SENDING sent from a browser on a subgroup stream was not observed.** On a request stream it was: when an own-browser subscriber cancelled, the relay printed the code `0x1` that `@xmoq/moqt` puts into the `WebTransportError`, in 53 of 60 rounds; in the other 7 the relay saw the reset of the other direction first, and it prints the line only when the STOP_SENDING comes first. On a subgroup stream the relay notices a STOP_SENDING when it next writes to the stream, and no interop run has a subscriber stop a stream the relay is still writing ([record](experiments/2026-10-10-disconnects-through-own-relay.md)).
- **`PublishedTrack.ended` after a PUBLISH_DONE that could not be written, in `@xmoq/moqt`.** Not a requirement of the draft: `done()` rejects with the error of the write, and `ended` resolves only when the session ends, although the session state has ended the subscription.
- **Request IDs of requests the peer opens, in the subscribe and fetch modes of the Rust client.** There the client answers every such request with `NOT_SUPPORTED` without its session, and does not check its Request ID (§10.1, `INVALID_REQUEST_ID`). The IDs are not remembered either, so a REQUEST_UPDATE that uses the Request ID of such a request again is not taken for a duplicate, where `@xmoq/moqt` closes the session. What comes on the stream of such a request after the refusal is not read either (row on what still comes on the stream of a request that was refused). The modes that publish, `publish` and `publish-namespace`, go through the session, and so does the relay. **No test or interop run has the Rust client see what follows a refusal**: a change that lets it forget a request it refused passes all of them. It takes a peer that sends a REQUEST_UPDATE after it was refused, and no client here sends one.
- **A SUBSCRIBE that the Rust client reads before it has sent its PUBLISH gets `NOT_SUPPORTED`.** No rule is broken: the subscription §5.1 means ("an existing subscription in Pending (publisher) state") begins with the PUBLISH, and once that is sent the session answers `DUPLICATE_SUBSCRIPTION`, as `@xmoq/moqt` does. The mode that sends PUBLISH serves no SUBSCRIBE, though, and the relay waits for a PUBLISH after `DUPLICATE_SUBSCRIPTION` and not after `NOT_SUPPORTED`: a subscriber whose SUBSCRIBE reaches that client through the relay before its PUBLISH is on the way gets `DOES_NOT_EXIST`. The track is there a moment later.
- **The Rust client in a mode that publishes leaves its peer unanswered in two waits.** While a SUBSCRIBE it is about to serve waits for `--serve-delay-ms` or for the driver's line `serve`, and in the up to 3 seconds after its last PUBLISH_DONE, when its driver is done and it waits for the peer to end that stream. A request of the peer that comes in the first is answered when the wait is over; one that comes in the second gets no answer, and the session closes right after. In every other wait (the answers to its PUBLISH_NAMESPACE and PUBLISH, `--publish-delay-ms`, the driver's line `publish`, an Object under way, the end of the first stream when it publishes anew) it answers. What it holds unread meanwhile is 16 events a queue, after which its readers wait.
- **`DUPLICATE_SUBSCRIPTION` from a publisher that sends no PUBLISH (§5.1, §10.6.2), in the relay.** The code is also the answer when the publisher still holds a subscription in the same role ("If an endpoint receives a message attempting to establish a second subscription to a Track with the same role, it MUST fail that request with a DUPLICATE_SUBSCRIPTION error"): for instance one the relay cancelled a moment ago and the publisher has not let go of yet. The relay cannot tell this from an announced PUBLISH and waits; up to 64 subscribers then get `TIMEOUT` after 5 seconds, where asking the publisher again would have got them the track. Asking again is left out because §10.6.2 ties it to the publisher's Retry Interval ("If the value is 0, the request SHOULD NOT be retried"), and the own session always sends 0 (the gap on Retry Interval below).
- **A responder's FIN after its REQUEST_OK to PUBLISH_NAMESPACE: the two clients differ.** The TypeScript client ends the request (`peer-fin`); the Rust client does not read the stream of its PUBLISH_NAMESPACE after the answer and goes on as if announced. Which of the two is right is not decided; the row on a requester's FIN covers the other direction only. The own relay never finishes that stream this way.

The relay (`crates/relay-core`, `crates/relay`) adds these:

- **Several publishers of one track (§9.3, §9.5). The MUSTs are met in part.** §9.5: "Relays MUST send SUBSCRIBE messages to all matching publishers. This includes matching both Established subscriptions on the Full Track Name and Namespace Prefix Matching against published Namespaces." §9.3: "Relays MUST handle Objects for the same Track from multiple publishers and forward them to matching Established subscriptions." §9.5: "When a relay receives an authorized PUBLISH_NAMESPACE for a namespace that matches one or more existing subscriptions to other upstream sessions, it MUST send a SUBSCRIBE to the publisher that sent the PUBLISH_NAMESPACE for each matching subscription." §9.5: "When it receives an authorized PUBLISH message for a Track that has Established downstream subscriptions, it MUST respond with PUBLISH_OK." Against that stands §9.3: "An implementation can use mechanisms such as REQUEST_ERROR or unsubscribing (see Section 3.3.2) if it cannot accept an additional publisher due to implementation constraints." §9.5 again: "Relays MUST forward PUBLISH_NAMESPACE or PUBLISH messages to all matching subscribers", which is empty here because the relay refuses SUBSCRIBE_NAMESPACE. What is done: a PUBLISH for a track is accepted whatever state the track is in, up to 4 sources a track, and each Subgroup is taken from the source that sends it first (rows below). A SUBSCRIBE goes to the publishers of a matching namespace, also for a track that has a source (row on a SUBSCRIBE for a track that has no source). A publisher that announces a namespace while tracks of it are subscribed to is asked for them then. What is not done, five things, each against one of the MUSTs above. **No more publishers are asked than the track has room for**: with its sources and what is asked already, 4; the others are asked when a subscriber comes or a namespace of the track is announced, and there is room. That holds for the publisher that sends PUBLISH_NAMESPACE as well: it is asked before the ones that were left out earlier, and not at all for a track that has no room. It rests on the sentence of §9.3 above. WHY: a publisher that accepted would be cancelled at once when the track is full, having started to send. **A publisher that was passed over because the relay had 64 requests open on it is not asked when one of them ends**, but when the next subscriber of the track comes or a namespace of it is announced. **A publisher that was asked for a track and did not become a source is not asked for it again** until it announces a namespace of the track anew, though it is still a matching publisher. WHY: it would get a SUBSCRIBE with every subscriber that comes to a track it has said it does not have, and the relay would open as many requests. **A PUBLISH_NAMESPACE does not get its publisher asked for a track that has a source and no subscriber.** §9.5 has "a namespace that matches one or more existing subscriptions to other upstream sessions", and a PUBLISH the relay accepted is a subscription of the relay to an upstream session, with subscribers or without; read so, the publisher is to be asked. The relay reads the sentence as being about tracks somebody is subscribed to, and asks for those. WHY: nobody wants more of a track nobody receives, and the publisher that is asked would send it to the relay all the same. **A SUBSCRIBE for a track whose sources all drain is refused** (row below), where §9.5 has "If there are no Established upstream subscriptions for the requested Track, the Relay MUST send a SUBSCRIBE request to each publisher that has published the subscription's namespace or prefix thereof": such a track has no place for subscribers that wait.
- **Sources of a track that do not send the same thing (§9.1, §2.4.2, §9.3).** §9.1: "An endpoint that receives a duplicate Object with a different Forwarding Preference, Subgroup ID, Priority or Payload MUST treat the track as Malformed." §2.4.2, the sixth example of a malformed track: "The same Object is received more than once with different Payload or other immutable properties." §9.3: "The Relay SHOULD attempt to deduplicate Objects before forwarding, subject to implementation constraints." Of the four, the relay compares the Priority, for a Subgroup it remembers and where it can tell the priority (row on a Subgroup that comes again with another Publisher Priority, and the known gap on when a priority is compared); the Forwarding Preference, the Subgroup ID and the Payload of what two sources of a track send are not compared, so the MUST is met in part, and the relay removes duplicates by Subgroup and not by Object. A Subgroup is taken from whichever source sends it first, whole, and the other source's stream for it is stopped unread; a source whose Groups are numbered differently from another's is passed on next to it as if the Groups were different ones while the numbers are less than 8 apart, and has all its streams stopped when its numbers are the smaller ones by 8 or more (row on how long the relay remembers). Runs with two publishers were done with publishers that send the same Object under the same Group ID only.
- **A session that has as many timers running as it may gets the next one at once (relay).** The hub runs at most 1,024 timers for a session at a time. One that is asked for beyond that is not started and is reported as run out at once, so that what it guarded is let go of and not kept for good: a wait for the last streams after PUBLISH_DONE then ends as soon as it begins, an early stream is dropped at once, and a request the relay sent counts as unanswered at once. The timers of waits that are over are not stopped and count until they run out (2 seconds for a wait after PUBLISH_DONE), so a publisher that publishes anew and says PUBLISH_DONE over and over reaches the limit with those alone. Read in `crates/relay/src/hub.rs`; not run.
- **A stream of a subscription that comes after a new subscription took its Track Alias (§10.11, §11.1).** A publisher says PUBLISH_DONE with a Stream Count, one of the streams it counted is still on its way, and a PUBLISH or SUBSCRIBE_OK that is accepted gives the alias to a new subscription. A subgroup stream carries the alias and nothing else that says which subscription it is of, so the late stream is taken for one of the new subscription: its Objects are delivered under it, and its end counts towards the Stream Count of the new subscription's PUBLISH_DONE. That wait can then end while a stream of the new subscription is open; the relay stops that stream, finishes the PUBLISH stream as if all had come, and ends the track where the source was its last. The streams of the old subscription that are open when the alias is taken are known and are not counted (row on a reused Track Alias). The draft gives a receiver no way to tell the others apart. **Such a stream is also read with the DEFAULT PUBLISHER PRIORITY of the new subscription where its header has no priority.** Where the two subscriptions have different defaults and the stream is for a Subgroup the relay remembers with the priority it really has, whether the first subscription sent that Subgroup or another source of the track did, the relay sees the Subgroup with two priorities and ends the track for every subscriber as malformed, though nothing is wrong with it. A test pins it. It takes a PUBLISH or a SUBSCRIBE_OK that gives the alias to a subscription with another default, headers without a priority, and a stream of the first subscription that arrives after it. **The same happens the other way round, with a stream of the new subscription that the relay reads before the PUBLISH_DONE of the first:** a publisher says PUBLISH_DONE, publishes anew under the alias with another default and sends a stream without a priority, the three on three streams between which QUIC keeps no order. Read first, the stream has the default of the first subscription, which to the relay still goes on. A test pins that as well. The relay cannot tell it from one subscription that sends a Subgroup again with another priority, which is what the comparison is there to find.
- **Streams a publisher sent ahead for a PUBLISH that is refused, under the Track Alias of a subscription that drains (§5.1, §10.10, §10.11).** §5.1: "Publishers MAY start sending Objects on PUBLISH-initiated subscriptions before receiving a PUBLISH_OK response". A publisher says PUBLISH_DONE, sends PUBLISH again under the same Track Alias while the streams the first one counted are awaited, and opens a stream at once. When the PUBLISH is refused, the alias means the draining subscription again, and nothing tells that stream from one of it: its Objects go to the subscribers of the draining subscription's track, and its end counts towards the Stream Count. With that the count can be reached before the streams that were counted have ended, and the first PUBLISH stream then gets its FIN early; a counted stream that comes after is stopped. The refused PUBLISH can be for another track, whose Objects then go out under the first track. The draft gives a receiver no way to tell the two apart. A PUBLISH that is refused before the session looks at its alias (`DUPLICATE_SUBSCRIPTION`, a Mandatory Track Property) and a refused SUBSCRIBE_OK leave the same behind. Before the Rust session kept the draining subscription through a refused PUBLISH, such a refusal always ended the wait at once. At the relay this takes a PUBLISH that is refused, which leaves a track that has all the sources it may have, a Mandatory Track Property, and the limit of open requests; a publisher that publishes its own track anew is accepted, under the same alias and under another.
- **A Subgroup without a Publisher Priority reaches the subscribers under the default of another source (§11.4.2, §12.4), in the relay.** Such a Subgroup has the DEFAULT PUBLISHER PRIORITY of the subscription it came on. The relay passes its header on as it came, and the Track Properties the subscribers have are those of the source that came last (§2.5). With two sources whose defaults differ, a Subgroup of the one that came first is therefore read by the subscribers with the default of the other. A test of the core pins it. With one source it does not happen. Mending it means writing the priority into the header where a track has had several sources, which goes with the question of whose Track Properties a track with several sources has.
- **A DEFAULT PUBLISHER PRIORITY above 255 is passed on as it came (§12.4).** "Priorities above 255 are invalid"; the draft does not say what a receiver does with one. The relay accepts the PUBLISH or SUBSCRIBE_OK, passes the property on, and counts the source as having no default (128) where it compares priorities. `moqtail` 0.15.0 refuses such a property when it decodes it (`src/model/property/track_property.rs`, "DEFAULT_PUBLISHER_PRIORITY must be 0-255", as a protocol violation), so a `moqtail` subscriber would not take what the relay passes on (read in that file; not run). Where two such properties come in one message the relay takes the first; nothing refuses the second.
- **A Publisher Priority is compared only for a Subgroup the relay remembers, and not where it cannot tell the default (§2.4.2).** The relay remembers the 8 newest Groups and 256 Subgroups of a track; a Subgroup that comes again later with another priority passes or is left like any other. A stream without a priority in its header that arrives under a Track Alias whose subscription drains is not compared either, and where the Subgroup is taken from it, the priority the relay remembered for that Subgroup is gone: a later stream is compared again only once the Subgroup has been taken from a stream whose priority is known, which a second stream of the same source does and a stream of another source, which is left, does not. All of that is on the side of not finding a difference: the publisher may have sent PUBLISH anew under the alias with another default, and the stream ahead of it (§5.1).
- **The other examples of a malformed track that reach across streams are not looked for (§2.4.2).** The fourth and the fifth, an Object past the last one of its Group or of the track, are found within one subgroup stream (row on an Object after End of Group or End of Track) and not across streams: the relay does not remember which Objects it has passed on. The seventh, another Forwarding Preference than before, cannot come about, since the relay reads no datagrams.
- **Objects past the end of a Subgroup, and a Subgroup on two streams that both end with a FIN with different last Objects (§2.4.2, the second and third example of a malformed track).** Not detected. A second stream for a Subgroup that ended with a FIN is stopped unread, when it opens or, where its header leaves the Subgroup ID to the first Object, when that Object comes; a stream that another took the place of is stopped unread as well. Nothing of either reaches the subscribers.
- **A second stream for a Subgroup the relay has forgotten (§2.2).** It passes, so the subscribers can get a Subgroup on two streams of which neither was reset, which §2.2 has as MUST NOT. The relay forgets a Subgroup when its Group is 8 or more behind the newest, and when the track has more than 256 Subgroups in those Groups: then the smallest Subgroup IDs of the oldest Group go, also ones whose stream is still open, and a second stream for one of those is opened downstream next to the first, which is not reset. That takes more than 32 Subgroups a Group on average over 8 Groups, or more than 256 in one; a publisher that sends every Object as a Subgroup of its own gets there. With one source per track it takes a publisher that sends a Subgroup twice. Once a track has had several sources, a stream of a Group that is 8 or more behind the newest is stopped and not passed on (row on how long the relay remembers), so a source that is merely behind another does not cause it, whether the other is still there or not; what is left is the limit of 256.
- **Which of two open streams for a Subgroup the source goes on with (§11.4).** The relay keeps the one whose header it read later (row on a second stream, below). It knows the order in which the headers were read and not the QUIC stream IDs. When a source resets a stream and sends the Subgroup again, and the header of the first stream is read after that of the second, the relay stops the second and keeps the first, which ends with the reset; §11.4.3 has "A publisher that receives a STOP_SENDING on a Subgroup stream SHOULD NOT attempt to open a new stream to deliver additional Objects in that Subgroup", so the Subgroup is lost for every subscriber. No subscriber gets a wrong Object. Whether this happens with real peers was not looked at.
- **A new stream for a Subgroup to a subscriber whose stream for it is closed (§11.4.3).** When a stream the relay opened to a subscriber is reported closed while the source's stream goes on, the next Object opens another stream to that subscriber for the same Subgroup. The I/O side reports a stream closed also when the subscriber stopped it, and for that case §11.4.3 has "SHOULD NOT attempt to open a new stream to deliver additional Objects in that Subgroup". The core is not told why a stream closed. A test of the core pins what it does; the case was not run with a peer that sends STOP_SENDING.
- **A SUBSCRIBE whose End Group is over already, or whose filter has no Location to start at, is accepted, in the relay (§5.1.2, SHOULD).** "If the publisher cannot satisfy the requested Subscription Filter ... or if the entire End Group has already been published it SHOULD send a REQUEST_ERROR with code INVALID_RANGE." The relay answers SUBSCRIBE_OK. It does not know that an End Group is published whole, and a Group at or before the End Group that reaches it late is still sent, so such a subscription can get Objects. What the MUST NOT of that paragraph asks ("A publisher MUST NOT send objects from outside the requested range") the relay keeps: the Start Location and the End Group of a filter (row on the Subscription Filter of a SUBSCRIBE).
- **A subscription is not ended when the End Group of its filter has passed, in the relay.** No PUBLISH_DONE with `SUBSCRIPTION_ENDED` (0x3, §10.11: "The publisher reached the end of an associated subscription filter") is sent; the subscription stays until the subscriber ends it or the track does. The draft does not ask it of a relay (§9.4: "A subscription with a filter can reach a state where all possible Objects matching the filter have been delivered to the subscriber. Since tracking this can be prohibitively expensive, Relays are not required or expected to do so").
- **A Subscription Filter that a REQUEST_UPDATE brings is not applied, in the relay (§10.2.9).** An update that carries one is refused, and the subscription ends (row on REQUEST_UPDATE for an Established subscription).
- **A publisher that is one of the two clients does not look at the Subscription Filter of a SUBSCRIBE (§5.1.2, MUST NOT).** `@xmoq/moqt` hands the SUBSCRIBE of a peer to its application with the filter in it, and sends what the application writes; the Rust client in the mode that serves a SUBSCRIBE sends every Object from the next one on. The own relay asks a publisher without a filter (row on the relay's SUBSCRIBE to a publisher), so neither is asked for one behind it.
- **NEW_GROUP_REQUEST (§10.2.13).** A relay MUST pass it on to the publisher; it is ignored.
- **Delivery timeouts (§8, §10.2.3, §10.2.4). Met in part (2026-10-12).** *As the draft has it*: the relay acts on the `SUBGROUP_DELIVERY_TIMEOUT` of a SUBSCRIBE. The timer of a subgroup stream towards that subscriber starts when the relay knows that the Subgroup has no more Objects (the FIN of the publisher's stream; §8, "once it becomes aware that all of the objects on the subgroup have been published"), and a stream the subscriber's transport has not acknowledged whole when it is over is reset with `DELIVERY_TIMEOUT` (0x2), written out or not ("If the timer expires before the underlying transport stream reaches \"all data committed\" state ..., the implementation MUST reset the stream"); the subscription goes on. 0 is no timeout. The timeout is never sent upstream (§10.2.3, SHOULD NOT). *The relay's own, provisional and off unless a flag asks*: `--delivery-patience-ms` is a time for the subscribers that set none, **which leaves §8's "if none of the timeouts are set to a non-zero value, all Objects ... are delivered"** for them, and where a subscriber set a longer one the smaller of the two holds; `--older-groups give-up` resets the streams of older Groups of a track when a newer one begins, for every subscriber whatever it set. The ground for both is §8, "Publishers can, at their discretion, discontinue forwarding Objects before either of the timeouts occurs", and not the draft's "smaller of the two", which is of a publisher's Track Property and a subscriber's parameter. **Not met**: the Track Properties `SUBGROUP_DELIVERY_TIMEOUT` and `OBJECT_DELIVERY_TIMEOUT` of a publisher are not read, so the smaller of the publisher's and the subscriber's (§8) is not taken; `OBJECT_DELIVERY_TIMEOUT` is read as a parameter and not acted on (§8 has it checked "before attempting to pass [the Object] to the underlying transport", and the relay hands every Object to a send window of 4 MiB as it comes, so the check would never fail; "SHOULD minimize the amount of data buffered at the underlying transport layer" is not followed); a REQUEST_UPDATE that sets `OBJECT_DELIVERY_TIMEOUT` is answered with REQUEST_OK like a SUBSCRIBE that sets it, and not acted on either. A REQUEST_UPDATE that sets `SUBGROUP_DELIVERY_TIMEOUT` is applied (row on a SUBGROUP_DELIVERY_TIMEOUT that a REQUEST_UPDATE changes). The two clients are not senders that take a timeout: they hand a peer's SUBSCRIBE to the application with its parameters, and neither acts on them.
- **How often the sessions together may announce is not bounded (§13.1), in the relay.** One session is: five `PUBLISH_NAMESPACE` requests at once and one more each second, the others refused with `EXCESSIVE_LOAD` (row "How often a session may announce"). A session that announces again is still asked before the publishers that announced earlier and wait for room, which is what §9.5 asks for, and each announcement that is accepted still makes the relay forget that the session declined the tracks of the namespace and ask it for up to 64 of them. Every session has its own allowance, and the relay takes 256 sessions. §13.1: "Relays SHOULD implement rate limiting on subscription requests"; the sentence is about the subscription requests of a subscriber, for which the relay has no rate limit, and does not name announcements.
- **Retry Interval (§10.6.2).** Where several publishers were asked, the subscribers get the Retry Interval of the answer that came last (row on the publisher's answer). What an implementation gives a REQUEST_ERROR it makes up itself is in the row "The Retry Interval of a REQUEST_ERROR"; **0, which reads as "do not retry", is still given where a retry could succeed a moment later** with `DUPLICATE_SUBSCRIPTION`: to a publisher whose PUBLISH is read before its own PUBLISH_DONE for the track (row on a PUBLISH for a track the relay knows already), and to a viewer that asks anew before it was sent PUBLISH_DONE. The values are fixed numbers and not what the relay knows of the case: `EXCESSIVE_LOAD` says "after a second" whatever the limit, and nothing is randomized. The relay passing on a publisher's REQUEST_ERROR which keeps the publisher's Retry Interval unless it replaces the Error Code with `INTERNAL_ERROR` (row on the publisher's answer and the table of codes, below). The relay does not honour a Retry Interval either. It remembers a publisher that declined a track and does not ask it again until that publisher announces the namespace anew (row on which publishers the relay asks), whatever the Retry Interval was: a publisher that refused with a wait is not asked again when the wait is over, and one that announces anew is asked at once, also after Retry Interval 0 ("If the value is 0, the request SHOULD NOT be retried"). That memory goes with the track. Where the last refusal ended a track that had no source, the next subscriber makes the relay ask every matching publisher again at once, also the ones that answered 0 or a wait that is not over. The SHOULD NOT that keeps the relay from asking again after `DUPLICATE_SUBSCRIPTION` applies there as well.
- **REQUEST_UPDATE** is applied for one thing: the SUBGROUP_DELIVERY_TIMEOUT of a subscription, in the relay (2026-10-12). Every other update of a subscription is refused, so the Forward State, the filter and the priority of a subscription cannot change, and no NEW_GROUP_REQUEST can be sent after the SUBSCRIBE. For a FETCH it is accepted and changes nothing (row on REQUEST_UPDATE for a FETCH). The two clients send one for a SUBSCRIBE of their own (`Subscription.update`, `Session::update_subscription`); none for a FETCH, a PUBLISH_NAMESPACE, or a subscription a PUBLISH of the peer made. **A REQUEST_UPDATE that gets no answer leaves the subscription as it is**: after the time a request gets (row on a request the peer does not answer), the browser client rejects the call and the Rust client prints `ANSWER_TIMED_OUT request=update`; neither ends the subscription, and an answer that comes later is still read. WHY not given up like a request: an update is on the stream of its SUBSCRIBE and cannot be cancelled alone.
- **A Joining FETCH for a subscription that a PUBLISH made is refused (§5.1, §10.12.2).** §5.1 gives such a subscription a Joining Location ("communicated in ... PUBLISH"), and the change log of draft 18 has "Allow joining FETCH for PUBLISH and REQUEST_UPDATE with forward=1"; the Joining Request ID is then the Request ID of the publisher's PUBLISH. The Rust session takes only a SUBSCRIBE of the peer and answers `INVALID_JOINING_REQUEST_ID` for the rest. It is met when a viewer that got a track by PUBLISH, and not by its own SUBSCRIBE, sends a Joining FETCH to the publisher or relay that published it: the own browser publisher sends PUBLISH, and so does the relay to no one yet. The sender's side is the same: the Rust session does not send a Joining FETCH that names a PUBLISH of the peer.
- **The Forward State of the subscription a Joining FETCH names is not looked at by the session (§10.12.2, MUST).** "A Joining Fetch is only permitted when the associated subscription has Forward State 1; otherwise the publisher MUST respond with a REQUEST_ERROR with error code INVALID_RANGE." Whoever answers the FETCH has to check it. The relay does (row on a Joining FETCH in the relay); the Rust client refuses every FETCH.
- **Priorities (§7.2, §7.3). Met in part (2026-10-13), in the relay.** The relay gives each stream it opens to a subscriber a priority of the transport from the SUBSCRIBER_PRIORITY of the SUBSCRIBE (128 without one) and the stream's Publisher Priority (its header's, or the default of its source, or 128): §7.2's first two steps. Every such stream is below the control stream and the request streams, which have the transport's own priority (§7.2: "the control streams SHOULD be prioritized highest, followed by the bidi request streams and then all subscribed Objects"). **Not met**: the third and fourth steps, the Group by the GROUP_ORDER and the lowest Subgroup ID. The transport takes one number for a stream and does not know which subscription it is of, so a Group in the number would order the streams of different tracks as well, where §7.2 has "the expectation is that all subscriptions will be able to send some data"; `moqtail`'s relay (0.15.0, `compute_stream_priority`) has the Group in it. Streams with the same two priorities take turns, old Groups with new. GROUP_ORDER is decoded and not used; a SUBSCRIBER_PRIORITY in a REQUEST_UPDATE is refused; **a fetch stream** the relay writes or passes on stands by the SUBSCRIBER_PRIORITY of its FETCH (128 without one, §10.2.7: "relative to other subscriptions and fetch responses in the same session") and a Publisher Priority of 128, whatever the Objects in it have (§7.1: "FETCH responses however can contain objects with different publisher priorities"; a fetch stream is one stream and the transport takes one number for it), and a Joining FETCH is not put before the subscription it joins; the relay's own subscriptions upstream name no priority. **The clients** write each stream as its bytes come and give the transport no priority; the audio publisher of `@xmoq/media` can name a Publisher Priority for its streams and names none by default. A priority is strict: a publisher that puts its sound below its video has the sound not sent on a link without room for both ([record](experiments/2026-10-13-the-sound-behind-the-video-on-a-narrow-link-and-priorities.md)). **Three things a priority does not reach** (the mechanism of each was read in the code on 2026-10-13; what it does to a broadcast was not measured): (1) the first bytes of every stream, its type of WebTransport, are written by `web-transport-quinn` 0.13.2 with the highest priority there is before the relay's number is set (`Session::open_uni`: "Max priority for the header so the application cannot queue lower-priority data in front of it"), so a track that opens a stream for every small Object may be ordered less than its priority says; (2) the order holds for what the transport has buffered and not sent, which is at most the send window of the connection (4 MiB), and a writer that waits for room there waits whatever its priority; (3) the relay's limit on what waits for one subscriber (`SendBudget`) is one for the session and not one for each subscription, so a subscriber whose video fills it can have its sound's subscription ended with `TOO_FAR_BEHIND` as well.
- **A subgroup stream whose writer panics ends with a FIN, in Rust.** The writer of a subgroup stream (`xmoq-moqt-io`) resets or finishes its stream by hand on every way out, and a sending half that is merely dropped ends with a FIN on a real connection (quinn 0.11.12; pinned by a test over loopback). So a panic inside the writer's task would end a Subgroup that was cut short as if it were complete. The writer of a fetch stream resets when it is dropped; the writer of a subgroup stream has no such guard.
- **Not verified against a real connection: what the relay does when it gives a fetch stream up before it is open.** A subscriber that takes nothing has its fetch stream reset with `TOO_FAR_BEHIND`. Where the relay was writing the stream this is tested, over loopback as well (`xmoq-moqt-io`: a writer that resets while its write waits). Where it gave up while the FETCH_HEADER was not all written, the reset is tested on an in-memory connection whose streams hold one byte, and on no real one: there the wait is more likely inside the opening of the stream, where there is nothing to reset. The relay's own clocks (10 seconds for the opening, and 10 for each piece it writes) run in tests on in-memory connections only. So does the stopping of a fetch stream the relay writes itself, when its FETCH is cancelled or its track is found malformed: the stream is a few bytes, which a real transport takes before a cancellation can arrive, and no run stopped one.
- **The relay does not look into a fetch stream it passes on (§2.4.2, §11.4).** It reads the FETCH_HEADER, writes one with the subscriber's Request ID, and moves the rest as bytes. So it does not find what breaks the object model there: Properties that are malformed, an Object after the end of its Group, a duplicate that differs. §2.4.2: "If a relay detects a Malformed Track, it MUST immediately terminate downstream subscriptions with PUBLISH_DONE and reset any fetch streams with Status Code MALFORMED_TRACK"; the relay detects none on a fetch stream, so a publisher's malformed fetch stream reaches the subscriber as it is, and the subscriptions to the track go on. A stream that ends with a FIN inside an Object (§11.4, a protocol violation) is passed on with its FIN as well; the subscriber is the first to decode it. Nothing of a fetch stream raises the largest Location the relay knows for the track.
- **The relay leaves the range of a FETCH to the publisher (§10.12.3, §10.13).** It checks that a Standalone FETCH does not end before it starts, and passes the Start Location and End Location on. Whether the range starts after the largest Object (`INVALID_RANGE`), where it is cut when it ends beyond it (the End Location of FETCH_OK), and the order of the Groups are what the publisher answers; the relay passes the answer and the stream on and compares neither with what it knows of the track. The `moqtail` test client as a publisher answers some of these otherwise than the draft has them ([record](experiments/2026-10-11-standalone-fetch-through-own-relay.md)), and so does what its subscriber gets through the relay.
- **One subscriber can keep every other from fetching from a publisher.** The relay asks one publisher for 16 FETCHes at once, and one session may have 16 open; a session that has 16 open for tracks of one publisher leaves none, and any other subscriber's FETCH for that publisher is refused with `EXCESSIVE_LOAD`. A FETCH has no time limit as a whole, so a subscriber that reads fast enough not to be cut, and no faster, holds the 16 for as long as its FETCHes last. Subscriptions are not touched by this: the publisher keeps 48 of its streams for them. Nothing here is authorized, so any client that reaches the relay can do it. Whether a session gets fewer than a publisher is asked for, and whether a FETCH gets a time limit as a whole, is open with the other limits. Run against real connections ([record](experiments/2026-10-11-rust-client-fetch.md)): a subscriber that read 16 KiB of each of its 16 fetch streams every half second held them, and another subscriber's FETCH was refused meanwhile; one that read the same every 2 seconds was cut as taking nothing, so on a real connection the slowest a subscriber may read is faster than the 1 KiB in 10 seconds the relay counts by. Where that lies was not measured.
- **The Rust client answers a FETCH only with `--answer-fetch`, and then only a Standalone one.** Without the flag: `NOT_SUPPORTED`, in every mode, which drivers count on to see what a relay makes of the refusal. With it, in the modes that publish: row on a publisher that answers a Standalone FETCH from what it published. A Joining FETCH is refused with `NOT_SUPPORTED` in either case; behind a relay a publisher gets none. It sends Standalone and Joining FETCH requests and reads their fetch streams.
- **A FETCH_OK with a Mandatory Track Property that comes after the fetch stream was passed on whole resets nothing (§2.5.1).** "If the relay has already forwarded data on a fetch stream, it MUST reset the stream": while the stream is passed on the relay does, with `UNSUPPORTED_EXTENSION`. When the publisher's stream ended with a FIN before its FETCH_OK came, the FIN has gone to the subscriber and there is no stream left to reset; the subscriber gets REQUEST_ERROR `UNSUPPORTED_EXTENSION` after a fetch stream that looked complete.
- **The relay's cache is the latest Group of a track, and nothing a FETCH brought (§9.1).** A FETCH for anything else is asked of a publisher, also for Objects that passed through the relay a moment ago (row on the relay's cache). The answer a publisher gives to a FETCH the relay passes on is not cached: the relay does not look into a fetch stream. So a publisher that sent an Object once, long before, and to no subscription that reached the relay, is asked for it every time; a publisher that pushes its Objects with PUBLISH, as the browser publisher does, has its latest Group in the cache. With FILL_TIMEOUT 0 the answer is still one End of Unknown Range indicator for the whole range, where the cache could give what it holds (row on FILL_TIMEOUT 0).
- **The relay finds an Object that comes again with other content, and a Group that contradicts itself, only in the Group its cache holds (§9.1, §2.4.2, §12.9; MUST).** What it compares an Object with is the latest Group of the track, as far as the cache has it (row on an Object that comes again). Nothing is found in an earlier Group, in a Group the cache gave up (over the limits, with an End of Track, with a stream whose default priority the relay cannot tell, after an Object was taken back, after an Object came at the Object ID of an End of Group, or after a second status came above one), or in a track that is not cached at all (MAX_CACHE_DURATION or Immutable Properties among its Track Properties): there a second Object goes out to the subscribers as it comes. Nor is an Object of a fetch stream the relay passes on from a publisher compared with anything: the relay hands those streams on as bytes and does not read the Objects in them. A Forwarding Preference cannot differ, since the relay takes no datagrams. What is compared in every track is the Publisher Priority of a Subgroup the relay remembers (row on a Subgroup that comes with another Publisher Priority).
- **An Object after the end of a track is not found (§2.4.2).** "An Object is received whose Group and Object ID are larger than the final Object in the Track. The final Object in a Track is the Object with Status END_OF_TRACK or the last Object sent in a FETCH whose response indicated End of Track." The relay keeps no status of End of Track: the Object that has it goes to the subscribers, its Group is not answered from the cache (§11.2.1.1 has of the statuses "All of those SHOULD be cached"), and what a publisher sends after it goes out as it comes.
- **An Object that comes where the relay recorded that none exists is sent on (§9.1, SHOULD NOT).** "As described in Section 2.1, an endpoint can receive an Object after it has already recorded that the Object does not exist. A caching relay SHOULD NOT cache or forward the Object in this case." The relay does not cache it, and forwards it (row on an Object that comes again, for why).
- **Object Properties that come again with another set do not replace the cached ones (§2.5, SHOULD).** "If a Track or Object arrives with a different set of unknown properties than previously cached, the most recent set SHOULD replace any cached values, removing any unknown values not present in the new set." The cache keeps the Object that came first, with its Object Properties (§9.1: "Relays MAY ignore subsequently received Objects"), so a FETCH answered from the cache has the first set where the subscribers got the second.
- **The relay does not read Immutable Properties (§12.7).** "When looking for the value of a property, processors MUST search both the mutable properties and the contents of Immutable Properties." The default Publisher Priority of a track and the Prior Object ID Gap of an Object are looked for among the mutable properties alone. For MAX_CACHE_DURATION the relay does not need to look: a track with Immutable Properties is not cached (row on the relay's cache).
- **FETCH_OK from the relay's cache always has End Of Track 0**, also where the track's publisher has sent PUBLISH_DONE and the relay waits for its last streams; a publisher asked for the same range might say 1.
- **A fetch stream the relay writes from its cache is bounded by no time as a whole.** A subscriber that takes it slowly, more than nothing in every 10 seconds for each Object, keeps the Objects of the Group it is being sent alive after the cache has moved on to a later Group: up to 8 MiB for each such Group, for as long as it reads. One session has 16 FETCH requests at most.
- **A FETCH is asked of one publisher, once (§9.5).** "When more than one publisher is available, the Relay MAY send the FETCH to any of them": the relay takes the first (row on whom a FETCH is asked of), and when that one refuses, does not answer in time, or goes, the subscriber is refused, though another publisher of the track might have served it.
- **A Joining FETCH that has no FETCH_OK yet ends when its subscription does, in the relay (§10.12.2).** The draft has "Changing the Forward State of the associated subscription to 0 after the Joining Fetch has been accepted has no effect on the Joining Fetch" and says nothing of a subscription that ends. The relay refuses the FETCH with `INVALID_JOINING_REQUEST_ID` and cancels what it asked of the publisher, also where the publisher's fetch stream is already passed on ahead of its FETCH_OK. A FETCH that has its FETCH_OK goes on to its end. What ends a subscription: the subscriber cancels its SUBSCRIBE; the track ends with PUBLISH_DONE or is found malformed (then the code is `MALFORMED_TRACK`); the subscriber falls behind on the subscription and the relay ends it with `TOO_FAR_BEHIND`; the subscriber sends a REQUEST_UPDATE for the subscription, which the relay refuses and ends the subscription for with `UPDATE_FAILED`. Only the first is the subscriber's wish. A viewer whose publisher ends the track, or that is slow at the moment it joins, loses the Groups before as well, if the publisher has not answered the FETCH by then.
- **The Largest Object of a track is raised when an Object has been read whole, in the relay, and not at its first byte (§5.1.2).** "Largest Object updates when the first byte of an Object with a Location larger than the previous value is published or received through a subscription." The relay learns of an Object from its reader when the whole of it is there. A SUBSCRIBE that comes while an Object is being received is told the Largest Object before it and gets that Object on the subscription, where the draft would have it in the Joining FETCH. Nothing is lost or sent twice for it: the LARGEST_OBJECT of the SUBSCRIBE_OK, the Joining Location and the Start Location of the filter are one value. The Rust client as a publisher counts an Object from the moment it begins to send it (row on a publisher that answers a Standalone FETCH); the rule the two share is that an endpoint tells one value and counts everything from it.
- **What a Joining FETCH and a subscription that starts at or before the Joining Location deliver can overlap, in the relay.** Such a subscription is one without a filter, or with an `AbsoluteStart` or `AbsoluteRange` filter whose Start Location is not after the Joining Location. The FETCH ends at the Joining Location (§10.12.2.1), and a subscription with the Largest Object filter starts right after it, so the two are "contiguous and non-overlapping"; the draft states that as what follows from the Joining Location, for no filter in particular, and has no word on a subscription that starts before it (row on the Subscription Filter of a SUBSCRIBE). A subscription without a filter passes "all Objects published or received via upstream subscriptions" (§5.1.2), and one with an `AbsoluteStart` filter everything from its Start Location: an Object at or before the Joining Location that reaches the relay after the SUBSCRIBE, on a stream that was behind, goes out on it and is in the fetch stream as well. That is the subscriber's choice of filter, and nothing the relay keeps apart. With a Next Group Start filter nothing overlaps, and the rest of the Group of the Joining Location is in neither. `@xmoq/moqt` sends the filter its application gives it, and none without one; the Rust client sends Largest Object unless `--subscription-filter` says otherwise. The `moqtail` relay 0.15.0 showed an overlap of another origin, a range counted from the largest Location at the time of the FETCH ([record](experiments/2026-10-11-moqtail-relay-fetch.md), a).
- **A Joining FETCH can miss Objects where a track has several sources, in the relay (§10.12.2.1).** The Joining Location is the largest Location the relay knows of the track, from any source, and the FETCH is asked of one publisher, the first source (row on whom a FETCH is asked of). A publisher that is behind the others is asked for a range it has not reached: it answers `INVALID_RANGE`, or with what it has, and what lies between its largest Object and the Joining Location is neither on the fetch stream nor on the subscription, which begins after the Joining Location. Which publisher a FETCH should go to where several publish a track is with the [open question](open-questions.md) on several publishers. Seen in a test of the relay core (a source with the largest Location {5, 2} is asked for {9, 0} to {9, 1}); not run against real publishers.
- **The Rust client answers a Joining FETCH that is read before its SUBSCRIBE with `NOT_SUPPORTED`.** Its session takes such a FETCH now (row on a Joining FETCH that names a Request ID the peer has not used yet), and the client, which answers no FETCH, refuses it like any other. `@xmoq/moqt` refuses it with the same code by itself.
- **A Joining FETCH for a SUBSCRIBE with Forward State 0 that the relay has not answered is held, and refused when the SUBSCRIBE is accepted (§10.12.2).** The Forward State is in the SUBSCRIBE, so `INVALID_RANGE` could be said at once; the relay says it where it works the range out.
- **The relay does not pass a REQUEST_UPDATE for a FETCH on to the publisher.** It answers REQUEST_OK itself (row on REQUEST_UPDATE for a FETCH); a SUBSCRIBER_PRIORITY in it reaches nobody.
- **Messages the relay does not implement (§4, MUST: "Relays MUST implement all MOQT messages defined in this document, as well as processing rules described in Section 9").** TRACK_STATUS, SUBSCRIBE_NAMESPACE, SUBSCRIBE_TRACKS, GOAWAY and datagrams are refused or not read, as the rows at the top say; REQUEST_UPDATE is applied for one parameter of a subscription and refused for the others (the gap on REQUEST_UPDATE above). What each waits for is in [open questions](open-questions.md).
- **Authorization (§9.4, §9.5).** Off unless the relay is given a key (row on the relay's authorization); without one nothing is checked. A publisher's `UNAUTHORIZED`, `MALFORMED_AUTH_TOKEN` or `EXPIRED_AUTH_TOKEN` to the relay's SUBSCRIBE reaches the subscribers as it is, although it is about a token the subscriber did not send there and cannot mend. The relay copies nothing of a subscriber's SUBSCRIBE into the SUBSCRIBE it sends a publisher, so a publisher behind the relay does not see a subscriber's AUTHORIZATION_TOKEN. Any session can announce any namespace, the one with no fields included (§2.4.1 allows "between 0 and 32 Track Namespace Fields"), which matches every track: whoever announces it first gets the SUBSCRIBE for every track that nobody has published. With several sources of a track, any session can also become a source of any track that has one, by sending PUBLISH for it, and then: end the track for every subscriber by sending something that breaks the object model (§2.4.2 has the relay end the subscriptions with `MALFORMED_TRACK`, and the other sources are cancelled with it), for which one subgroup stream with another Publisher Priority than the Subgroup had is enough; take a Subgroup from the other sources by sending it first; keep the other sources from being heard, by sending one stream with a Group ID far ahead of theirs, after which their Groups count as too old and their streams are stopped; make the relay forget which stream it took a Subgroup from, by sending more Subgroups than it remembers, after which the same Subgroup can reach the subscribers on two streams (§2.2); raise the largest Location of the track, with the LARGEST_OBJECT parameter of its PUBLISH or with an Object on a stream that is passed on, so that a subscriber that comes gets a LARGEST_OBJECT the other publishers never sent; and send so many streams that a subscriber runs into the limit of what waits to be written and loses its subscription. The newest Group of a track is kept for the track and not for each source, on purpose: a share for each source needs to know who a source is. Any session can also ask any publisher for a FETCH of any track, and hold every FETCH that publisher is asked for (item on one subscriber that keeps every other from fetching).
- **Nothing bounds how many requests of `@xmoq/moqt` wait for a stream at once, nor what is kept for a stream that is being opened.** Each waits 10 seconds at most (row "A request that waits for a stream"), and the caller is what keeps their number down: every request is a call of the application.
- **A write on a stream of `@xmoq/moqt` that could not be opened closes the session, where the failure to open it did not.** The session of the library has forgotten the stream by then in every path it has (a request is cancelled, a Subgroup is told to be not opened), so no such write is made; a caller of the stream layer alone could make one.

## Relay

Choices of the relay where the draft leaves one. The limits are **provisional**.

| Case | Behaviour | Basis |
|---|---|---|
| PUBLISH for a track the relay knows already | Accepted, with PUBLISH_OK, in each of the three states a track can be in. A track that has a source, whether a PUBLISH or a SUBSCRIBE of the relay that a publisher accepted, and with or without subscribers: it has one more. A track the relay has asked a publisher for and has no answer about: the PUBLISH gives it its source, the subscribers that waited get SUBSCRIBE_OK with what the PUBLISH brought, and what the relay asked stays asked (row on the publisher's answer, below); where the PUBLISH comes from the publisher that was asked, the relay's SUBSCRIBE to it gives way (row on a PUBLISH for a track the relay has asked a publisher for). A track whose sources have all said PUBLISH_DONE and whose last streams are awaited: it goes on with the new source, for the subscribers it has and for ones that come, and the old sources end one by one as their streams do. **That holds for a publisher that goes on with the track's Group IDs.** The subscribers are those of the track as it was, so what the relay remembers of its Groups stays. What a publisher gets that counts from 0 depends on its session. On another session than the old source: the track counts as one that has had several sources (row on how long the relay remembers), and a publisher that takes over a track at Group 50 and counts from 0 gets PUBLISH_OK and has every stream stopped (`CANCELLED`) until it is at Group 43, 8 below the newest the old source sent; all it is told is the STOP_SENDING on each stream. On the session of the old source, under the same Track Alias or another: the track does not count as one that has had several sources for that, a Group older than what the relay remembers passes as it does for a single publisher, and the subscribers see the Group IDs go back within their subscription. Before, such a PUBLISH was refused, and one sent a moment later, when the track was gone, made a new track that started at any Group. Within a scope "a Full Track Name is guaranteed to be unique and identify a specific track" (§2.4.3), so the publisher is sending the same track, and going on with its numbers is the publisher's part. For media, MSF has the same as a rule for the publisher (`draft-ietf-moq-msf-01` §6.1): "Group IDs for a track MUST be unique and MUST increase monotonically", and "When a publisher restarts (e.g., after connectivity loss or encoder restart), it MUST ensure the new starting Group ID is greater than any previously published Group ID for that track". Refused with REQUEST_ERROR `EXCESSIVE_LOAD` (`0x9`) when the track has 4 sources; one that drains counts, since it still holds its streams. From a session that is a source of the track already: `DUPLICATE_SUBSCRIPTION` (`0x19`, row below) while that source goes on. **Once the session has said PUBLISH_DONE, its PUBLISH for the track is accepted, also while the relay still waits for the streams the first subscription counted.** Under another Track Alias the two are two sources of the track, told apart by the alias: the first drains as it would have, the second is taken like a source of another session (a Subgroup both send is taken from whichever sends it first), and the track does not count as one that has had several sources for it. ## Encodings the draft does not give

- `RENDEZVOUS_TIMEOUT` (`0x04`) and `FILL_TIMEOUT` (`0x0A`): the value is a variable-length integer in milliseconds. The draft (§10.2.5, §10.2.6) gives no encoding. This follows `moqtail` 0.15.0, read in `libs/moqtail-rs/src/model/parameter/message_parameter.rs` at tag `relay@0.15.0` on 2026-10-10 (lines 510–515 build the pair, line 733 writes it; only FORWARD, SUBSCRIBER_PRIORITY and GROUP_ORDER are written as one fixed byte). The basis is source reading only: no captured bytes carry these parameters.

## Other observations about the draft

- The variable-length integer of draft 18 is not the QUIC (RFC 9000) varint: the number of leading one bits gives the length, up to 9 bytes.
- **A browser page that is closed without `close()` ends differently at the relay by browser** (observed, [record of browser support](experiments/2026-10-10-browser-support-webtransport-webcodecs.md)). With Chromium 156 the relay sees the session end first (`ClosedByPeer { code: 0 }`). With the Firefox 157.0 build of Playwright it sees the page's control stream end first, and closes the session itself with `PROTOCOL_VIOLATION` ("the peer closed its control stream"), which is what §3.3 asks for: "A control stream MUST NOT be closed at the underlying transport layer during the session's lifetime. Doing so results in the session being closed as a PROTOCOL_VIOLATION." The subscribers of a track that page published get the same in both cases, PUBLISH_DONE `TRACK_ENDED` with the Stream Count, and the other sessions go on. The relay has a wait of 200 milliseconds for the like case of a STOP_SENDING on its own control stream (row in the relay's table) and none for this one. Nothing was changed.
- The second example in §11.6 does not add up (a 14-byte value under `Length = 21`). It is not used as a test fixture.
- **§10.2.2 has a message rejected with a code that only ends sessions.** "The receiver of a message referencing an Alias that is not currently registered MUST reject the message with UNKNOWN_AUTH_TOKEN_ALIAS" (lines 3163 to 3165 of the text), where the sentences around it have "close the Session with". The code of that name is among the Session Termination Error Codes (§3.5, 0x17; lines 1744 and 6818) and not among the codes of REQUEST_ERROR (§10.6, the table from line 6838), which has UNAUTHORIZED, MALFORMED_AUTH_TOKEN and EXPIRED_AUTH_TOKEN. **XmoQ closes the session with 0x17**: the one code of that name there is, which a peer can read.
- **§12.9 calls malformed what §2.1 and §9.1 allow.** §2.1 has of an Object that is known to exist "From this state, it can transition to not existing, but not vice versa", and §9.1 lists among the fields of a cached Object that can be updated "Object can transition from existing to not existing in cases where the object is no longer available". §12.9 has "A Track is considered malformed ... if ... An endpoint receives an Object with a Prior Object ID Gap covering an Object it previously received", which is such a transition, said with the property. XmoQ follows each where it applies: the gap is malformed, a status in the place of an Object is not (row on an Object that comes again).
- **§2.1 says "not malformed" where §2.4.2 and §12.9 say malformed.** §2.1: "an endpoint can receive an Object after it has already recorded that the Object does not exist (e.g., via a FETCH gap from one source and later delivery via a subscription). This is not a protocol error and the Track is not malformed", with no condition. §2.4.2 has as an example of a malformed track "An Object is received in a Group whose Object ID is larger than the final Object in the Group", and §12.9 "An endpoint receives an Object with an Object ID within a previously communicated gap": both are Objects that come where the endpoint recorded that none exists. Where XmoQ puts the border is in the row on an Object that comes again.
- **Prior Object ID Gap has a type from the range §2.5 leaves to applications.** §2.5 has "Certain Property type ranges are reserved for application-specific use and will never be allocated by IANA in future MOQT specifications: 0x38 to 0x3F (1-byte encoding)", and §12 "Property types in ranges reserved for application-specific use (0x38-0x3F, 0x3800-0x3FFF) are not defined by MOQT". §12.9 defines Prior Object ID Gap with the type 0x3E, and §12.8 Prior Group ID Gap with 0x3C; the table of Properties among the IANA considerations lists both. XmoQ reads 0x3E as §12.9 has it, so an application that uses 0x3E for something of its own makes its track malformed or leaves holes in what the relay's cache answers.
- `moqtail` 0.15.0 clients omit `MOQT_IMPLEMENTATION` in SETUP (§10.3.1.5 is a SHOULD); its relay sends it. The relay's control-message log prints the raw bytes received and sent, checked in `libs/moqtail-rs/src/transport/control_stream_handler.rs` at tag `relay@0.15.0` on 2026-10-10.
- **`moqtail` 0.15.0 keeps the prior Group ID and Object ID of the last Object after an End of Range indicator on a fetch stream**, where §11.4.4.2 has those of the indicator (row above). Read in the crate `moqtail` 0.15.0, `src/model/data/fetch_object.rs` on 2026-10-11 ("Returns None for EndOfRange markers — they MUST NOT update prior state"). For the same reason it takes an Object that follows an indicator, with no Object before, for the first of the stream: its Group ID and Object ID have to be there and are absolute (lines 166 to 186 of that file), which is the reading of §11.4.4.1 the row on the first Object does not follow. An Object that follows an indicator and leaves out its Group ID or Object ID is read as another Object by the two. Not run: no stream with an indicator was obtained.
- **`moqtail` 0.15.0 has a third Group Order, `Original` = 0x0** (`src/model/control/constant.rs`, read on 2026-10-11), and reads a GROUP_ORDER of 0 as it. §10.2.8 has "Ascending (0x1) or Descending (0x2)" and for any other value a `PROTOCOL_VIOLATION`. XmoQ closes the session for 0.
- **The `moqtail` relay 0.15.0 answers a FETCH in five ways draft 18 does not have** ([record](experiments/2026-10-11-moqtail-relay-fetch.md), one run each, with moqtail's test client as the publisher). The own relay is to follow the draft in each.

  | | Case | Draft 18 | The `moqtail` relay |
  |---|---|---|---|
  | a | The range of a Joining FETCH | Ends at the Joining Location, the Largest Location of the SUBSCRIBE_OK (§5.1, §10.12.2.1) | It looks as if it is counted from the largest Location when the FETCH arrives: an Object came on the fetch stream and on the subscription. Its `fetch_handler.rs` reads the track's largest Location there. **Seen with a catalog as well** ([record](experiments/2026-10-11-pages-send-and-play-video.md)): for a track whose one Object, at {its time in milliseconds, 0}, had been sent before the relay subscribed, the SUBSCRIBE_OK the subscriber got had that Location as LARGEST_OBJECT, and its Joining FETCH with Joining Start 0 was answered for {0, 0} to {0, 1}, with a fetch stream without Objects.   | b | End Location {G, 0} | "the entire group is requested" (§10.12.1) | Nothing of Group G is sent; Start {1, 0} with End {1, 0} gives FETCH_OK and a stream without Objects |
  | c | Start Location beyond the largest Object | REQUEST_ERROR `INVALID_RANGE` (§10.12.3, MUST) | FETCH_OK with the End Location that was asked for, and a stream without Objects |
  | d | A Joining FETCH whose Joining Request ID is no subscription | `INVALID_JOINING_REQUEST_ID` (§10.12.2) | REQUEST_ERROR `DOES_NOT_EXIST`, "Track does not exist" (in `fetch_handler.rs`, the same path as a track that is not found) |

Whether the `moqtail` relay would do the same by itself was not seen. For c it is not known whether the relay or the test client behind it decides: the relay's own function for the range does what the draft has for b and c.
- moqtail-ts 0.13.0 answers a SUBSCRIBE with a SUBSCRIBE_OK that repeats the parameters of the SUBSCRIBE (`handlerSubscribe`, read in `dist/client-BzncAN14.mjs` of the npm package `moqtail` 0.13.0 on 2026-10-10: `const parameters = [...msg.parameters]`). A SUBSCRIBE with FORWARD therefore gets a SUBSCRIBE_OK with FORWARD, which §10.2.12 does not list for SUBSCRIBE_OK, and §10.2.1 has the receiver close the session ("If it appears in some other type of message, the receiving endpoint MUST close the connection with a PROTOCOL_VIOLATION"). The own relay closed the session of a moqtail-ts publisher for this while its SUBSCRIBE carried FORWARD ([the routing record](experiments/2026-10-10-relay-namespace-routing.md), run 10). XmoQ keeps the check; the relay's SUBSCRIBE no longer carries the parameter (row on the relay's SUBSCRIBE), and with that the same run passes ([record](experiments/2026-10-10-routing-follow-ups.md)).
