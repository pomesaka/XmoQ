# MoQ Transport implementation notes

Behaviour that the Rust (`crates/moqt`) and TypeScript (`packages/moqt`) implementations must share, where `draft-ietf-moq-transport-18` is silent, contradicts itself, or leaves a choice. Both implementations follow this table; a change here is made in both in the same pull request.

Items marked **provisional** depend on an [open question](open-questions.md).

| Case | Behaviour | Basis |
|---|---|---|
| Request that the draft defines and XmoQ does not implement, opened by the peer (SUBSCRIBE_TRACKS), and a FETCH or SUBSCRIBE_NAMESPACE that the receiver does not serve | Answer with REQUEST_ERROR `NOT_SUPPORTED` (`0x3`); the session stays open. Of a SUBSCRIBE_TRACKS only the Request ID is read (`UNSUPPORTED_REQUESTS`, `crates/moqt/src/message.rs`). A FETCH and a SUBSCRIBE_NAMESPACE are decoded whole first, in both implementations, so a malformed one closes the session with `PROTOCOL_VIOLATION`: a FETCH with a Fetch Type other than 1, 2 and 3 or a parameter §10.2 does not list for it (`fixtures/peer-fetch/opened.tsv`), a SUBSCRIBE_NAMESPACE whose prefix has more than 32 fields (`MAX_NAMESPACE_FIELDS`, `crates/moqt/src/name.rs`) or a parameter other than AUTHORIZATION_TOKEN. The relay serves both (rows in the relay's table). The Rust client answers a Standalone FETCH for its own track with `--answer-fetch` (row below) and refuses every other FETCH; `@xmoq/moqt` hands a Standalone FETCH to its application where it asked for that (`serve({ fetch })`; `fetchRefusal`, `packages/moqt/src/core/peer-requests.ts`). Neither client serves a Joining FETCH: one that names a SUBSCRIBE of the peer that is Pending or Established, or a Request ID of the peer that is yet to come, gets `NOT_SUPPORTED`; one that names neither, `INVALID_JOINING_REQUEST_ID` (row below, and `fixtures/joining-request-id/`). **The two differ** between a REQUEST_UPDATE that was refused and the PUBLISH_DONE that follows: the Rust session still takes the SUBSCRIBE as open; `@xmoq/moqt` sends both at once, and a Joining FETCH behind them gets `INVALID_JOINING_REQUEST_ID` | §10.6.2 provides the code. §10.12, §10.18 and §10.2.1 for what closes the session |
| TRACK_STATUS (§10.14), in both sessions | Decoded as a SUBSCRIBE is, and a request of its own: **AUTHORIZATION_TOKEN is the one parameter it may carry**, and its REQUEST_OK (TRACK_STATUS_OK) `LARGEST_OBJECT` alone, with Track Properties; any other parameter closes the session with `PROTOCOL_VIOLATION`. Answered once, with REQUEST_OK or REQUEST_ERROR, after which the responder finishes the stream. A REQUEST_UPDATE on its stream closes the session with `PROTOCOL_VIOLATION` (`MessageKind::TrackStatus`, `crates/moqt/src/params.rs`). The two clients refuse a TRACK_STATUS of the peer with `NOT_SUPPORTED` (decided on 2026-10-24; `refusal_code`, `crates/moqt-client/src/main.rs`); the relay answers it (row on TRACK_STATUS in the relay's table). The fixed bytes are moqtail's (`fixtures/moqt-18/`, capture P) | §10.14: "The TRACK_STATUS message format is identical to the SUBSCRIBE message (Section 10.7)", "The bidi stream is closed with a FIN after TRACK_STATUS_OK or REQUEST_ERROR are sent", "the subscriber cannot send REQUEST_UPDATE". §10.2.2 and §10.2.11 for the two parameters; §10.2.6 has RENDEZVOUS_TIMEOUT "in a SUBSCRIBE message" alone, so a TRACK_STATUS cannot ask to be held for a publisher. **The draft is silent** on what follows from a REQUEST_UPDATE that "cannot" be sent. `moqtail` 0.15.0 answers `LARGEST_OBJECT` {0, 0} for a track it has before any Object came, and puts no Track Properties in TRACK_STATUS_OK (capture P) |
| SUBSCRIBE, PUBLISH or PUBLISH_NAMESPACE opened by the peer, received by an implementation that has no responder side (the clients) | REQUEST_ERROR `NOT_SUPPORTED`. **A SUBSCRIBE is the exception in both clients**: the Rust client answers one for a track it announced (`refusal_code`, `crates/moqt-client/src/main.rs`), and `@xmoq/moqt` hands one to the application once it has said how it serves requests (`MoqtConnection.serve`; `ServeHandlers.subscribe`, `packages/moqt/src/webtransport/connection.ts`). A SUBSCRIBE for a track this endpoint sent PUBLISH for gets `DUPLICATE_SUBSCRIPTION` either way (row below); one that does not decode closes the session with `PROTOCOL_VIOLATION`, with or without `serve` | A client that does not serve a kind of request says so; the relay serves them |
| REQUEST_UPDATE for an Established subscription that the receiver publishes to (on the stream of the peer's SUBSCRIBE, or of its own PUBLISH) | **With no parameter but delivery timeouts (SUBGROUP_DELIVERY_TIMEOUT, OBJECT_DELIVERY_TIMEOUT) and NEW_GROUP_REQUEST: REQUEST_OK, and the subscription goes on.** The value of a NEW_GROUP_REQUEST is handed to whoever uses the session (row on NEW_GROUP_REQUEST); the relay acts on the Subgroup's timeout (next row); nothing else changes. With any other parameter, also next to a timeout: the first such update gets REQUEST_ERROR `NOT_SUPPORTED`, then the subscription ends with PUBLISH_DONE `UPDATE_FAILED` (`0x8`); later ones before the end get no reply; the session stays open. A parameter §10.2.1 does not allow is a `PROTOCOL_VIOLATION` first (`only_the_subgroup_timeout`, `crates/moqt/src/session/peer.rs`; `onRequestUpdate`, `packages/moqt/src/core/requests.ts`) | §10.9, §10.9.1, §10.2.13, §13.6.1. **The draft does not say which**: nothing in §10.9 tells a publisher that cannot apply a parameter whether to fail the update or to leave it. `moqtail`'s relay (0.15.0) answers REQUEST_OK to every update of a subscription and writes the parameters over the ones it has (`update_subscription`); nothing in its code of a subscription reads a delivery timeout (`subscription.rs` and `subscribe_handler.rs` at the tag `relay@0.15.0`, read on 2026-10-12) |
| A SUBGROUP_DELIVERY_TIMEOUT that a REQUEST_UPDATE changes, in the relay | The new time holds for every subgroup stream towards that subscriber whose end the relay learns after the update, the ones open when it came included. **A stream whose timer runs keeps the time it was finished with.** 0 takes the timeout away; an update without the parameter leaves it; the smaller of it and `--delivery-patience-ms` holds. Never sent upstream (`set_delivery_timeout`, `crates/relay-core/src/lib.rs`; `OutgoingSubgroup::set_delivery_timeout`, `crates/moqt-io/src/streams.rs`). **Provisional** | §8 starts the timer "once it becomes aware that all of the objects on the subgroup have been published", and says nothing of a timeout that changes while a timer runs. §10.9.1 has, of a filter, "it might still receive Objects outside the new range if the publisher sent them before the update was processed", the same leaning. §10.2.3 |
| NEW_GROUP_REQUEST (§10.2.13), and DYNAMIC_GROUPS (§12.6) | **A publisher that is one of the two clients**: the NEW_GROUP_REQUEST of a REQUEST_UPDATE is answered with REQUEST_OK and handed to the application (`PublishedTrack.onNewGroupRequest`; `SubscriptionUpdated { new_group_request }`); that of a SUBSCRIBE or a PUBLISH_OK is among the parameters the application has. Whether and when a Group begins is the application's. The video sender of `@xmoq/media` with `dynamicGroups` sets DYNAMIC_GROUPS = 1 in its SUBSCRIBE_OK and begins a Group for a request of 0 or above the Group it sends, once that Group is 500 ms long (`DEFAULT_SHORTEST_GROUP_MS`, `packages/media/src/moqt/video-track-publisher.ts`, decided on 2026-10-21). The Rust client with `--dynamic-groups yes` sets the property, prints the request and begins nothing (`NewGroups`, `crates/moqt-client/src/main.rs`). **The relay** passes on a NEW_GROUP_REQUEST of an accepted SUBSCRIBE for a track with a source, or of a REQUEST_UPDATE, as a REQUEST_UPDATE to every source whose Track Properties have DYNAMIC_GROUPS = 1 (outside Immutable Properties or inside) and that has not said PUBLISH_DONE. Not passed on: a value other than 0 that is not above the Group of the Largest Location; any value while one it sent, equal or larger, is outstanding (0 while any is). Outstanding ends with an Object of a larger Group, and when a source is added. At most 16 updates wait for a publisher's answer (`ask_for_a_new_group`, `crates/relay-core/src/lib.rs`). The subscriber's own update gets REQUEST_OK whatever is passed on. Where the track has no source, the relay's SUBSCRIBE upstream carries the largest NEW_GROUP_REQUEST of the subscribers that wait, and to a relay above this one their longest hold (row on a SUBSCRIBE for a track nobody publishes); its PUBLISH_OK carries none. A DYNAMIC_GROUPS above 1 in SUBSCRIBE_OK, PUBLISH, REQUEST_OK or FETCH_OK, also inside Immutable Properties (§12.7), closes the session with `PROTOCOL_VIOLATION` in both decoders (`decode_track_properties`, `crates/moqt/src/message.rs`) | §10.2.13, Relay Handling: "A relay that receives a NEW_GROUP_REQUEST for a Track without an Established subscription MUST include the NEW_GROUP_REQUEST when subscribing upstream", and "After sending a NEW_GROUP_REQUEST upstream, the request is considered outstanding until the Largest Group increases." §12.6: "If omitted, the value is 0." **The draft does not say** what the "Established subscription" of a SUBSCRIBE is that the relay answers from a track it has: read here as the relay's subscription upstream. Nor which publisher is meant where a track has several: each that has the property is asked. Nor what a publisher does with the parameter for a track without the property (row on REQUEST_UPDATE). A publisher's answer that comes after its PUBLISH_DONE closes its session: §10.11 has PUBLISH_DONE as "the final message". **Not met**, in the known shortcomings: `@xmoq/moqt` cannot send a REQUEST_UPDATE for a subscription a PUBLISH of the peer made. `moqtail`'s relay and test client at `relay@0.15.0` neither send the parameter nor act on it (read in `apps/` of the checkout for that tag, commit dd8623d, on 2026-10-13; its libraries encode the parameter and the property), so this is run between own parts only, where both sides can share a misreading ([record](experiments/2026-10-13-a-subscriber-asks-for-a-new-group.md)) |
| REQUEST_UPDATE on any other request stream of a client | `PROTOCOL_VIOLATION` | §10.9 lets only the sender of a request, or the subscriber of a subscription created by PUBLISH, send it. A client's own SUBSCRIBE or PUBLISH_NAMESPACE stream cannot carry one from the peer |
| Answers to the REQUEST_UPDATEs a subscriber sent, received | Each REQUEST_OK and REQUEST_ERROR answers one update, in the order sent. After the first REQUEST_ERROR, the answers to the updates that still wait are taken and the application learns nothing of them; the PUBLISH_DONE that follows ends the subscription, whatever still waits. An answer when none waits closes the session with `PROTOCOL_VIOLATION`. `fixtures/update-answers/` has the rows both read | §10.9: "The receiver of a REQUEST_UPDATE MUST respond with exactly one REQUEST_OK or REQUEST_ERROR". §10.9.1 lets a publisher coalesce updates and send "only a single REQUEST_ERROR", and has it end the subscription with PUBLISH_DONE `UPDATE_FAILED` after a refusal. Reading the first REQUEST_ERROR as the answer to all that wait fits only a publisher that coalesces: one that answers each would have its second REQUEST_ERROR close the session |
| A request stream of the peer that ends with a FIN inside its first message | The session is closed with `PROTOCOL_VIOLATION`, whatever the request. A stream that ends without a byte is no request; a reset is no error either (`MessageDecoder::finish`, `crates/moqt/src/message.rs`; `endedInside`, `packages/moqt/src/core/peer-requests.ts`). **The two differ in what they send first**: `@xmoq/moqt` refuses a request it does not serve as soon as its Request ID is read, so the peer has REQUEST_ERROR `NOT_SUPPORTED` before the session closes; the Rust implementation decodes the whole message first and only closes. A FETCH is decoded whole by both. What follows on the stream of a request that was refused, by the session or its caller, or that ended, is decoded by both: bytes that do not decode close the session, and a REQUEST_UPDATE uses up its Request ID (`PeerRequestState::Rejected`, `crates/moqt/src/session/peer.rs`, to which the relay's `finish_slot` and the Rust client's `said_the_last` hand it; `readAfterRefusal`, `packages/moqt/src/core/peer-requests.ts`). `@xmoq/moqt` drops it unread once it has stopped or reset the stream, and where it keeps as many refused requests as it may | §10: "If the length does not match the length of the Message Payload, the receiver MUST close the session with a PROTOCOL_VIOLATION". A stream that ends inside a message is read as a length its payload does not match. §10.1 for the Request ID |
| Other message or stream type that the draft defines and XmoQ does not implement (messages that have no reply) | Close the session with `INTERNAL_ERROR` (`UNSUPPORTED`, `crates/moqt/src/message.rs`; `UNIMPLEMENTED_MESSAGE_TYPES`, `packages/moqt/src/core/control-message.ts`) | There is no per-request answer to give, and the peer follows the draft. A FETCH_OK on a request stream that carries no FETCH of the receiver answers no request and closes the session with `PROTOCOL_VIOLATION`. A fetch stream is read (rows on FETCH below) and is not of this row |
| A datagram of an unknown type, received | **The session is closed with `PROTOCOL_VIOLATION` (`0x3`), in both implementations**: the relay, the Rust client and the terminal viewer by `xmoq-moqt-io`, which reads every datagram for its type (`datagram_fault`, `crates/moqt/src/data.rs`), and `@xmoq/moqt` (`classifyDatagram`, `packages/moqt/src/core/datagram.ts`). Unknown: a type that is not of the form 0b00X0XXXX (`0x10` to `0x1F`, `0x30` and up, any type of two bytes or more, the type of a padding stream among them), one with both the STATUS bit (`0x20`) and the END_OF_GROUP bit (`0x02`), and a datagram that is empty or ends inside its type. A non-minimal encoding of a valid type is that type. An `OBJECT_DATAGRAM` of a valid type is dropped unread (known gap on datagrams). **A PADDING DATAGRAM (`0x132B3E29`) is discarded whatever follows its type.** `@xmoq/moqt` reads one at a time and keeps none, so what waits is held by the browser, which drops the oldest when its queue is full (`readDatagrams`, `packages/moqt/src/webtransport/stream-io.ts`; W3C WebTransport, Editor's Draft read on 2026-10-24). Run in `mise run interop`: `xmoq-quiet-peer --quiet datagram` sends own-rust, the terminal viewer and own-browser a datagram of the type 0x30 after their SETUP (`quiet peer: ... datagram`), and as a client sends the own relay one (`--send-datagram-hex 30`) ([record](experiments/2026-10-24-datagrams-read-by-the-browser-client.md)) | §11: "All MOQT datagrams start with a variable-length integer indicating the type of the datagram", and "An endpoint that receives an unknown datagram type MUST close the session". §11.3.1 for the invalid types and the code. §11.5.2: "The receiver MUST discard all data received in a padding datagram"; that the Padding Data "MUST all be set to zero" binds its sender, and is not checked |
| GOAWAY (§10.4), received | **On the control stream, after SETUP: taken, and the session opens no request after it; what is open goes on.** Both sessions close with `PROTOCOL_VIOLATION` for a second GOAWAY, for one without a Request ID, as a server for one with a New Session URI, and for a URI over 8,192 bytes (`MAX_NEW_SESSION_URI_LEN`); with `INVALID_REQUEST_ID` for a Request ID of the sender's parity (`on_go_away`, `crates/moqt/src/session.rs`). A new request is refused to the caller (`subscribe()` and the others reject; `UsageError("the peer sent GOAWAY")`), and `MoqtConnection.goAway` resolves. **What each does next**: `keepPlaying` and `keepPublishing` of `@xmoq/media` close the session with `NO_ERROR` and connect anew at once, handing the GOAWAY to every `connect` until another comes (`keepMoving`, `packages/moqt/src/webtransport/keep-moving.ts`; the interop pages connect to the New Session URI with the same certificate hash, the demo's pages ask the room again); the terminal viewer does the same, also without a room and while it waits for the catalog; the gatherer and the transcriber close with `NO_ERROR` and connect to the New Session URI, or to the same URL without one, at once once in a row and after their wait that grows otherwise, and keep to that URI for every later try (`NextTry`, `crates/track-serving/src/backoff.rs`, by `NextSession` of `xmoq-again`, which the viewers go by); the Rust client closes with `NO_ERROR` and leaves with 0. **A request refused with `GOING_AWAY` is followed by a wait of up to 10 seconds for the GOAWAY behind it** (`goAwayBehind`), in `keepMoving` (by which the chat's `keepInTheRoom` and the transcript's `keepFollowingTranscript` go on as well), in the terminal viewer and in the Rust client. The relay asks a publisher that sent one for no track and no FETCH (`crates/relay-core/src/routing.rs`). **On a request stream: taken, for that request alone.** Both sessions close with `PROTOCOL_VIOLATION` for a second GOAWAY on one request stream, for one that carries a Request ID, and, as a server, for one with a New Session URI, also on the stream of a request of the peer that was refused or ended; one that crosses the end of a PUBLISH of this endpoint is not read. The session tells it for a request of its own (`RequestEvent::GoAway`, and `PeerRequestEvent::GoAway` for one of the peer; `Subscription.goAway`, also for one before `SUBSCRIBE_OK`), and `@xmoq/moqt` tells nothing for a request of the peer, nor for its PUBLISH, PUBLISH_NAMESPACE or FETCH. **What each does next**: on the video's subscription, `playVideoTrack` ends with `moved` and the viewer leaves the session as at a GOAWAY on the control stream (`movedBy`, `packages/media/src/moqt/keep-broadcast.ts`), the terminal viewer too; on the sound's alone, it is asked for again on the session (`keepTrackOnSession`; in Rust `xmoq_viewer_io::kept`, by which the terminal viewer keeps its sound, the reader for agents its video, and both the chat's `lines` and the transcript's `speech`), also where a URI is named; the gatherer and the transcriber ask that request alone again on the session, as after its end, a subscription and a SUBSCRIBE_NAMESPACE cancelled and a PUBLISH ended with PUBLISH_DONE `GOING_AWAY` (`0x4`) and sent again (`request_moved`, the `session.rs` of each), also where a URI is named (gap below); the Rust client leaves with `NO_ERROR` (`REQUEST_GOAWAY`); the relay does nothing. A client sends no GOAWAY (row on a GOAWAY the relay sends). Run in `mise run interop` against `xmoq-quiet-peer --quiet goaway` (`quiet peer: ... GOAWAY`), which refuses every request of its first session with `GOING_AWAY` and sends the GOAWAY after the first refusal, and against moqtail's relay at SIGTERM (`moqtail relay: goaway`), which sends one to every session with its `--redirect-uri`, a Timeout of 10,000 ms and Request ID 0 (relay@0.15.0, `broadcast_goaway`): the pages move to the URI and play on, the Rust client leaves with 0; the byte rows are in `fixtures/moqt-18-from-libraries/` | §10.4: "Upon receiving a GOAWAY on the control stream, an endpoint SHOULD NOT initiate new requests to the peer", "The GOAWAY message does not impact subscription state", "to initiate migration of that individual request"; §3.6, §9.5.1, §10.6.2. WHY the clients connect again at once after a GOAWAY, and only once in a row: what is played stands still until the next session, and a relay that sends GOAWAY on every session would have them connect as fast as they can. WHY the URI is decoded as bytes in Rust and as text in TypeScript: as the Connect URI of a Redirect in each |
| GOAWAY (§10.4), sent by the relay | **At SIGTERM or SIGINT: a GOAWAY on the control stream of every session**, with the New Session URI of `--redirect-uri` (empty where it is not given; always empty on a session where the relay is the client), the Timeout of `--goaway-timeout-ms` (`GOAWAY_TIMEOUT_MS`, `crates/relay/src/main.rs`; decided on 2026-10-24) and the smallest Request ID of the peer the session has not seen. A session that opens after it gets one after its SETUP. From then on every request of the peer is refused with `GOING_AWAY` by the Rust session (`Session::go_away`); what was taken goes on. **A connection that comes after it is refused** (QUIC `CONNECTION_REFUSED`). The relay ends as soon as no session of its clients is left, after closing its sessions with the upstream with `NO_ERROR` (`0x0`) (`upstream_drained`, `crates/relay/src/hub.rs`), or when the Timeout is over, after closing what is left with `GOAWAY_TIMEOUT` (`0x10`) (`go_away`, `crates/relay/src/hub.rs`), and prints `GOING_AWAY sessions=<n> timeout_ms=<t> uri=<uri>`. `@xmoq/moqt` sends no GOAWAY. Run in `mise run interop` (`own relay: goaway`): the own pages that publish and play move to the second own relay it names and play on, own-rust prints the GOAWAY (`request_id=2` after its SUBSCRIBE 0) and leaves with 0, and the terminal viewer moves and plays the same broadcast there | §3.6: "The sender SHOULD close the session with GOAWAY_TIMEOUT after the indicated timeout if there are still open subscriptions or fetches on a connection". §10.4 for the Request ID and `GOING_AWAY`, and "A client MUST send a zero-length New Session URI in any GOAWAY". WHY the relay ends before the Timeout when nobody is left: the Timeout is "the time in milliseconds the sender will wait for graceful closure", and nothing is left to wait for. WHY the session with the upstream is not waited for: its server has no reason to close it on a client's GOAWAY, which tells "the peer it intends to close the session soon" (§10.4), and `GOAWAY_TIMEOUT` is for a peer that "took too long to close the session in response to a GOAWAY" (§3.5). WHY the relay does not unsubscribe upstream first, though "When the server is a subscriber, it SHOULD send a GOAWAY message to downstream subscribers prior to unsubscribing from upstream publishers": it does not unsubscribe at all, and its upstream subscriptions end with the sessions |
| A FETCH whose End Location is before its Start Location, received (Standalone) | REQUEST_ERROR `INVALID_RANGE`; the session stays open. The session answers by itself, and its caller does not see the request. An End Location with Object 0 is the end of its Group for the comparison (`start_of`, `crates/moqt/src/session/peer.rs`; `ends_before`, `crates/moqt/src/session/fetch.rs`; `fetchRefusal` and `endsBefore`, `packages/moqt/src/core/`). The sender's side refuses to send such a FETCH | §10.12.3: "End Location MUST specify the same or a larger Location than Start Location for Standalone and Absolute Joining Fetches", without a consequence; §10.6.2 has the code. | The Joining Request ID of a Joining FETCH, received | It has to be a SUBSCRIBE of the peer in the same session that is Pending or Established, or a Request ID whose request is yet to come: the Rust session hands a FETCH that names such an ID to its caller, and says which of the two it is (row on a Joining FETCH that names a Request ID the peer has not used yet). | A Joining FETCH whose SUBSCRIBE is Pending, or is over when the FETCH is to be answered | The Rust session does not make a FETCH_OK for it. | How long the sender of a FETCH keeps the request | Until it was rejected, until it was cancelled, or until both its FETCH_OK came and its fetch stream ended. | A fetch stream whose Request ID is no open FETCH of the receiver | For a request of the receiver that is over, of whatever kind: the stream is stopped, and the session stays open. For an ID the receiver never gave a request, for an open request that is no FETCH, and for a second stream of an open FETCH: `PROTOCOL_VIOLATION`. Not checked for a Relative Joining FETCH (`on_fetch_ok`, `crates/moqt/src/session/fetch.rs`; `onFetchOk`, `packages/moqt/src/core/requests.ts`) | §10.13: "If End Location is smaller than the Start Location in the corresponding FETCH the receiver MUST close the session with a PROTOCOL_VIOLATION". | A FETCH_OK whose Track Properties hold a Mandatory Track Property | The FETCH is over: its sender cancels the request stream and stops the fetch stream. The session stays open. So also where Immutable Properties make the Track malformed (`track_properties_refusal`, `crates/moqt/src/immutable.rs`; `onFetchOk`, `packages/moqt/src/core/requests.ts`) | §2.5.1, §2.4.2 and §12.7, as for SUBSCRIBE_OK |
| REQUEST_UPDATE for a FETCH, received | Accepted with REQUEST_OK when it carries no parameter or only SUBSCRIBER_PRIORITY, AUTHORIZATION_TOKEN, OBJECT_DELIVERY_TIMEOUT and SUBGROUP_DELIVERY_TIMEOUT; only the relay uses one, the priority (row on the priority of a FETCH, in the relay's table). With FORWARD, a Subscription Filter or NEW_GROUP_REQUEST: `PROTOCOL_VIOLATION` (`allowed_in`, `crates/moqt/src/params.rs`). One that comes before the FETCH is answered gets its REQUEST_OK after the FETCH_OK. If the FETCH is rejected instead, it gets no answer, and neither does one that arrives after the REQUEST_ERROR; the session stays open (`PeerRequestEvent::UpdateAccepted`, `UpdateHeld`, `crates/moqt/src/session/peer.rs`). `@xmoq/moqt` does the same; `fixtures/peer-fetch/updates.tsv` has the rows both implementations read. **Two things differ.** The updates that wait for the answer are at most 64 in `@xmoq/moqt` and in the relay, and one more refuses the FETCH with `EXCESSIVE_LOAD` (`MAX_HELD_FETCH_UPDATES`); the Rust session leaves the limit to its caller. The wait is counted from the FIN in the Rust client, and in `@xmoq/moqt` from the moment the transport has taken PUBLISH_DONE and the FIN, so a subscriber that does not read can hold `done()` up for longer. Both wait in the same way after the PUBLISH_DONE `UPDATE_FAILED` that answers a refused REQUEST_UPDATE (in `@xmoq/moqt` nobody is told how it ended), and after they served a peer's SUBSCRIBE and ended it with PUBLISH_DONE. The Rust client has no end to that wait where it ended a subscription with `UPDATE_FAILED` while it was still publishing (read, not run). Where the session ends during the wait, `done()` resolves with `session-closed`, and the Rust client's run ends with the error of the lost connection (read in `finish_and_await_close`; not run). `@xmoq/moqt` takes another wait as `peerStreamEndTimeoutMs`, from 0 to 2^31 - 1 milliseconds; with 0 it does not wait but still stops the subscriber's direction, and a session closed right after can lose what was sent last. The Rust client has no such setting. What the relay does with a publisher's STOP_SENDING that arrives while it still waits for the counted streams was not looked at | §10.11 and §5.1.1 say when the publisher sends PUBLISH_DONE and FIN, and give the subscriber's direction no meaning afterwards and no time to close it; §3.3.2 makes a reset of an open direction a cancellation. So a FIN there is XmoQ's convention, and a peer that knows nothing of it sees an ordinary end. `web-transport-quinn` 0.13.2 can lose a stream that arrived and was not accepted when the connection closes. The `moqtail` relay 0.15.0 also finishes the stream after PUBLISH_DONE (seen in the interop logs); what it means by that was not looked at |
| Track Namespace and Track Name in message types | The names an API user sees follow the draft's message definitions: `track_namespace` and `track_name`, camelCase in TypeScript. TypeScript keeps two fields (`FullTrackName`, `packages/moqt/src/core/track.ts`). Rust keeps one validated `full_track_name` (`FullTrackName`, `crates/moqt/src/name.rs`), read with `track_namespace()` and `track_name()` of SUBSCRIBE and PUBLISH, and with `namespace()` and `name()` of the `FullTrackName` where a message has no such methods (a Standalone FETCH, a Redirect) | §2.4.1 and each message's definition. What must match between the implementations is the vocabulary, not the representation |

## Known gaps against the draft

These are requirements of draft 18 that the implementations do not meet yet, and this list is the whole of them. A `FIXME:` in the code marks the place of some of them; one is not there for every entry, and nothing checks that the two agree.

**The four that could do the most harm**, ordered by who is hurt: other viewers first, then the relay, then the one session. Three are limited for one session and open for a sender with several sessions; the second waits for the decision on authorization.

1. **One subscriber could keep every other from a publisher.** Limited to 8 of the 64 requests the relay has open on a publisher for one subscriber's session, and 4 of its 16 FETCH requests (`MAX_OWN_REQUESTS_FOR_ONE_SUBSCRIBER`, `crates/relay-core/src/routing.rs`; `MAX_OWN_FETCHES_FOR_ONE_SUBSCRIBER`, `crates/relay-core/src/fetch.rs`; row "How much of a publisher one subscriber's session may take"). Without the limit, a session that sent 10 FETCHes a second to a publisher that answered nothing had 12 of another viewer's 14 FETCHes refused with `EXCESSIVE_LOAD`, and one that sent 30 SUBSCRIBEs a second for new track names had half of another viewer's refused; with it, every request of the other viewer reached the publisher ([record](experiments/2026-10-13-a-session-that-asks-for-a-new-track-again-and-again.md)). **What is left**: a sender with several sessions has that many shares, and 8 sessions, or 4, do what one did; the relay takes `HubConfig::max_sessions` and does not count them by where they come from.
2. **Any client can be a further source of a track** (the two gaps on several publishers, and authorization). Without a key the relay takes a PUBLISH for a track that is being broadcast from anybody, up to `MAX_SOURCES`, and passes on each Subgroup from whichever source sends it first: a client that sends its own Subgroups under the Group IDs to come would have them passed on to every viewer in place of the publisher's (derived from the rule; not run). With a key, only a holder of a token for that namespace can (`crates/relay/src/auth.rs`).
3. **What a fetch stream the relay writes from its cache keeps alive was bounded by nothing.** Limited by a time for the whole stream (`cached_fetch_whole`, `crates/relay/src/hub.rs`) and by what such streams keep of Groups the cache has let go of, for the relay and for one session (`MAX_BYTES_HELD_BEYOND_THE_CACHE` and `SHARE_OF_BYTES_HELD_BEYOND_THE_CACHE`, `crates/relay-core/src/fetch.rs`; rows "A fetch stream the relay writes from its cache" and "What the relay's fetch streams keep beyond its cache"). Without the limits, a reader that took 16 KiB a second on each of 16 fetch streams had none of them ended in 90 s, with the Group they carried dropped from the cache after 5. **What is left**: a sender with nine sessions or more has more than the whole, and the relay then stops the streams of whoever has the most, which may be another's ([record](experiments/2026-10-13-a-fetch-from-the-relays-cache-that-is-read-slowly.md)).
4. **A session could announce a namespace as often as it liked.** Limited per session (`MAX_ANNOUNCEMENTS_AT_ONCE` and `ANNOUNCEMENT_EVERY_MS`, `crates/relay-core/src/routing.rs`; row "How often a session may announce"). With the limit, a session that announced and withdrew 100 times a second, with 64 tracks or more of the namespace held or subscribed to, cost 0.02 to 0.03 of a core, and 0.14 at 1,000 a second; the Objects of the sessions beside it were not late (11 cores). **What is left**: each session has its own allowance, so `HubConfig::max_sessions` sessions have that many times as much, which was not run ([record](experiments/2026-10-13-a-session-that-announces-a-namespace-again-and-again.md)).

- **A subscription a page accepted holds a place for as long as it lasts.** No requirement of the draft. Its request stream is one of the bidirectional streams `@xmoq/moqt` reads at once (`maxPeerBidiStreams`, `packages/moqt/src/webtransport/connection.ts`). Nothing ends a subscription whose subscriber neither ends it nor is sent anything; that is a subscription that goes on, not a stream that fails to end.
- **A STOP_SENDING for a stream the peer opened that arrives before the page has taken the stream is not always reported by Chromium** (13 of 120, [record](experiments/2026-10-11-write-abort-in-chromium.md)). A peer that cancels a request that way, without resetting its own direction, can leave `@xmoq/moqt` with a request, or an accepted subscription, it believes open. The own relay and the moqtail relay reset their direction as well when they cancel (the latter by its source, not run), and the reset is seen.
- **The relay takes a WebTransport session only from a peer that sends the older token in its CONNECT.** `web-transport-proto` 0.6.2, under `web-transport-quinn` 0.13.2, wants `:protocol` to be `webtransport`; a peer that sends `webtransport-h3`, the token of `draft-ietf-webtrans-http3-15` §3.2, is turned away during the handshake (`HANDSHAKE_FAILED … expected webtransport, got: Some("webtransport-h3")`). `moqlivemock`'s clients send the newer token, and connect only with one line changed ([`interop/peers/moqlivemock/`](../interop/peers/moqlivemock/README.md)). Against `moqtail`'s relay the unchanged subscriber failed as well (`http3: parsing frame failed: EOF` on its side); the relay's side was not looked at. Chromium 156 connects, so it sends the older token; its CONNECT was not looked at. When a browser changes the token, the relay stops taking it until the library does.
- **`@xmoq/moqt` and `@xmoq/msf` report a failure of a handler with the global `reportError`, unguarded.** In a runtime without it the call throws: a handler's failure is then an unhandled rejection, and `end` of a catalog publisher rejects. Not run in such a runtime.
- **A limit on the payload of an Object for one subscription holds only from its SUBSCRIBE_OK on.** An Object whose length was read while the Track Alias of its stream was unknown is under the connection's limit (`maxObjectPayloadLength`, `packages/moqt/src/core/requests.ts`; `StreamStops::limit_payload`, `crates/moqt-io/src/streams.rs`; row "Undecoded bytes of subgroup streams"). Who sets one: `@xmoq/msf` and the terminal viewer and the transcriber for the catalog (1 MiB), `@xmoq/chat` and the terminal viewer for the chat's `lines` (64 KiB). A fetch stream is decoded by its reader, which can give a smaller limit, and `@xmoq/msf` does. No media track sets one.
- **`@xmoq/moqt` remembers no Object it sent.** A page answers the FETCH the relay sends it for a viewer's Joining FETCH only through its application (`serve({ fetch })`), which has to have kept the Objects, and has to pass LARGEST_OBJECT to `accept` (`packages/moqt/src/webtransport/connection.ts`). Without it the relay refuses a viewer's Joining FETCH for that subscription with `INVALID_RANGE`.
- **A FETCH of the peer that `@xmoq/moqt` accepted and that the subscriber neither reads nor gives up holds its two streams, and its place among `limits.maxPeerFetches`, for the session.** Behind the own relay this does not happen: the relay gives up on a subscriber that does not read and cancels upstream.
- **Through `moqtail`'s relay, what a page answers a FETCH with does not reach the viewer.** That relay sends the viewer a fetch stream that carries the Request ID of its own FETCH to the publisher, which no FETCH of the viewer has ([record](experiments/2026-10-11-a-page-answers-a-fetch.md)). The own relay writes the viewer's Request ID.
- **Authorization token structure (§10.2.2).** The sessions of both implementations carry the token as opaque bytes, so the alias types (REGISTER, USE_ALIAS, DELETE) and their rules are enforced only by a relay with a key, which decodes the Token (`RoomTokens::setup` and `RoomTokens::request`, `crates/relay/src/auth.rs`). The clients and a relay without a key do not (`Parameter::AuthorizationToken`, `crates/moqt/src/params.rs`; `AUTHORIZATION_TOKEN`, `packages/moqt/src/core/parameters.ts`). Left until authentication is decided.
- **Datagrams (§11).** Neither implementation delivers an OBJECT_DATAGRAM: it is dropped without notice, and its Object is lost. Both read every datagram for its type (row on a datagram of an unknown type). The rules on the fields of an OBJECT_DATAGRAM (§11.3.1: a PROPERTIES bit with a Properties Length of 0, STATUS with PROPERTIES, a Status that is not Normal; §11.2.1.1: an unknown Object Status) are checked by neither. Outside the Phase 0b scope ([record](experiments/2026-10-24-datagrams-read-by-the-browser-client.md)).
- **Connection flow control for control streams first (§11.4.2, MUST: "endpoints MUST allocate connection flow control to the control streams before allocating it to any data streams"). Met by the relay as a receiver; not as a sender, nor by the clients as receivers in the browser.** **As a receiver** the relay keeps its connection window above what the peer's unidirectional streams can hold (`receive_window_for` and `CONTROL_STREAM_RESERVE`, `crates/moqt-io/src/wt.rs`; row on the QUIC windows of the relay); a real connection did not get a request through 64 unread streams of 256 KiB with smaller windows, and did with these (`a_request_gets_through_data_streams_nobody_reads_only_where_the_windows_leave_room`, and the same with the relay's values, run once). The Rust client leaves quinn's connection window at its default (`client_config`, `crates/moqt-io/src/wt.rs`). **As a sender** the relay and the Rust client cannot keep credit for the control streams: quinn-proto 0.11.19 takes the peer's connection credit for a stream when it is written to (`write_limit`, `streams/state.rs`), first come first served, and a stream's priority orders only what goes into packets. `@xmoq/moqt` puts its data streams below its control stream (`DATA_STREAM_SEND_ORDER`, `packages/moqt/src/core/session-output.ts`); Chromium 156 was not seen to give its credit by that order ([record](experiments/2026-10-25-send-order-of-data-streams-in-chromium.md)). **As a receiver in the browser** the windows are the browser's, and the API has no way to set them; a deadlock of the kind the draft names was seen there for request streams, 3 of 3 (FIXME at `uniSlots`, `packages/moqt/src/webtransport/stream-io.ts`; [record](experiments/2026-10-10-subscription-backlog-in-chromium.md)). An application that reads, however slowly, frees the credit; one that never reads can stall its own session. Whether the client should end such a subscription itself is in [open questions](open-questions.md).
- **Stream error codes on reserved codepoints (`draft-ietf-webtrans-http3-16` §4.4, §9.5), in Rust.** A reset with a codepoint of the form `0x1f * N + 0x21` is reported with a code where it should be a reset without one (FIXME at the top of `crates/moqt-io/src/wt.rs`). The same goes for the code of a STOP_SENDING, which the relay and the Rust client print. A peer that maps its codes as §4.4 says never sends such a codepoint.
- **The code of a STOP_SENDING sent from a browser on a subgroup stream was not observed.** On a request stream it was: when an own-browser subscriber cancelled, the relay printed the code `0x1` that `@xmoq/moqt` puts into the `WebTransportError`, in 53 of 60 rounds; in the other 7 the relay saw the reset of the other direction first, and it prints the line only when the STOP_SENDING comes first. On a subgroup stream the relay notices a STOP_SENDING when it next writes to the stream, and no interop run has a subscriber stop a stream the relay is still writing ([record](experiments/2026-10-10-disconnects-through-own-relay.md)).
- **`PublishedTrack.ended` after a PUBLISH_DONE that could not be written, in `@xmoq/moqt`.** Not a requirement of the draft: `done()` rejects with the error of the write, and `ended` resolves only when the session ends, although the session state has ended the subscription.
- **A SUBSCRIBE that the Rust client reads before it has sent its PUBLISH gets `NOT_SUPPORTED`** (`refusal_code`, `crates/moqt-client/src/main.rs`). No rule is broken: the subscription §5.1 means ("an existing subscription in Pending (publisher) state") begins with the PUBLISH, and once that is sent the session answers `DUPLICATE_SUBSCRIPTION`, as `@xmoq/moqt` does. The relay waits for a PUBLISH after `DUPLICATE_SUBSCRIPTION` and not after `NOT_SUPPORTED`, so a subscriber whose SUBSCRIBE reaches that client through the relay before its PUBLISH is on the way gets `DOES_NOT_EXIST`. The track is there a moment later.
- **The Rust client in a mode that publishes leaves its peer unanswered in two waits.** While a SUBSCRIBE it is about to serve waits for `--serve-delay-ms` or for the driver's line `serve` (`before_serving`, `crates/moqt-client/src/main.rs`), and in the up to 3 seconds after its last PUBLISH_DONE, when it waits for the peer to end that stream. A request of the peer that comes in the first is answered when the wait is over; one that comes in the second gets no answer, and the session closes right after. In every other wait (the answers to its PUBLISH_NAMESPACE and PUBLISH, `--publish-delay-ms`, the driver's line `publish`, an Object under way, the end of the first stream when it publishes anew) it answers. What it holds unread meanwhile is `EVENT_QUEUE` events a queue (`crates/moqt-client/src/io.rs`), after which its readers wait.
- **`DUPLICATE_SUBSCRIPTION` from a publisher that sends no PUBLISH (§5.1, §10.6.2), in the relay.** The code is also the answer when the publisher still holds a subscription in the same role, for instance one the relay cancelled a moment ago. The relay cannot tell this from an announced PUBLISH and waits; up to `MAX_WAITING_SUBSCRIBERS` subscribers then get `TIMEOUT` when the wait for the answer is over, where asking the publisher again would have got them the track (FIXME in `on_upstream_refusal`, `crates/relay-core/src/routing.rs`; the gap on Retry Interval below).
- **A GOAWAY with a New Session URI on a request stream (§10.4, SHOULD: "the endpoint SHOULD re-issue that specific request on a session at the specified URI").** The clients that ask a request again after one (`keepTrackOnSession` of `@xmoq/moqt`, `KeptTrack` of `xmoq-viewer-io`, the gatherer, the transcriber) ask it on the session they have, where the URI names another: each keeps one session (FIXME at `request_moved` in `crates/chat/src/bin/xmoq-chat/session.rs` and `crates/transcriber/src/bin/xmoq-transcriber/session.rs`, and in `answered`, `crates/viewer-io/src/kept.rs`). The own relay sends no GOAWAY on a request stream.
- **A responder's FIN after its REQUEST_OK to PUBLISH_NAMESPACE: the two clients differ.** The TypeScript client ends the request (`peer-fin`); the Rust client does not read the stream of its PUBLISH_NAMESPACE after the answer and goes on as if announced. Which of the two is right is not decided; the row on a requester's FIN covers the other direction only. The own relay never finishes that stream this way.

The relay (`crates/relay-core`, `crates/relay`) adds these:

- **Several publishers of one track (§9.3, §9.5). The MUSTs are met in part.** §9.5: "Relays MUST send SUBSCRIBE messages to all matching publishers. This includes matching both Established subscriptions on the Full Track Name and Namespace Prefix Matching against published Namespaces." §9.3: "Relays MUST handle Objects for the same Track from multiple publishers and forward them to matching Established subscriptions." §9.5: "When a relay receives an authorized PUBLISH_NAMESPACE for a namespace that matches one or more existing subscriptions to other upstream sessions, it MUST send a SUBSCRIBE to the publisher that sent the PUBLISH_NAMESPACE for each matching subscription." §9.5: "When it receives an authorized PUBLISH message for a Track that has Established downstream subscriptions, it MUST respond with PUBLISH_OK." Against that stands §9.3: "An implementation can use mechanisms such as REQUEST_ERROR or unsubscribing (see Section 3.3.2) if it cannot accept an additional publisher due to implementation constraints." §9.5 again: "Relays MUST forward PUBLISH_NAMESPACE or PUBLISH messages to all matching subscribers": a SUBSCRIBE_NAMESPACE is told of the namespaces with NAMESPACE (row on SUBSCRIBE_NAMESPACE), and no PUBLISH is forwarded to a subscriber. What is done is in the rows on a PUBLISH for a track the relay knows already and on a SUBSCRIBE for a track that has no source. What is not done, five things, each against one of the MUSTs above (listed in the crate doc of `crates/relay-core/src/lib.rs`). **No more publishers are asked than the track has room for**, the one that sent PUBLISH_NAMESPACE first (`ask_the_publishers`, `crates/relay-core/src/routing.rs`). **A publisher that was passed over because the relay had 64 requests open on it is not asked when one of them ends**, but when the next subscriber of the track comes or a namespace of it is announced. **A publisher that was asked for a track and did not become a source is not asked for it again** until it announces a namespace of the track anew, or falls out of the `MAX_DECLINED_PUBLISHERS` a track remembers, though it is still a matching publisher. **A PUBLISH_NAMESPACE does not get its publisher asked for a track that has a source and no subscriber.** §9.5 has "a namespace that matches one or more existing subscriptions to other upstream sessions", and a PUBLISH the relay accepted is a subscription of the relay to an upstream session, with subscribers or without; read so, the publisher is to be asked. The relay reads the sentence as being about tracks somebody is subscribed to. WHY: nobody wants more of a track nobody receives, and the publisher that is asked would send it to the relay all the same. **A SUBSCRIBE for a track whose sources all drain is refused** (row below), where §9.5 has "If there are no Established upstream subscriptions for the requested Track, the Relay MUST send a SUBSCRIBE request to each publisher that has published the subscription's namespace or prefix thereof": such a track has no place for subscribers that wait.
- **Sources of a track that do not send the same thing (§9.1, §2.4.2, §9.3).** §9.1: "An endpoint that receives a duplicate Object with a different Forwarding Preference, Subgroup ID, Priority or Payload MUST treat the track as Malformed." §2.4.2, the sixth example of a malformed track: "The same Object is received more than once with different Payload or other immutable properties." §9.3: "The Relay SHOULD attempt to deduplicate Objects before forwarding, subject to implementation constraints." Of the four, the relay compares the Priority, for a Subgroup it remembers and where it can tell the priority (the known gap on when a priority is compared); the Forwarding Preference, the Subgroup ID and the Payload are not compared, so the MUST is met in part, and duplicates are removed by Subgroup and not by Object (the comment on `Subgroups`, `crates/relay-core/src/lib.rs`; row on how long the relay remembers). Runs with two publishers were done with publishers that send the same Object under the same Group ID only.
- **A session that has as many timers running as it may gets the next one at once (relay).** A timer beyond `HubConfig::max_timers_per_session` is not started and is reported as run out at once, so a wait for the last streams after PUBLISH_DONE ends as soon as it begins, an early stream is dropped at once, and a request the relay sent counts as unanswered at once (row "Timers running for one session"). The timers that give a session an announcement back and that send an announcement upstream again are started all the same (`Hub::timer_limit`, `crates/relay/src/hub.rs`).
- **A stream of a subscription that comes after a new subscription took its Track Alias (§10.11, §11.1).** A publisher says PUBLISH_DONE with a Stream Count, one of the streams it counted is still on its way, and a PUBLISH or SUBSCRIBE_OK that is accepted gives the alias to a new subscription. The late stream is taken for one of the new subscription: its Objects are delivered under it, and its end counts towards the Stream Count of the new subscription's PUBLISH_DONE, which can then end that wait while a stream of the new subscription is open. **Such a stream is also read with the DEFAULT PUBLISHER PRIORITY of the new subscription where its header has no priority**, and where the two defaults differ for a Subgroup the relay remembers, the track ends for every subscriber as malformed, though nothing is wrong with it. **The same happens the other way round, with a stream of the new subscription that the relay reads before the PUBLISH_DONE of the first.** The streams of the old subscription that are open when the alias is taken are not counted (row on a reused Track Alias). The draft gives a receiver no way to tell the others apart. Tests pin the three (`known_gap_*` in `crates/relay-core/src/tests/sources.rs`).
- **Streams a publisher sent ahead for a PUBLISH that is refused, under the Track Alias of a subscription that drains (§5.1, §10.10, §10.11).** §5.1: "Publishers MAY start sending Objects on PUBLISH-initiated subscriptions before receiving a PUBLISH_OK response". A publisher says PUBLISH_DONE, sends PUBLISH again under the same Track Alias while the streams the first one counted are awaited, and opens a stream at once. When the PUBLISH is refused, the alias means the draining subscription again, and nothing tells that stream from one of it: its Objects go to the subscribers of the draining subscription's track, and its end counts towards the Stream Count. With that the count can be reached before the streams that were counted have ended, and the first PUBLISH stream then gets its FIN early; a counted stream that comes after is stopped. The refused PUBLISH can be for another track, whose Objects then go out under the first track. The draft gives a receiver no way to tell the two apart. A PUBLISH that is refused before the session looks at its alias (`DUPLICATE_SUBSCRIPTION`, a Mandatory Track Property) and a refused SUBSCRIBE_OK leave the same behind. At the relay this takes a PUBLISH that is refused, which leaves a track that has all the sources it may have, a Mandatory Track Property, and the limit of open requests; a publisher that publishes its own track anew is accepted, under the same alias and under another. A test pins it (`known_gap_a_stream_sent_ahead_for_a_refused_publish_is_taken_for_the_draining_one`, `crates/relay-core/src/tests.rs`).
- **A Subgroup without a Publisher Priority reaches the subscribers under the default of another source (§11.4.2, §12.4), in the relay.** Such a Subgroup has the DEFAULT PUBLISHER PRIORITY of the subscription it came on. The relay passes its header on as it came, and the Track Properties the subscribers have are those of the source that came last (§2.5), so with two sources whose defaults differ, a Subgroup of the first is read with the default of the other. A test of the core pins it. Mending it means writing the priority into the header where a track has had several sources, which goes with the question of whose Track Properties a track with several sources has.
- **Two DEFAULT PUBLISHER PRIORITY properties in one message are not refused (§12.4), in the relay.** The relay takes the first where it compares priorities (`default_publisher_priority`, `crates/relay-core/src/lib.rs`), and passes both on.
- **A Publisher Priority is compared only for a Subgroup the relay remembers, and not where it cannot tell the default (§2.4.2).** A Subgroup that comes again after the relay has forgotten it (`MAX_REMEMBERED_GROUPS`, `MAX_REMEMBERED_SUBGROUPS`, `crates/relay-core/src/lib.rs`) passes or is left like any other. A stream without a priority in its header under a Track Alias whose subscription drains is not compared either, and where the Subgroup is taken from it, the priority the relay remembered for that Subgroup is gone: a later stream is compared again only once the Subgroup has been taken from a stream whose priority is known, which a second stream of the same source does and a stream of another source, which is left, does not. All of that is on the side of not finding a difference.
- **The fourth example of a malformed track is looked for across streams only in the Group the cache keeps (§2.4.2).** The fifth, an Object past the END_OF_TRACK Object, is found across streams (`Track::past_its_end`, `crates/relay-core/src/lib.rs`; row on an Object past the end of a track). The fourth, an Object past the End of Group, is found across streams only for the Group the cache keeps and has not given up (`Track::malformed_at`, `crates/relay-core/src/lib.rs`), and otherwise within one subgroup stream (row on an Object after End of Group or End of Track). The seventh, another Forwarding Preference than before, cannot come about, since the relay reads no datagrams.
- **Objects past the end of a Subgroup, and a Subgroup on two streams that both end with a FIN with different last Objects, where the relay does not read the second stream (§2.4.2, the second and third example of a malformed track).** The relay finds both only on a second stream of the same source for a Subgroup it delivered whole (row on a Subgroup that ends twice). Where it does not look is listed at `Subgroups` (`crates/relay-core/src/lib.rs`): a stream of another source, a second stream whose header is read before the FIN of the first, a stream past `MAX_CHECKED_STREAMS_PER_TRACK` or `CHECKED_STREAM_WAIT_MS`, and a Subgroup the relay has forgotten.
- **A second stream for a Subgroup the relay has forgotten (§2.2).** It passes, so the subscribers can get a Subgroup on two streams of which neither was reset, which §2.2 has as MUST NOT. When the relay forgets is at `MAX_REMEMBERED_GROUPS`, `MAX_REMEMBERED_SUBGROUPS` and `Subgroups::admit` (`crates/relay-core/src/lib.rs`). It takes more than 32 Subgroups a Group on average over 8 Groups, or more than 256 in one; a publisher that sends every Object as a Subgroup of its own gets there. With one source per track it also takes a publisher that sends a Subgroup twice. Once a track has had several sources, only the limit of 256 is left.
- **Which of two open streams for a Subgroup the source goes on with (§11.4).** The relay keeps the one whose header it read later (`Subgroups`, `crates/relay-core/src/lib.rs`). When a source resets a stream and sends the Subgroup again, and the header of the first stream is read after that of the second, the relay stops the second and keeps the first, which ends with the reset; §11.4.3 has "A publisher that receives a STOP_SENDING on a Subgroup stream SHOULD NOT attempt to open a new stream to deliver additional Objects in that Subgroup", so the Subgroup is lost for every subscriber. No subscriber gets a wrong Object. Whether this happens with real peers was not looked at.
- **A Subgroup that a subscriber stopped reaches it again on another stream of its source (§11.4.3).** "SHOULD NOT attempt to open a new stream to deliver additional Objects in that Subgroup". A subscription whose stream was stopped with `STOP_SENDING` gets no other stream for it from the source's stream that goes on (`InStream::stopped` and `Relay::out_stream_stopped`, `crates/relay-core/src/lib.rs`); where the Subgroup is taken anew from another stream of the source, it gets one again (the gap on a second stream for a Subgroup above). A `STOP_SENDING` is seen when the relay next writes on the stream, so a stop that comes after the last Object is not marked. A test of the core pins it; the case was not run with a peer that sends `STOP_SENDING` on a subgroup stream.
- **A SUBSCRIBE whose End Group is over already, or whose filter has no Location to start at, is accepted, in the relay (§5.1.2, SHOULD).** "If the publisher cannot satisfy the requested Subscription Filter ... or if the entire End Group has already been published it SHOULD send a REQUEST_ERROR with code INVALID_RANGE." The relay answers SUBSCRIBE_OK. It does not know that an End Group is published whole, and a Group at or before the End Group that reaches it late is still sent, so such a subscription can get Objects. The MUST NOT of that paragraph is kept (`Subscriber::start` and `Subscriber::end_group`, `crates/relay-core/src/lib.rs`).
- **A subscription is not ended when the End Group of its filter has passed, in the relay.** No PUBLISH_DONE with `SUBSCRIPTION_ENDED` (0x3) is sent; the subscription stays until the subscriber ends it or the track does. §9.4 does not ask it of a relay (`Subscriber::end_group`, `crates/relay-core/src/lib.rs`).
- **A Subscription Filter that a REQUEST_UPDATE brings is not applied, in the relay (§10.2.9).** An update that carries one is refused, and the subscription ends (row on REQUEST_UPDATE for an Established subscription; `Session::answer_update`, `crates/moqt/src/session/peer.rs`).
- **A publisher that is one of the two clients does not look at the Subscription Filter of a SUBSCRIBE (§5.1.2, MUST NOT).** `@xmoq/moqt` hands the SUBSCRIBE of a peer to its application with the filter in it, and sends what the application writes; the Rust client in the mode that serves a SUBSCRIBE sends every Object from the next one on. The own relay asks a publisher without a filter (row on the relay's SUBSCRIBE to a publisher), so neither is asked for one behind it.
- **NEW_GROUP_REQUEST (§10.2.13), DYNAMIC_GROUPS (§12.6). Met in part.** The relay passes the request on (row on NEW_GROUP_REQUEST). **Only the video sender of `@xmoq/media` begins a Group for a request**, and only where its caller gives `dynamicGroups`; the demo does not. `playVideoTrack` joins with a Joining FETCH and sends the parameter only when asked (`joiningFetch` and `newGroupRequest`, `packages/media/src/web/play-video-track.ts`). The terminal viewer sends neither, and waits for the next key frame. `@xmoq/moqt` refuses every PUBLISH of the peer with `NOT_SUPPORTED`, so a page has no subscription a PUBLISH made to ask for; the Rust session accepts one and can ask (`Session::update_published`), and only the relay does.
- **Delivery timeouts (§8, §10.2.3, §10.2.4). Met in part.** *As the draft has it*: the relay acts on the `SUBGROUP_DELIVERY_TIMEOUT` of a SUBSCRIBE and of a REQUEST_UPDATE (row on a SUBGROUP_DELIVERY_TIMEOUT that a REQUEST_UPDATE changes). A subgroup stream towards that subscriber that the transport has not acknowledged whole when the timer is over is reset with `DELIVERY_TIMEOUT` (0x2), and the subscription goes on; 0 is no timeout, and the timeout is never sent upstream (`OutgoingSubgroup::spawn`, `crates/moqt-io/src/streams.rs`). *The relay's own, off unless a flag asks*: `--delivery-patience-ms` is a time for the subscribers that set none, **which leaves §8's "if none of the timeouts are set to a non-zero value, all Objects ... are delivered"** for them (`SendLimits::delivery_patience`, `crates/moqt-io/src/streams.rs`). WHY NOT "give the older Groups of a track up when a newer one begins": with a sound of one piece a Group and no grace, 204 to 375 of about 985 pieces sounded on a link of 2 and 2.5 Mbit/s ([record](experiments/2026-10-12-a-page-behind-a-link-with-too-little-room-and-a-relay-that-gives-groups-up.md)), and a viewer that asks for 100 ms on its video alone has the picture that gave with 100 ms of grace, and its sound whole ([record](experiments/2026-10-12-the-relay-follows-the-delivery-timeout-a-viewer-asks-for.md)). **Not met** (the FIXME at the top of `crates/relay-core/src/lib.rs`): the Track Properties `SUBGROUP_DELIVERY_TIMEOUT` and `OBJECT_DELIVERY_TIMEOUT` of a publisher are not read, so the smaller of the publisher's and the subscriber's (§8) is not taken; `OBJECT_DELIVERY_TIMEOUT` in a SUBSCRIBE or a REQUEST_UPDATE is accepted and not acted on. §8 has it checked "before attempting to pass [the Object] to the underlying transport", and the relay hands every Object to a send window of 4 MiB as it comes, so the check would never fail; "SHOULD minimize the amount of data buffered at the underlying transport layer" is not followed. The two clients hand a peer's SUBSCRIBE to the application with its parameters, and neither acts on them.
- **How often the sessions together may announce is not bounded (§13.1), in the relay.** One session is (`MAX_ANNOUNCEMENTS_AT_ONCE` and `ANNOUNCEMENT_EVERY_MS`, `crates/relay-core/src/routing.rs`; row "How often a session may announce"). Each announcement that is accepted makes the relay forget that the session declined the tracks of the namespace and ask it for up to 64 of them. Every session has its own allowance, and the relay takes `HubConfig::max_sessions`. §13.1's "Relays SHOULD implement rate limiting on subscription requests" is about the subscription requests of a subscriber, for which the relay has no rate limit, and does not name announcements. **What a subscriber that asks for a new track name each time costs**: the relay sends one SUBSCRIBE to every session that announced a namespace of the track for each such request, so with four of them 1,000 requests a second became 4,000 a second upstream; the relay took 0.44 of a core (0.2 with one publisher), and the Objects of the sessions beside it were not late (95th percentile 0.7 to 1.2 ms, on 11 cores). A session that does not end its requests is stopped by the 256 it may have open. With a publisher that does not answer, one session takes no more of it than its share (`MAX_OWN_REQUESTS_FOR_ONE_SUBSCRIBER`; `MAX_OWN_FETCHES_FOR_ONE_SUBSCRIBER`, `crates/relay-core/src/fetch.rs`); several sessions are the item below. More than four publishers and a machine with one core were not run ([record](experiments/2026-10-13-a-session-that-asks-for-a-new-track-again-and-again.md)).
- **Retry Interval (§10.6.2).** Where several publishers were asked, the subscribers get the Retry Interval of the answer that came last (row on the publisher's answer). What an implementation gives a REQUEST_ERROR it makes up itself is in the row "The Retry Interval of a REQUEST_ERROR" (`retry_interval_of`, `crates/relay-core/src/routing.rs`). **0, which reads as "do not retry", is still given where a retry could succeed a moment later** with `DUPLICATE_SUBSCRIPTION`: to a publisher whose PUBLISH is read before its own PUBLISH_DONE for the track (row on a PUBLISH for a track the relay knows already), and to a viewer that asks anew before it was sent PUBLISH_DONE. The values are fixed numbers, and nothing is randomized. The relay does not honour a Retry Interval either: a publisher that declined a track is not asked for it again until it announces the namespace anew, whatever the Retry Interval was, and is asked at once then, also after Retry Interval 0 ("If the value is 0, the request SHOULD NOT be retried") (row on which publishers the relay asks). That memory goes with the track, and a track forgets the oldest of more than `MAX_DECLINED_PUBLISHERS`, which the next subscriber has asked again. Where the last refusal ended a track that had no source, the next subscriber makes the relay ask every matching publisher again at once, also the ones that answered 0 or a wait that is not over.
- **REQUEST_UPDATE** is applied for one thing: the SUBGROUP_DELIVERY_TIMEOUT of a subscription, in the relay. Every other update of a subscription is refused (`Session::answer_update`, `crates/moqt/src/session/peer.rs`), so the Forward State, the filter and the priority of a subscription cannot change; a NEW_GROUP_REQUEST is accepted and, in the relay, passed on (row on NEW_GROUP_REQUEST). For a FETCH it is accepted and changes nothing (row on REQUEST_UPDATE for a FETCH). The two clients send one for a SUBSCRIBE of their own (`Subscription.update`, `Session::update_subscription`); none for a FETCH or a PUBLISH_NAMESPACE, and for a subscription a PUBLISH of the peer made only the Rust session, for the relay's NEW_GROUP_REQUEST. **A REQUEST_UPDATE that gets no answer leaves the subscription as it is**: after the time a request gets (row on a request the peer does not answer), the browser client rejects the call and the Rust client prints `ANSWER_TIMED_OUT request=update`; neither ends the subscription, and an answer that comes later is still read (`send_update`, `crates/moqt-client/src/main.rs`).
- **A Joining FETCH for a subscription that a PUBLISH made is refused (§5.1, §10.12.2).** §5.1 gives such a subscription a Joining Location ("communicated in ... PUBLISH"), and the change log of draft 18 has "Allow joining FETCH for PUBLISH and REQUEST_UPDATE with forward=1"; the Joining Request ID is then the Request ID of the publisher's PUBLISH. The Rust session takes only a SUBSCRIBE of the peer and answers `INVALID_JOINING_REQUEST_ID` for the rest, and sends no Joining FETCH that names a PUBLISH of the peer (the FIXME in `crates/moqt/src/session/peer.rs`). It is met when a viewer that got a track by PUBLISH, and not by its own SUBSCRIBE, sends a Joining FETCH to the publisher that published it: the own browser publisher sends PUBLISH, and the relay sends none.
- **The Forward State of the subscription a Joining FETCH names is not looked at by the session (§10.12.2, MUST).** "A Joining Fetch is only permitted when the associated subscription has Forward State 1; otherwise the publisher MUST respond with a REQUEST_ERROR with error code INVALID_RANGE." Whoever answers the FETCH has to check it. The relay does (`Relay::join`, `crates/relay-core/src/fetch.rs`); the Rust client refuses every Joining FETCH (`refusal_code`, `crates/moqt-client/src/main.rs`).
- **Priorities (§7.2, §7.3). Met in part, in the relay.** Each stream the relay opens to a subscriber gets a priority of the transport from the SUBSCRIBER_PRIORITY of the SUBSCRIBE and the stream's Publisher Priority, §7.2's first two steps, below the control stream and the request streams (`send_order`, `crates/relay-core/src/lib.rs`). **Not met**: the third and fourth steps, the Group by the GROUP_ORDER and the lowest Subgroup ID (WHY NOT at `send_order`); `moqtail`'s relay (0.15.0, `compute_stream_priority`) has the Group in it. Streams with the same two priorities take turns, old Groups with new. GROUP_ORDER is decoded and not used; a SUBSCRIBER_PRIORITY in a REQUEST_UPDATE of a subscription is refused; **a fetch stream** stands by the SUBSCRIBER_PRIORITY of its FETCH, or of the REQUEST_UPDATE for it that came last, and a Publisher Priority of 128, whatever the Objects in it have (`fetch_send_order`, `crates/relay-core/src/fetch.rs`), and a Joining FETCH is not put before the subscription it joins; the relay's own subscriptions upstream name no priority. **The clients** write each stream as its bytes come and give the transport no priority; the audio publisher of `@xmoq/media` can name a Publisher Priority for its streams and names none by default. A priority is strict: a publisher that puts its sound below its video has the sound not sent on a link without room for both ([record](experiments/2026-10-13-the-sound-behind-the-video-on-a-narrow-link-and-priorities.md)). **Three things a priority does not reach** (read in the code on 2026-10-13): (1) the first bytes of every stream, its type of WebTransport, are written by `web-transport-quinn` 0.13.2 with the highest priority there is before the relay's number is set (`Session::open_uni`: "Max priority for the header so the application cannot queue lower-priority data in front of it"), so a track that opens a stream for every small Object may be ordered less than its priority says; not measured. (2) The order holds for what the transport has buffered and not sent, which is at most the send window of the connection (4 MiB), and a writer that waits for room there waits whatever its priority. Behind a link of 2 Mbit/s with a video of 2.65 and no timeout on the video, the window was full from about 52 s, and the sound came later and thinner from then, with a priority above the video as without; a window of 1 MiB brought it at about 20 s ([record](experiments/2026-10-15-what-the-sound-waits-behind-on-a-narrow-link.md), the relay's `--stats-every-ms`). Not to be built, decided on 2026-10-21: a relay that sends from its writers of the highest priority first, and the sound above the video by default. The demo's viewer asks for 150 ms on its video, and with that the send window does not fill. (3) The relay's limit on what waits for one subscriber (`SendBudget`, `crates/relay/src/hub.rs`) is one for the session and not one for each subscription; the subscription it ends is the one whose open streams carry the most bytes (row on a subscriber that does not take what is sent to it). Behind a link of 2 Mbit/s with a video of 2.65 and the demo's viewer as it is, nothing was ended in 3 minutes, in a run made while the relay ended the subscription that went over instead ([record](experiments/2026-10-14-three-minutes-behind-a-narrow-link-and-the-relays-limit-for-one-viewer.md)).
- **Not verified against a real connection: what the relay does when it gives a fetch stream up before it is open.** A subscriber that takes nothing has its fetch stream reset with `TOO_FAR_BEHIND`. Where the relay was writing the stream this is tested, over loopback as well (`xmoq-moqt-io`: a writer that resets while its write waits). Where it gave up while the FETCH_HEADER was not all written, the reset is tested on an in-memory connection whose streams hold one byte, and on no real one: there the wait is more likely inside the opening of the stream, where there is nothing to reset. The relay's own clocks (10 seconds for the opening, and 10 for each piece it writes) run in tests on in-memory connections only. So does the stopping of a fetch stream the relay writes itself, when its FETCH is cancelled or its track is found malformed: the stream is a few bytes, which a real transport takes before a cancellation can arrive, and no run stopped one.
- **The relay does not look into a fetch stream it passes on (§2.4.2, §11.4).** It reads the FETCH_HEADER, writes one with the subscriber's Request ID, and moves the rest as bytes (`crates/relay-core/src/fetch.rs`). So it does not find what breaks the object model there: Properties that are malformed, an Object after the end of its Group, a duplicate that differs. §2.4.2: "If a relay detects a Malformed Track, it MUST immediately terminate downstream subscriptions with PUBLISH_DONE and reset any fetch streams with Status Code MALFORMED_TRACK"; a publisher's malformed fetch stream reaches the subscriber as it is, and the subscriptions to the track go on. A stream that ends with a FIN inside an Object (§11.4, a protocol violation) is passed on with its FIN as well. Nothing of a fetch stream raises the largest Location the relay knows for the track.
- **The relay leaves the range of a FETCH to the publisher (§10.12.3, §10.13).** It checks that a Standalone FETCH does not end before it starts, and passes the Start Location and End Location on. For a FETCH it asks a publisher for, whether the range starts after the largest Object (`INVALID_RANGE`), where it is cut when it ends beyond it (the End Location of FETCH_OK), and the order of the Groups are what the publisher answers; the relay passes the answer and the stream on and compares neither with what it knows of the track. Only a FETCH the relay answers itself, from its cache or with FILL_TIMEOUT 0, gets the relay's own End Location, and with FILL_TIMEOUT 0 its own `INVALID_RANGE` (`answer_without_asking`, `crates/relay-core/src/fetch.rs`). The `moqtail` test client as a publisher answers some of these otherwise than the draft has them ([record](experiments/2026-10-11-standalone-fetch-through-own-relay.md)), and so does what its subscriber gets through the relay.
- **Several sessions of one sender can keep every other from a publisher.** The relay asks one publisher for 16 FETCHes at once and has 64 requests open on it in all; one subscriber's session gets 4 and 8 of them (row "How much of a publisher one subscriber's session may take"), so it takes 4 sessions to have all 16 FETCHes, and 8 to have all 64 requests, and any other subscriber's request for that publisher is then refused with `EXCESSIVE_LOAD`. The relay takes `HubConfig::max_sessions` and does not count how many come from one place. A FETCH has no time limit as a whole, so a subscriber that reads fast enough not to be cut, and no faster, holds its FETCHes for as long as they last. Subscriptions are not touched by this: the publisher keeps 48 of its streams for them. Nothing here is authorized, so any client that reaches the relay can do it. Whether a FETCH gets a time limit as a whole is open with the other limits. On real connections, in a run made when one session could have all 16 ([record](experiments/2026-10-11-rust-client-fetch.md)): a subscriber that read 16 KiB of each of its 16 fetch streams every half second held them, and another subscriber's FETCH was refused meanwhile; one that read the same every 2 seconds was cut as taking nothing, so on a real connection the slowest a subscriber may read is faster than the 1 KiB in 10 seconds the relay counts by. Where that lies was not measured.
- **The Rust client answers a FETCH only with `--answer-fetch`, and then only a Standalone one.** Without the flag: `NOT_SUPPORTED`, in every mode, which drivers count on to see what a relay makes of the refusal. With it, in the modes that publish: row on a publisher that answers a Standalone FETCH from what it published. A Joining FETCH is refused with `NOT_SUPPORTED` in either case (`refusal_code`, `crates/moqt-client/src/main.rs`); behind a relay a publisher gets none. It sends Standalone and Joining FETCH requests and reads their fetch streams.
- **A FETCH_OK with a Mandatory Track Property that comes after the fetch stream was passed on whole resets nothing (§2.5.1).** "If the relay has already forwarded data on a fetch stream, it MUST reset the stream": while the stream is passed on the relay does, with `UNSUPPORTED_EXTENSION` (`on_fetch_not_processed`, `crates/relay-core/src/fetch.rs`). When the publisher's stream ended with a FIN before its FETCH_OK came, the FIN has gone to the subscriber and there is no stream left to reset; the subscriber gets REQUEST_ERROR `UNSUPPORTED_EXTENSION` after a fetch stream that looked complete.
- **The relay's cache is the latest Group of a track, and nothing a FETCH brought (§9.1).** A FETCH for anything else is asked of a publisher, also for Objects that passed through the relay a moment ago (`crates/relay-core/src/cache.rs`). The answer a publisher gives to a FETCH the relay passes on is not cached: the relay does not look into a fetch stream. So a publisher that sent an Object once, long before, and to no subscription that reached the relay, is asked for it every time; a publisher that pushes its Objects with PUBLISH, as the browser publisher does, has its latest Group in the cache.
- **The relay finds an Object that comes again with other content, and a Group that contradicts itself, only in the Group its cache holds (§9.1, §2.4.2, §12.9; MUST).** What it compares an Object with is the latest Group of the track, as far as the cache has it (`Cache::insert`, `crates/relay-core/src/cache.rs`). Nothing is found in an earlier Group, in a Group the cache gave up (over the limits, with an End of Track, with a stream whose default priority the relay cannot tell, after an Object was taken back, after an Object came at the Object ID of an End of Group, or after a second status came above one), or in a track that is not cached at all (MAX_CACHE_DURATION or Immutable Properties among its Track Properties): there a second Object goes out to the subscribers as it comes. Nor is an Object of a fetch stream the relay passes on from a publisher compared with anything. A Forwarding Preference cannot differ, since the relay takes no datagrams. What is compared in every track is the Publisher Priority of a Subgroup the relay remembers (row on a Subgroup that comes with another Publisher Priority).
- **The end of a track that a FETCH says is taken from its FETCH_OK, not from its fetch stream (§2.4.2, §10.13).** The relay ends a track as malformed for an Object past one with the status END_OF_TRACK on a subgroup stream (row on a malformed track), and takes the End Location of a publisher's FETCH_OK with End Of Track 1, less one, for the final Object of the track; an End Location with Object 0 says the whole Group, whose last Object is then not known. Where a larger Object or another final Object is known, that FETCH alone is refused with `MALFORMED_TRACK` and the track goes on, where §2.4.2 would have the track malformed (`Track::ends_at`, `crates/relay-core/src/lib.rs`). "The last Object sent in a FETCH whose response indicated End of Track" is not looked for on the fetch stream: the relay does not read into a fetch stream it passes on.
- **An Object that comes where the relay recorded that none exists is sent on (§9.1, SHOULD NOT).** "As described in Section 2.1, an endpoint can receive an Object after it has already recorded that the Object does not exist. A caching relay SHOULD NOT cache or forward the Object in this case." The relay does not cache it, and forwards it (`Cache::insert`, `crates/relay-core/src/cache.rs`; row on an Object that comes again).
- **The application gets Immutable Properties as one property with its bytes.** Both sessions, and the readers of LOC in both implementations, look inside them for what they read (`locProperties`, `packages/media/src/moqt/loc-properties.ts`; `searched_properties`, `crates/moqt/src/immutable.rs`). Any other reader of a property above the session has to open them itself (§12.7, MUST).
- **FETCH_OK from the relay's cache has End Of Track 0 where no Object with the status END_OF_TRACK came** and no publisher's FETCH_OK with End Of Track 1 gave the final Object (`write_answer`, `crates/relay-core/src/fetch.rs`; `Track::ends_at`), also where the track's publisher has sent PUBLISH_DONE with TRACK_ENDED and the relay waits for its last streams; a publisher asked for the same range might say 1. PUBLISH_DONE names no Location (§10.11), and it comes before the streams its Stream Count names have ended, so the largest Object the relay has received when it comes need not be the last, and taking it as the end would make a track malformed whose later Object is larger (§2.4.2). Once every stream the Stream Count names has ended, the relay removes the track of its last source with its cache. Answering from the cache with End Of Track 1 needs the relay to keep a track that has ended, which `crates/relay-core/src/cache.rs` has as not done.
- **A Descending FETCH with FILL_TIMEOUT 0 whose range reaches beyond the Group the relay's cache keeps gets no Object (§10.2.5).** The whole range is one End of Unknown Range indicator, where an Ascending one gets the cache's Objects (row on FILL_TIMEOUT 0; WHY NOT at `answer_without_asking`, `crates/relay-core/src/fetch.rs`). §11.4.4.2 does not say where an indicator begins in a Descending stream.
- **Several sessions of one sender can use up what the relay's fetch streams may keep beyond its cache.** The relay has 256 MiB for all and 32 MiB for one session (`MAX_BYTES_HELD_BEYOND_THE_CACHE` and `SHARE_OF_BYTES_HELD_BEYOND_THE_CACHE`, `crates/relay-core/src/fetch.rs`; row "What the relay's fetch streams keep beyond its cache"). Eight sessions that each keep their share have the whole; a FETCH the cache could answer is then refused with `EXCESSIVE_LOAD` for everybody, and a Group the cache lets go of is taken from the session that has the most kept, which need not be one of the eight. The relay takes `HubConfig::max_sessions` and does not count how many come from one place. A fetch stream that is passed on from a publisher has no time for the whole, and is not counted: its bytes are the publisher's.
- **A Joining FETCH that has no FETCH_OK yet ends when its subscription does, in the relay (§10.12.2).** The draft says what a Forward State of 0 does to an accepted Joining FETCH and nothing of a subscription that ends. The relay refuses the FETCH with `INVALID_JOINING_REQUEST_ID` and cancels what it asked of the publisher, also where the publisher's fetch stream is already passed on ahead of its FETCH_OK (`subscribe_is_over`, `crates/relay-core/src/fetch.rs`). A FETCH that has its FETCH_OK goes on to its end. What ends a subscription: the subscriber cancels its SUBSCRIBE; the track ends with PUBLISH_DONE or is found malformed (then the code is `MALFORMED_TRACK`); the subscriber falls behind and the relay ends the subscription with `TOO_FAR_BEHIND`; the subscriber sends a REQUEST_UPDATE for it, which the relay refuses with `UPDATE_FAILED`. Only the first is the subscriber's wish. A viewer whose publisher ends the track, or that is slow at the moment it joins, loses the Groups before as well, if the publisher has not answered the FETCH by then.
- **The relay passes an Object on only once it is whole (§5.1: "A publisher SHOULD begin sending incomplete objects when available").** A subscriber gets an Object that is under way when its last byte has reached the relay, and a FETCH whose range has one is held until then (`ReceiptWait`, `crates/relay-core/src/fetch.rs`; row on a FETCH for an Object the relay is receiving). Passing Objects on as they arrive is what would take the place of that hold.
- **What a Joining FETCH and a subscription that starts at or before the Joining Location deliver can overlap, in the relay.** Such a subscription is one without a filter, or with an `AbsoluteStart` or `AbsoluteRange` filter whose Start Location is not after the Joining Location. The FETCH ends at the Joining Location (§10.12.2.1), and a subscription with the Largest Object filter starts right after it, so the two are "contiguous and non-overlapping"; the draft states that for no filter in particular, and has no word on a subscription that starts before it (row on the Subscription Filter of a SUBSCRIBE). An Object at or before the Joining Location that reaches the relay after the SUBSCRIBE, on a stream that was behind, goes out on such a subscription and is in the fetch stream as well. With a Next Group Start filter nothing overlaps, and the rest of the Group of the Joining Location is in neither. `@xmoq/moqt` sends the filter its application gives it, and none without one; the Rust client sends Largest Object unless `--subscription-filter` says otherwise. The `moqtail` relay 0.15.0 showed an overlap of another origin, a range counted from the largest Location at the time of the FETCH ([record](experiments/2026-10-11-moqtail-relay-fetch.md), a).
- **A Joining FETCH can miss Objects where a track has several sources, in the relay (§10.12.2.1).** The Joining Location is the largest Location the relay knows of the track, from any source, and the FETCH is asked of the first source first (`whom_to_ask`, `crates/relay-core/src/fetch.rs`). A publisher that is behind the others is asked for a range it has not reached: where it answers `INVALID_RANGE`, the next one is asked; where it answers with what it has, what lies between its largest Object and the Joining Location is neither on the fetch stream nor on the subscription. Which publisher a FETCH should go to where several publish a track is not decided. Seen in a test of the relay core (a source with the largest Location {5, 2} is asked for {9, 0} to {9, 1}); not run against real publishers.
- **The Rust client answers a Joining FETCH that is read before its SUBSCRIBE with `NOT_SUPPORTED`**, as it answers every Joining FETCH (row on a Joining FETCH that names a Request ID the peer has not used yet). `@xmoq/moqt` refuses it with the same code by itself.
- **A Joining FETCH for a SUBSCRIBE with Forward State 0 that the relay has not answered is held, and refused when the SUBSCRIBE is accepted (§10.12.2).** The Forward State is in the SUBSCRIBE, so `INVALID_RANGE` could be said at once; the relay says it where it works the range out (`Relay::join`, `crates/relay-core/src/fetch.rs`).
- **The publisher does not learn the priority of the relay's FETCH.** The relay's FETCH names no SUBSCRIBER_PRIORITY (row on the parameters of the relay's FETCH), and a REQUEST_UPDATE for a FETCH is answered by the relay and moves only the fetch stream to the subscriber (row on the priority of a FETCH). Where the publisher's link to the relay is the narrow one, the publisher orders the relay's fetch streams by its own defaults.
- **Messages the relay does not implement (§4, MUST: "Relays MUST implement all MOQT messages defined in this document, as well as processing rules described in Section 9").** SUBSCRIBE_TRACKS and datagrams are refused or not read, as the rows at the top say, TRACK_STATUS is answered (row on TRACK_STATUS in the relay's table), SUBSCRIBE_NAMESPACE is served (row on it in the relay's table) without a REQUEST_UPDATE of it, and GOAWAY is taken from a client, and sent when the relay is told to stop (rows on GOAWAY); REQUEST_UPDATE is applied for one parameter of a subscription, passes a NEW_GROUP_REQUEST on, and is refused for the others (the gap on REQUEST_UPDATE above).
- **Authorization (§9.4, §9.5).** Off unless the relay is given a key (row on the relay's authorization; `crates/relay/src/auth.rs`); without one nothing is checked. With one, a subscription that was allowed goes on after its token has expired (the FIXME in `crates/relay/src/auth.rs`). A publisher's `UNAUTHORIZED`, `MALFORMED_AUTH_TOKEN` or `EXPIRED_AUTH_TOKEN` to the relay's SUBSCRIBE reaches the subscribers as it is, although it is about a token the subscriber did not send there and cannot mend. A publisher behind the relay does not see a subscriber's AUTHORIZATION_TOKEN. Any session can announce any namespace, the one with no fields included (§2.4.1 allows "between 0 and 32 Track Namespace Fields"), which matches every track: whoever announces it first gets the SUBSCRIBE for every track that nobody has published. With several sources of a track, any session can also become a source of any track that has one, by sending PUBLISH for it, and then: end the track for every subscriber by sending something that breaks the object model (§2.4.2), for which one subgroup stream with another Publisher Priority than the Subgroup had is enough; take a Subgroup from the other sources by sending it first; keep the other sources from being heard, by sending one stream with a Group ID far ahead of theirs; make the relay forget which stream it took a Subgroup from, by sending more Subgroups than it remembers, after which the same Subgroup can reach the subscribers on two streams (§2.2); raise the largest Location of the track, with the LARGEST_OBJECT parameter of its PUBLISH or with an Object on a stream that is passed on, so that a subscriber that comes gets a LARGEST_OBJECT the other publishers never sent; and send so many streams that a subscriber runs into the limit of what waits to be written and loses its subscription. The newest Group of a track is kept for the track and not for each source, on purpose: a share for each source needs to know who a source is. Any session can also ask any publisher for a FETCH of any track, and several sessions can hold every FETCH that publisher is asked for (item on several sessions of one sender that keep every other from a publisher).
- **Nothing bounds how many requests of `@xmoq/moqt` wait for a stream at once, nor what is kept for a stream that is being opened.** Each waits 10 seconds at most (row "A request that waits for a stream"), and the caller is what keeps their number down: every request is a call of the application.
- **A write on a stream of `@xmoq/moqt` that could not be opened closes the session, where the failure to open it did not.** The session of the library has forgotten the stream by then in every path it has (a request is cancelled, a Subgroup is told to be not opened), so no such write is made; a caller of the stream layer alone could make one.

## Encodings the draft does not give

- `RENDEZVOUS_TIMEOUT` (`0x04`) and `FILL_TIMEOUT` (`0x0A`): the value is a variable-length integer in milliseconds. The draft (§10.2.5, §10.2.6) gives no encoding. This follows `moqtail` 0.15.0, read in `libs/moqtail-rs/src/model/parameter/message_parameter.rs` at tag `relay@0.15.0` on 2026-10-10 (lines 510–515 build the pair, line 733 writes it; only FORWARD, SUBSCRIBER_PRIORITY and GROUP_ORDER are written as one fixed byte). The basis is source reading only: no captured bytes carry these parameters.

## Other observations about the draft

- The variable-length integer of draft 18 is not the QUIC (RFC 9000) varint: the number of leading one bits gives the length, up to 9 bytes.
- **A browser page that is closed without `close()` ends differently at the relay by browser** (observed, [record of browser support](experiments/2026-10-10-browser-support-webtransport-webcodecs.md)). With Chromium 156 the relay sees the session end first (`ClosedByPeer { code: 0 }`). With the Firefox 157.0 build of Playwright it sees the page's control stream end first, and closes the session itself with `PROTOCOL_VIOLATION` ("the peer closed its control stream"), which is what §3.3 asks for: "A control stream MUST NOT be closed at the underlying transport layer during the session's lifetime. Doing so results in the session being closed as a PROTOCOL_VIOLATION." The subscribers of a track that page published get the same in both cases, PUBLISH_DONE `TRACK_ENDED` with the Stream Count, and the other sessions go on. The relay has a wait of 200 milliseconds for the like case of a STOP_SENDING on its own control stream (row in the relay's table) and none for this one. Nothing was changed.
- The second example in §11.6 does not add up (a 14-byte value under `Length = 21`). It is not used as a test fixture.
- **§10.2.2 has a message rejected with a code that only ends sessions.** "The receiver of a message referencing an Alias that is not currently registered MUST reject the message with UNKNOWN_AUTH_TOKEN_ALIAS" (lines 3163 to 3165 of the text), where the sentences around it have "close the Session with". The code of that name is among the Session Termination Error Codes (§3.5, 0x17; lines 1744 and 6818) and not among the codes of REQUEST_ERROR (§10.6, the table from line 6838), which has UNAUTHORIZED, MALFORMED_AUTH_TOKEN and EXPIRED_AUTH_TOKEN. **XmoQ closes the session with 0x17**: the one code of that name there is, which a peer can read.
- **§12.9 calls malformed what §2.1 and §9.1 allow.** §2.1 has of an Object that is known to exist "From this state, it can transition to not existing, but not vice versa", and §9.1 lists among the fields of a cached Object that can be updated "Object can transition from existing to not existing in cases where the object is no longer available". §12.9 has "A Track is considered malformed ... if ... An endpoint receives an Object with a Prior Object ID Gap covering an Object it previously received", which is such a transition, said with the property. XmoQ follows each where it applies: the gap is malformed, a status in the place of an Object is not (row on an Object that comes again).
- **§2.1 says "not malformed" where §2.4.2 and §12.9 say malformed.** §2.1: "an endpoint can receive an Object after it has already recorded that the Object does not exist (e.g., via a FETCH gap from one source and later delivery via a subscription). This is not a protocol error and the Track is not malformed", with no condition. §2.4.2 has as an example of a malformed track "An Object is received in a Group whose Object ID is larger than the final Object in the Group", and §12.9 "An endpoint receives an Object with an Object ID within a previously communicated gap": both are Objects that come where the endpoint recorded that none exists. Where XmoQ puts the border is in the row on an Object that comes again.
- **Prior Object ID Gap has a type from the range §2.5 leaves to applications.** §2.5 has "Certain Property type ranges are reserved for application-specific use and will never be allocated by IANA in future MOQT specifications: 0x38 to 0x3F (1-byte encoding)", and §12 "Property types in ranges reserved for application-specific use (0x38-0x3F, 0x3800-0x3FFF) are not defined by MOQT". §12.9 defines Prior Object ID Gap with the type 0x3E, and §12.8 Prior Group ID Gap with 0x3C; the table of Properties among the IANA considerations lists both. XmoQ reads 0x3E as §12.9 has it, so an application that uses 0x3E for something of its own makes its track malformed or leaves holes in what the relay's cache answers.
