# MoQ Transport implementation notes

Behaviour that the Rust (`crates/moqt`) and TypeScript (`packages/moqt`) implementations must share, where `draft-ietf-moq-transport-18` is silent, contradicts itself, or leaves a choice. Both implementations follow this table; a change here is made in both in the same pull request.

Items marked **provisional** depend on an [open question](open-questions.md).

| Case | Behaviour | Basis |
|---|---|---|
| Request that the draft defines and XmoQ does not implement, opened by the peer (FETCH, TRACK_STATUS, SUBSCRIBE_NAMESPACE, SUBSCRIBE_TRACKS) | Answer with REQUEST_ERROR `NOT_SUPPORTED` (`0x3`); the session stays open | §10.6.2 provides the code. Closing the session would drop every other track for one unsupported request |
| SUBSCRIBE, PUBLISH or PUBLISH_NAMESPACE opened by the peer, received by an implementation that has no responder side (the clients) | Same answer: REQUEST_ERROR `NOT_SUPPORTED` | A client does not serve requests; the relay will |
| REQUEST_UPDATE for a subscription that the receiver publishes to (the stream of its own established PUBLISH) | Answer the first one with REQUEST_ERROR `NOT_SUPPORTED`, then end the subscription with PUBLISH_DONE `UPDATE_FAILED` (`0x8`). Further REQUEST_UPDATEs that arrive before the subscription has ended get no reply. The session stays open. The parameters of every REQUEST_UPDATE are still checked against §10.2.1 first, and a parameter that is not allowed there is a `PROTOCOL_VIOLATION` | §10.9 requires REQUEST_OK or REQUEST_ERROR in reply, and when the update is unsuccessful the publisher MUST also terminate the subscription with `UPDATE_FAILED`. §10.9.1: when coalesced updates fail, "only a single REQUEST_ERROR will be sent". Updates are not implemented |
| REQUEST_UPDATE on any other request stream of a client | `PROTOCOL_VIOLATION` | §10.9 lets only the sender of a request, or the subscriber of a subscription created by PUBLISH, send it. A client's own SUBSCRIBE or PUBLISH_NAMESPACE stream cannot carry one from the peer |
| Other message or stream type that the draft defines and XmoQ does not implement (`FETCH_HEADER`, GOAWAY and other messages that have no reply) | Close the session with `INTERNAL_ERROR` | There is no per-request answer to give. The peer follows the draft, so it is not a violation |
| An Object after End of Group or End of Track on the same subgroup stream | Malformed Track: the subscription is cancelled and the session stays open. Decided as soon as the first byte of the further Object arrives, without waiting for the whole Object | §2.4.2 lists it as a malformed track. §11.4.3 calls it "a protocol violation" in passing; the list in §2.4.2 is taken as the rule. Waiting would buffer up to the Object size limit for an Object that is discarded anyway |
| One Object with more than one fault | The fault in the earlier field decides, because an Object is judged field by field as it arrives. Object Properties come before Payload Length and Object Status, so an Object whose properties make the track malformed is a Malformed Track even if its status is not Normal (which would be a session-level violation on its own). A fault before the properties (Object ID overflow, a broken key-value encoding, a receive limit) is reported first. An Object after End of Group or End of Track is not decoded at all (row above) | Follows from deciding as early as possible (rows above and below); any other order would need the whole Object buffered |
| Any message that arrives on the request stream of a PUBLISH after the publisher sent PUBLISH_DONE for it, whether the PUBLISH was pending or established | Ignored, until the stream closes | §5.1 allows PUBLISH_DONE in both states, and §10.9 lets the subscriber send REQUEST_UPDATE, so a PUBLISH_OK, a REQUEST_ERROR and several updates can all cross the PUBLISH_DONE |
| SUBSCRIBE_OK that reuses a Track Alias whose previous subscription received PUBLISH_DONE and is still draining | Accepted. The alias now names the new subscription and the old one ends | §11.1 requires `DUPLICATE_TRACK_ALIAS` only when two established subscriptions overlap |
| A subscription ends while subgroup streams for it are open | Send STOP_SENDING on each of them | §10.11 (SHOULD). Otherwise each stream can buffer up to the Object size limit |
| Message type `0x1E` | Treated as defined and not implemented (row above) | Table 5 lists `0x1E` as PUBLISH_OK; §10.5 says PUBLISH is answered with REQUEST_OK (`0x7`). XmoQ follows §10.5, as `moqtail` 0.15.0 does |
| Message or stream type that appears in no table, and the message IDs that Table 5 marks RESERVED (`0x01`, `0x20`, `0x21`, `0x40`, `0x41`, the setup messages of older drafts) | Close the session with `PROTOCOL_VIOLATION` | The draft says to close the session and names no code. A reserved ID is not a message of draft 18 |
| Unknown Setup Option, unknown Property, unknown error code in REQUEST_ERROR, PUBLISH_DONE or a stream reset, unknown auth token type | Never a reason to close the session. An unknown error code is treated as `INTERNAL_ERROR` for that context | §14 (MUST): these registries can grow without negotiation |
| `AUTHORIZATION_TOKEN` | Accepted and carried as opaque bytes; not interpreted | Authentication is undecided. Rejecting the parameter would break peers that send it |
| `FILL_TIMEOUT` or `TRACK_NAMESPACE_PREFIX` in a message that does not allow it | `PROTOCOL_VIOLATION` | §10.2.1 |
| Padding stream (`0x132B3E28`) | Read and discard | §11.5.1 (MUST) |
| After PUBLISH_DONE | The Track Alias stays usable until the number of streams in Stream Count have ended, or the caller reports a timeout. A finished alias is remembered, up to a bound, as "discard" so that a late Object is not resolved to a new track. The timer lives outside the sans-I/O core | §10.11, §11.1 |
| Receive limit exceeded | Control message: close the session with `INTERNAL_ERROR`. Object on a data stream: stop that stream only. The values of the limits are **provisional** | Decided for XmoQ: one oversized Object does not cost the other tracks of the session |
| More than 64 key-value pairs in one list (Setup Options, Message Parameters including repeated `AUTHORIZATION_TOKEN`s, Track Properties, Object Properties) | A receive limit (row above). The number is the same in both implementations, so that neither accepts input the other rejects. Where the list carries a count, the count is checked against the limit as soon as it is read, before any pair is decoded, so a count that is over the limit and also larger than the remaining bytes is reported as the limit. **Provisional** | The draft sets no limit. A pair arrives in 2 bytes and takes far more in memory. Closing for the count is not closing "solely because of an unknown value" (§14) |
| Stream Reset Error Code used with STOP_SENDING or a reset | Malformed Track: `MALFORMED_TRACK` (`0x12`). Receive limit exceeded: `INTERNAL_ERROR` (`0x0`). The subscription ended or was cancelled: `CANCELLED` (`0x1`) | §3.3.3 (SHOULD use a relevant code). `0x12` is described for a relay publisher; it is still the code that tells the sender why |
| A Stream Reset Error Code an application gives when it resets a subgroup stream | TypeScript: a whole number from 0 to 255; anything else is refused before the stream is touched. Rust: any 32-bit code. What either receives is not limited this way | Chromium 156 clamps the code of a `WebTransportError` to 8 bits where the W3C specification has 32, so a larger code would reach the peer as 255 ([record](experiments/2026-10-10-webtransport-error-in-chromium.md)). Every code of §3.3.3 is `0x12` or less |
| Unidirectional streams of the peer read at once | 64 in both implementations, the peer's control stream among them. Further streams are left with the transport, where flow control holds the peer back. What is bounded is the number of streams, not Objects or bytes: a stream hands over what it has read before it waits for the application. **Provisional** | The draft sets no limit. Without one, a queue grows with the number of streams ([record](experiments/2026-10-10-subscription-backlog-in-chromium.md)). What the limit costs is in the known gaps, under connection flow control |
| The code and reason an application closes a session with | The code is a whole number from 0 to 2^32 - 1 in both implementations; TypeScript refuses anything else before it touches the session. The reason is cut to at most 1024 bytes of UTF-8 between two characters before it is handed to the transport, and what an endpoint reports about a close it asked for is the cut reason. One exception in TypeScript: when the session closes because of an error in this endpoint, `closed` carries that error as it was and the peer gets its message, cut. The cut is pinned by [`fixtures/webtransport-close/`](../fixtures/webtransport-close/README.md), rows of what Chromium sent; the TypeScript tests and the Rust test read them. The Rust test checks the 12 rows whose reason is text; the 2 rows with half of a surrogate pair cannot be put into a Rust string and are only read for their form | `draft-ietf-webtrans-http3-16` §6 for the 1024 bytes. Chromium 156 wraps a code outside 32 bits (2^32 arrives as 0, -1 as 2^32 - 1) and resolves `closed` with the reason as it was given, so both are settled before the browser is asked ([record](experiments/2026-10-10-webtransport-close-info-in-chromium.md)). The Session Termination Error Codes of the draft are integers of up to 62 bits; the named ones are `0x1A` or less |
| Object Properties that make the track malformed (a Mandatory Track Property on an Object, a broken Prior Group ID Gap or Prior Object ID Gap) | Decided when the properties have been read, before the payload arrives | Same reason as the End of Group row: the payload of a rejected Object is not buffered. Otherwise a stream that ends inside the payload gives a different result in each implementation |
| SUBSCRIBE_OK that reuses the Track Alias of a draining subscription and is itself refused (it carries a Mandatory Track Property the receiver does not support) | The draining subscription is left as it is. The refused one never takes the alias | A subscription that was never established cannot end another one |
| Remembered Track Aliases of ended subscriptions; stream closes counted before SUBSCRIBE_OK | At most 64 of each; the oldest is dropped. **Provisional** | Same number in both implementations |
| A Mandatory Track Property error and a duplicate Track Alias in the same message | The session-closing error (`DUPLICATE_TRACK_ALIAS`) wins | §11.1 |
| The peer sends STOP_SENDING on a request stream that this endpoint opened | On the stream of an established PUBLISH: the subscription ends and its open subgroup streams are reset. On the stream of a request that is still pending: nothing changes yet; the request ends when the peer's own direction of the stream is reset or carries a reply. On the stream of an Established SUBSCRIBE: nothing changes either, since the SUBSCRIBE_OK was read and what follows (PUBLISH_DONE, Objects) travels the other way; this holds for the relay's own SUBSCRIBE to a publisher as well. On the stream of a SUBSCRIBE that already received PUBLISH_DONE: nothing changes, the subscription keeps draining so that late Objects still arrive. On the stream of a PUBLISH for which this endpoint has sent PUBLISH_DONE: nothing changes. This endpoint has finished its direction, so there is nothing left to stop, and it goes on waiting for the subscriber to end its own direction (the row on a publisher that ended its PUBLISH). On a control stream: `PROTOCOL_VIOLATION` | §5.1 and §5.1.1 make STOP_SENDING the subscriber's way to end an established subscription created by PUBLISH. §3.3.2: a receiver that cancels a request terminates every direction that is still open, so the reset of its own direction follows, and acting on STOP_SENDING alone could drop a REQUEST_ERROR that is already in flight. §10.11 lets Objects arrive after PUBLISH_DONE. §5.1 lets the subscriber end a subscription with STOP_SENDING in the Pending and Established states, and PUBLISH_DONE has moved it to Terminated, so a STOP_SENDING after this endpoint's own PUBLISH_DONE has nothing to end; the Rust client reads only the receiving half of the stream while it waits, and `@xmoq/moqt` has a test for it. §3.3 forbids closing a control stream |
| The peer resets its direction of a request stream that this endpoint opened | A pending request ends as cancelled by the peer. An established subscription ends. A SUBSCRIBE that already received PUBLISH_DONE keeps draining. A PUBLISH for which this endpoint already sent PUBLISH_DONE is over either way; the reset changes nothing, and both clients report it as how the peer ended the stream (row on closing after PUBLISH_DONE below) | §3.3.2, §10.11 |
| A requester finishes its direction of a request stream and does nothing else (no reset, no STOP_SENDING) | Not a cancellation, in every role. A SUBSCRIBE stays Established and Objects go on; a PUBLISH_NAMESPACE stays announced; and on the stream of an Established PUBLISH, where the subscriber is the one that finishes, the subscription goes on as well. The request ends by STOP_SENDING, by a reset, or with the session. Two cases are endings and stay so: a publisher that finishes the stream of its PUBLISH without PUBLISH_DONE has ended the track, because PUBLISH_DONE travels on that direction and can no longer come; and a responder that finishes its direction without having answered, or a publisher that finishes the stream of a SUBSCRIBE without PUBLISH_DONE, has ended the request. The FIN of a subscriber *after* this endpoint's PUBLISH_DONE is the answer described in the row on closing after PUBLISH_DONE | §5.1: "The subscriber terminates a subscription ... by sending STOP_SENDING"; §3.3.2 cancels by "resetting or sending STOP_SENDING"; §6.2 withdraws a PUBLISH_NAMESPACE "by cancelling the request". §6.1 names a FIN as a cancellation for SUBSCRIBE_NAMESPACE and SUBSCRIBE_TRACKS only. §11.4.1: "Termination of a bidi request stream terminates the Subscription, Fetch, Track Status, Publish Namespace, or Subscribe Namespace request"; a FIN of one direction leaves the other open, so the bidirectional stream is not terminated by it. A requester that finishes its direction can send no REQUEST_UPDATE any more and has asked for nothing. The `moqtail` clients unsubscribe with a reset and STOP_SENDING, not a FIN (read in `moqtail` npm 0.13.0, `unsubscribe`) |
| Request ID parity; Redirect in REQUEST_ERROR | Both are checked | §10.1, §10.6.1 |
| Request IDs from the peer that arrive out of order or leave gaps | Never a reason to close the session. Seen IDs are remembered to detect a duplicate; when more than 1024 IDs are remembered above the lowest one not seen yet, each new ID pushes out the lowest remembered one, so a duplicate of that ID is no longer detected. One exception, in Rust only: an ID whose request is still open is a duplicate even after it was pushed out (TypeScript keeps no requests of the peer, so the case does not arise there). A REQUEST_UPDATE consumes a Request ID even when the message itself is ignored: one that crosses this endpoint's PUBLISH_DONE, and one that follows an update that was refused. An update that is itself a protocol violation, as one for a PUBLISH that is still Pending, closes the session for that, and its Request ID is not looked at. Covered by tests of the two session states; neither client was run against a peer that sends REQUEST_UPDATE, and the places where the Rust client hands what arrives late to its session have no test (it has no peer to run against in a test) | §10.1 asks the receiver to check parity and duplicates only. Forgetting gaps instead ("everything below is seen") would turn a late, valid request into a duplicate and close the session |
| More subgroup streams arrive for a subscription than the Stream Count of its PUBLISH_DONE | Not checked. The streams are handled like the others, and the session stays open | §10.11 gives the count so that the subscriber knows when everything arrived. Closing for a wrong count is not asked for, and a publisher that cannot count sends 2^62 - 1 |
| A stream error code received from WebTransport that is outside the range of `draft-ietf-webtrans-http3-16` §4.4 | Reported as a reset or stop without a code, which is then handled like `INTERNAL_ERROR` (unknown-code row above). Every code a `wtransport` 0.7.2 peer sends is one, the `moqtail` relay and clients among them: they put the code on the wire unmapped. In Rust the mapping in both directions is done by `web-transport-quinn`; XmoQ keeps none of its own. A code on a reserved codepoint inside the range is not caught: see the known gaps | §4.4: such a code SHOULD be delivered "as a stream reset with no application error code" |
| A session a peer closes without a CLOSE_WEBTRANSPORT_SESSION capsule, with an application code on the QUIC connection | In Rust, read as the Session Termination Error Code and reason of that close, when the code is below `0x100`. From `0x100` on the codes are those of HTTP/3 and QPACK (RFC 9114 §8.1, RFC 9204 §6), which an HTTP/3 stack sends for itself; such a close is a lost connection | A `wtransport` 0.7.2 peer closes this way and cannot send the capsule. Not in a draft; without it every session a `moqtail` peer ends would show as a lost connection |
| A publisher that ended its PUBLISH with PUBLISH_DONE and wants to close the session | After PUBLISH_DONE and its FIN, the publisher waits up to 3 seconds for the subscriber to end its direction of the request stream, and only then closes the session. The relay, as the subscriber, ends that direction with a FIN once as many subgroup streams as the Stream Count named have ended there, and resets it (`CANCELLED`) when its wait for them ran out. From an XmoQ relay, a FIN tells the publisher that nothing it sent is still under way, and a reset or nothing in time that this is not known. A stream the relay stopped itself, as one for a Subgroup it took from another source of the track, counts among those that ended, so a publisher all of whose streams were stopped gets the FIN as well: the FIN says that the relay waits for nothing more of this publisher, and not that what it sent reached a subscriber. Neither client can tell what kind of peer it has, so each reports only what it saw and treats none of it as an error. The Rust client prints `PUBLISH_DONE_PEER_ENDED how=FIN`, a reset with its code, or `nothing in time`, and closes in every case. In `@xmoq/moqt`, `PublishedTrack.done()` resolves with `fin`, `reset` and its code, or `nothing-in-time`, and the application closes the session after it. A subscriber that had finished its direction before PUBLISH_DONE is not waited for: both report a FIN at once, and that FIN says nothing about the counted streams, also from an XmoQ relay (which does not finish before PUBLISH_DONE). A reset is reported with its code, or without one where the transport gave none. While they wait, both decode what the subscriber still sends on the stream and ignore it; bytes that do not decode close the session with the code of that error. The Request ID of a REQUEST_UPDATE among it is checked by both (row on Request IDs from the peer, above), each against the IDs it has seen: `@xmoq/moqt` has seen those of every request the peer opened, the Rust client only those of requests that went through its session, which in its publish and subscribe modes is none (a known gap, below). Both stop the subscriber's direction (`CANCELLED`) when the wait is over, and read nothing more of the stream. The wait is counted from the FIN in the Rust client, and in `@xmoq/moqt` from the moment the transport has taken PUBLISH_DONE and the FIN, so a subscriber that does not read can hold `done()` up for longer. After the PUBLISH_DONE `UPDATE_FAILED` that answers a refused REQUEST_UPDATE, both wait and stop the direction in the same way; in `@xmoq/moqt` nobody is told how it ended, as the application did not call `done()`. The Rust client waits in the same way after it served a peer's SUBSCRIBE, which `@xmoq/moqt` does not do. What the relay does with a publisher's STOP_SENDING that arrives while it still waits for the counted streams was not looked at; by the limits below it has ended its direction a second before. Where the session ends during the wait, `done()` resolves with `session-closed`, and the Rust client's run ends with the error of the lost connection (as read in `finish_and_await_close`, `crates/moqt-client/src/io.rs`; not run). The wait is 3 seconds in both; `@xmoq/moqt` takes another value as `peerStreamEndTimeoutMs`, from 0 to 2^31 - 1 milliseconds. With 0 it does not wait: it still stops the subscriber's direction, so that the stream is not left open, and a session closed right after can lose what was sent last. The Rust client has no such setting | §10.11 and §5.1.1 say when the publisher sends PUBLISH_DONE and FIN, and give the subscriber's direction no meaning afterwards and no time to close it; §3.3.2 makes a reset of an open direction a cancellation. So a FIN there is XmoQ's convention, and a peer that knows nothing of it sees an ordinary end. It is needed because a transport can lose a stream that arrived and was not accepted when the connection closes (`web-transport-quinn` 0.13.2 does). The `moqtail` relay 0.15.0 also finishes the stream after PUBLISH_DONE (seen in the interop logs); what it means by that was not looked at |
| Track Namespace and Track Name in message types | The names an API user sees are `track_namespace` and `track_name` (camelCase in TypeScript), as in the draft's message definitions. How a message stores them is each implementation's choice: Rust keeps one validated full-track-name value, TypeScript keeps two fields | §2.4.1 and each message's definition. What must match between the implementations is the vocabulary, not the representation |

## Known gaps against the draft

These are requirements of draft 18 that the implementations do not meet yet. Each has a `FIXME:` at the place in the code where it belongs.

- **Authorization token structure (§10.2.2).** The token is carried as opaque bytes, so the alias types (REGISTER, USE_ALIAS, DELETE) and the rules for them in SETUP are not enforced. Left until authentication is decided.
- **Datagrams (§11).** Neither implementation reads datagrams, so an OBJECT_DATAGRAM is dropped without notice and the rule "an endpoint that receives an unknown datagram type MUST close the session" is not met. Datagram delivery is outside the Phase 0b scope.
- **Connection flow control for control streams first (§11.4.2, MUST: "endpoints MUST allocate connection flow control to the control streams before allocating it to any data streams").** Not met by any of the three implementations. As receivers: the relay bounds the connection's receive window (4 MiB), and subgroup streams whose readers are held back can take all of it, so the request streams of that session wait too; the clients leave the window at their stack's default. As senders, if the sentence means them as well (it goes on: "while the sender waits for flow control to send the message"): which stream uses the connection's credit is the QUIC stack's choice, and neither Rust nor TypeScript sets a stream priority or send order. The deadlock the draft names does not arise at the relay, because a stream with an unknown Track Alias is read and held within limits and not left unread. **A deadlock of the same kind was seen in the browser client**, for request streams where the draft speaks of control messages: the client reads 64 unidirectional streams of the peer at once and leaves the rest with the browser. With a subscription the page did not read and one Object of 100,000 bytes a stream, the relay's PUBLISH_DONE for it did not reach the page, and after the relay had ended that subscription its SUBSCRIBE_OK for another track of the same session did not arrive either (3 of 3), until the page read again. With 57-byte Objects and with 30 Objects a stream both arrived, and without the limit the second request was answered while the page held everything that was sent ([record](experiments/2026-10-10-subscription-backlog-in-chromium.md)). The likely cause, not verified with a capture, is that the streams the page has not taken hold the connection's credit. An application that reads, however slowly, frees it; one that never reads can stall its own session. Whether the client should end such a subscription itself is in [open questions](open-questions.md).
- **Stream error codes on reserved codepoints (`draft-ietf-webtrans-http3-16` §4.4, §9.5), in Rust.** The WebTransport range has codepoints of the form `0x1f * N + 0x21` that are not WebTransport codes. `web-transport-proto` 0.6.2 checks the range only, so a reset with `0x52e4a40fa8f9` is reported with the code `0x1e` where it should be a reset without a code. XmoQ gets the decoded value and cannot tell. The same goes for the code of a STOP_SENDING, which the relay and the Rust client print. A peer that maps its codes as §4.4 says never sends such a codepoint.
- **The code of a STOP_SENDING sent from a browser on a subgroup stream was not observed.** On a request stream it was: when an own-browser subscriber cancelled, the relay printed the code `0x1` that `@xmoq/moqt` puts into the `WebTransportError`, in 53 of 60 rounds; in the other 7 the relay saw the reset of the other direction first, and it prints the line only when the STOP_SENDING comes first. On a subgroup stream the relay notices a STOP_SENDING when it next writes to the stream, and no interop run has a subscriber stop a stream the relay is still writing ([record](experiments/2026-10-10-disconnects-through-own-relay.md)).
- **`PublishedTrack.ended` after a PUBLISH_DONE that could not be written, in `@xmoq/moqt`.** Not a requirement of the draft: `done()` rejects with the error of the write, and `ended` resolves only when the session ends, although the session state has ended the subscription.
- **Request IDs of requests the peer opens, in the publish and subscribe modes of the Rust client.** There the client answers every such request with `NOT_SUPPORTED` without its session, and does not check its Request ID (§10.1, `INVALID_REQUEST_ID`). The IDs are not remembered either, so a REQUEST_UPDATE that uses the Request ID of such a request again is not taken for a duplicate, where `@xmoq/moqt` closes the session. The mode that serves a SUBSCRIBE goes through the session, and so does the relay.
- **A SUBSCRIBE for a track a client has sent PUBLISH for (§5.1), in both clients.** "If a publisher receives a SUBSCRIBE request for a Track with an existing subscription in Pending (publisher) state, it MUST fail that request with a DUPLICATE_SUBSCRIPTION error." The TypeScript client, and the Rust client in the mode that sends PUBLISH, answer `NOT_SUPPORTED`, as to every request a peer opens. The relay waits for the PUBLISH after `DUPLICATE_SUBSCRIPTION` and not after `NOT_SUPPORTED`, so with an own client as the publisher, a subscriber whose SUBSCRIBE crossed the PUBLISH gets `DOES_NOT_EXIST` when the client's answer is read before its PUBLISH. The track is there a moment later.
- **`DUPLICATE_SUBSCRIPTION` from a publisher that sends no PUBLISH (§5.1, §10.6.2), in the relay.** The code is also the answer when the publisher still holds a subscription in the same role ("If an endpoint receives a message attempting to establish a second subscription to a Track with the same role, it MUST fail that request with a DUPLICATE_SUBSCRIPTION error"): for instance one the relay cancelled a moment ago and the publisher has not let go of yet. The relay cannot tell this from an announced PUBLISH and waits; up to 64 subscribers then get `TIMEOUT` after 5 seconds, where asking the publisher again would have got them the track. Asking again is left out because §10.6.2 ties it to the publisher's Retry Interval ("If the value is 0, the request SHOULD NOT be retried"), and the own session always sends 0 (the gap on Retry Interval below).
- **A responder's FIN after its REQUEST_OK to PUBLISH_NAMESPACE: the two clients differ.** The TypeScript client ends the request (`peer-fin`); the Rust client does not read the stream of its PUBLISH_NAMESPACE after the answer and goes on as if announced. Which of the two is right is not decided; the row on a requester's FIN covers the other direction only. The own relay never finishes that stream this way.

The relay (`crates/relay-core`, `crates/relay`) adds these:

- **Several publishers of one track (§9.3, §9.5). The MUSTs are met in part.** §9.5: "Relays MUST send SUBSCRIBE messages to all matching publishers. This includes matching both Established subscriptions on the Full Track Name and Namespace Prefix Matching against published Namespaces." §9.3: "Relays MUST handle Objects for the same Track from multiple publishers and forward them to matching Established subscriptions." §9.5: "When a relay receives an authorized PUBLISH_NAMESPACE for a namespace that matches one or more existing subscriptions to other upstream sessions, it MUST send a SUBSCRIBE to the publisher that sent the PUBLISH_NAMESPACE for each matching subscription." §9.5: "When it receives an authorized PUBLISH message for a Track that has Established downstream subscriptions, it MUST respond with PUBLISH_OK." Against that stands §9.3: "An implementation can use mechanisms such as REQUEST_ERROR or unsubscribing (see Section 3.3.2) if it cannot accept an additional publisher due to implementation constraints." §9.5 again: "Relays MUST forward PUBLISH_NAMESPACE or PUBLISH messages to all matching subscribers", which is empty here because the relay refuses SUBSCRIBE_NAMESPACE. What is done: a PUBLISH for a track that has a source is accepted, up to 4 sources a track, and each Subgroup is taken from the source that sends it first (rows below). What is not: a SUBSCRIBE is routed to the publisher whose matching namespace was announced first, and to no other; a PUBLISH_NAMESPACE that comes later changes nothing for tracks that already have a source; and a PUBLISH is still refused with `UNINTERESTED` in three cases. For a track whose sources have all said PUBLISH_DONE and whose last streams are awaited: its downstream subscriptions are still Established, so this is the case of §9.5's "MUST respond with PUBLISH_OK". For a track that has other sources, from a publisher that said PUBLISH_DONE for it and whose last streams the relay still awaits: the same MUST, and the publisher's earlier subscription is Terminated for it (§5.1), so it does nothing wrong by publishing anew. And for a track the relay has asked another publisher for and has no answer about: there the downstream subscriptions are Pending, and the sentence of §9.5 does not apply; what is not met is that the track could have had a source at once. The [roadmap](roadmap.md), Phase 0b, has the item.
- **Sources of a track that do not send the same thing (§9.1, §2.4.2, §9.3).** §9.1: "An endpoint that receives a duplicate Object with a different Forwarding Preference, Subgroup ID, Priority or Payload MUST treat the track as Malformed." §2.4.2, the sixth example of a malformed track: "The same Object is received more than once with different Payload or other immutable properties." §9.3: "The Relay SHOULD attempt to deduplicate Objects before forwarding, subject to implementation constraints." Nothing compares what two sources of a track send, so the MUST is not met, and the relay removes duplicates by Subgroup and not by Object. A Subgroup is taken from whichever source sends it first, whole, and the other source's stream for it is stopped unread; a source whose Groups are numbered differently from another's is passed on next to it as if the Groups were different ones while the numbers are less than 8 apart, and has all its streams stopped when its numbers are the smaller ones by 8 or more (row on how long the relay remembers). Runs with two publishers were done with publishers that send the same Object under the same Group ID only.
- **A PUBLISH that uses a Track Alias again while the subscription that had it drains (§10.11).** A publisher says PUBLISH_DONE, the relay waits for the streams it counted, and the publisher sends PUBLISH for the same track under the same Track Alias. The relay refuses it (row on a PUBLISH for a track that has a source), and with that the wait is cut short: the session state takes the alias for the new PUBLISH when it arrives and gives it up when the PUBLISH is refused, so the relay no longer waits for the streams the first subscription counted: when the next stream of it ends, the first PUBLISH stream gets its FIN although fewer streams ended than were counted, and the timer for them does nothing (seen in a test of the core: 2 counted, 1 ended). So "accepted once that wait is over" does not hold for a PUBLISH under the same alias: it ends the wait. This is so for a track with one source as well, and was before several sources were taken.
- **Objects past the end of a Subgroup, and a Subgroup on two streams that both end with a FIN with different last Objects (§2.4.2, the second and third example of a malformed track).** Not detected. A second stream for a Subgroup that ended with a FIN is stopped unread, when it opens or, where its header leaves the Subgroup ID to the first Object, when that Object comes; a stream that another took the place of is stopped unread as well. Nothing of either reaches the subscribers.
- **A second stream for a Subgroup the relay has forgotten (§2.2).** It passes, so the subscribers can get a Subgroup on two streams of which neither was reset, which §2.2 has as MUST NOT. The relay forgets a Subgroup when its Group is 8 or more behind the newest, and when the track has more than 256 Subgroups in those Groups: then the smallest Subgroup IDs of the oldest Group go, also ones whose stream is still open, and a second stream for one of those is opened downstream next to the first, which is not reset. That takes more than 32 Subgroups a Group on average over 8 Groups, or more than 256 in one; a publisher that sends every Object as a Subgroup of its own gets there. With one source per track it takes a publisher that sends a Subgroup twice. Once a track has had several sources, a stream of a Group that is 8 or more behind the newest is stopped and not passed on (row on how long the relay remembers), so a source that is merely behind another does not cause it, whether the other is still there or not; what is left is the limit of 256.
- **Which of two open streams for a Subgroup the source goes on with (§11.4).** The relay keeps the one whose header it read later (row on a second stream, below). It knows the order in which the headers were read and not the QUIC stream IDs. When a source resets a stream and sends the Subgroup again, and the header of the first stream is read after that of the second, the relay stops the second and keeps the first, which ends with the reset; §11.4.3 has "A publisher that receives a STOP_SENDING on a Subgroup stream SHOULD NOT attempt to open a new stream to deliver additional Objects in that Subgroup", so the Subgroup is lost for every subscriber. No subscriber gets a wrong Object. Whether this happens with real peers was not looked at.
- **A new stream for a Subgroup to a subscriber whose stream for it is closed (§11.4.3).** When a stream the relay opened to a subscriber is reported closed while the source's stream goes on, the next Object opens another stream to that subscriber for the same Subgroup. The I/O side reports a stream closed also when the subscriber stopped it, and for that case §11.4.3 has "SHOULD NOT attempt to open a new stream to deliver additional Objects in that Subgroup". The core is not told why a stream closed. A test of the core pins what it does; the case was not run with a peer that sends STOP_SENDING.
- **Subscription Filter (§5.1.2).** Every subscriber gets what arrives after it subscribed, whatever its filter says.
- **NEW_GROUP_REQUEST (§10.2.13).** A relay MUST pass it on to the publisher; it is ignored.
- **Delivery timeouts (§8, §10.2.3, §10.2.4).** `OBJECT_DELIVERY_TIMEOUT` and `SUBGROUP_DELIVERY_TIMEOUT` are ignored, as parameters and as Track Properties.
- **RENDEZVOUS_TIMEOUT (§10.2.6).** A SUBSCRIBE that carries it is rejected at once with `DOES_NOT_EXIST` when the track has no publisher and no publisher announced a matching namespace, where the relay SHOULD wait. Without the parameter, or with 0, the immediate `DOES_NOT_EXIST` is what the section requires.
- **Retry Interval (§10.6.2).** 0 in every REQUEST_ERROR an implementation makes up itself, which reads as "do not retry", also where a retry could succeed later: so for the `EXCESSIVE_LOAD` and the `UNINTERESTED` a publisher gets for a PUBLISH the relay would take once a source of the track is gone or has drained. The one exception is the relay passing on a publisher's REQUEST_ERROR, which keeps the publisher's Retry Interval unless it replaces the Error Code with `INTERNAL_ERROR` (row on the publisher's answer and the table of codes, below). The relay does not honour a Retry Interval either: a track that a publisher refused with Retry Interval 0 ("If the value is 0, the request SHOULD NOT be retried") is asked for again at once when the next subscriber wants it, and one refused with a wait is asked for again before the wait is over. The SHOULD NOT that keeps the relay from asking again after `DUPLICATE_SUBSCRIPTION` applies here as well; the relay keeps no memory of refusals.
- **REQUEST_UPDATE** is refused, never applied, so the Forward State of a subscription cannot change.
- **Messages the relay does not implement (§4, MUST: "Relays MUST implement all MOQT messages defined in this document, as well as processing rules described in Section 9").** FETCH, TRACK_STATUS, SUBSCRIBE_NAMESPACE, SUBSCRIBE_TRACKS, REQUEST_UPDATE, GOAWAY and datagrams are refused or not read, as the rows at the top say. What each waits for is in [open questions](open-questions.md).
- **Authorization (§9.4, §9.5).** Not done; there is no authentication yet. A publisher's `UNAUTHORIZED`, `MALFORMED_AUTH_TOKEN` or `EXPIRED_AUTH_TOKEN` to the relay's SUBSCRIBE reaches the subscribers as it is, although it is about a token the subscriber did not send there and cannot mend. The relay copies nothing of a subscriber's SUBSCRIBE into the SUBSCRIBE it sends a publisher, so a publisher behind the relay does not see a subscriber's AUTHORIZATION_TOKEN. Any session can announce any namespace, the one with no fields included (§2.4.1 allows "between 0 and 32 Track Namespace Fields"), which matches every track: whoever announces it first gets the SUBSCRIBE for every track that nobody has published. With several sources of a track, any session can also become a source of any track that has one, by sending PUBLISH for it, and then: end the track for every subscriber by sending something that breaks the object model (§2.4.2 has the relay end the subscriptions with `MALFORMED_TRACK`, and the other sources are cancelled with it); take a Subgroup from the other sources by sending it first; keep the other sources from being heard, by sending one stream with a Group ID far ahead of theirs, after which their Groups count as too old and their streams are stopped; make the relay forget which stream it took a Subgroup from, by sending more Subgroups than it remembers, after which the same Subgroup can reach the subscribers on two streams (§2.2); raise the largest Location of the track, with the LARGEST_OBJECT parameter of its PUBLISH or with an Object on a stream that is passed on, so that a subscriber that comes gets a LARGEST_OBJECT the other publishers never sent; and send so many streams that a subscriber runs into the limit of what waits to be written and loses its subscription. The newest Group of a track is kept for the track and not for each source, on purpose: a share for each source needs to know who a source is.

| A subscriber that does not close its direction of the request stream after the relay's PUBLISH_DONE | After a wait, the relay sends STOP_SENDING (`CANCELLED`) and forgets the request | §10.11 and §5.1.1 do not make the subscriber close the stream, and until it does the request counts against the limit of open ones |
| A publisher whose connection goes | What had arrived on streams the relay already accepted is read first, for a limited time, and only then is the session treated as closed. Subgroup streams the publisher had finished are delivered whole to the subscribers; only the ones cut short are reset, with `CANCELLED`, whether the relay sees the end of the stream or the end of the session first. A stream the relay had not accepted yet can be lost (row on PUBLISH_DONE above) | Which bytes a transport still hands over after a close is pinned by the tests in `crates/moqt-io/src/contract.rs` |

## Encodings the draft does not give

- `RENDEZVOUS_TIMEOUT` (`0x04`) and `FILL_TIMEOUT` (`0x0A`): the value is a variable-length integer in milliseconds. The draft (§10.2.5, §10.2.6) gives no encoding. This follows `moqtail` 0.15.0, read in `libs/moqtail-rs/src/model/parameter/message_parameter.rs` at tag `relay@0.15.0` on 2026-10-10 (lines 510–515 build the pair, line 733 writes it; only FORWARD, SUBSCRIBER_PRIORITY and GROUP_ORDER are written as one fixed byte). The basis is source reading only: no captured bytes carry these parameters.

## Other observations about the draft

- The variable-length integer of draft 18 is not the QUIC (RFC 9000) varint: the number of leading one bits gives the length, up to 9 bytes.
- **A browser page that is closed without `close()` ends differently at the relay by browser** (observed, [record of browser support](experiments/2026-10-10-browser-support-webtransport-webcodecs.md)). With Chromium 156 the relay sees the session end first (`ClosedByPeer { code: 0 }`). With the Firefox 157.0 build of Playwright it sees the page's control stream end first, and closes the session itself with `PROTOCOL_VIOLATION` ("the peer closed its control stream"), which is what §3.3 asks for: "A control stream MUST NOT be closed at the underlying transport layer during the session's lifetime. Doing so results in the session being closed as a PROTOCOL_VIOLATION." The subscribers of a track that page published get the same in both cases, PUBLISH_DONE `TRACK_ENDED` with the Stream Count, and the other sessions go on. The relay has a wait of 200 milliseconds for the like case of a STOP_SENDING on its own control stream (row in the relay's table) and none for this one. Nothing was changed.
- The second example in §11.6 does not add up (a 14-byte value under `Length = 21`). It is not used as a test fixture.
- `moqtail` 0.15.0 clients omit `MOQT_IMPLEMENTATION` in SETUP (§10.3.1.5 is a SHOULD); its relay sends it. The relay's control-message log prints the raw bytes received and sent, checked in `libs/moqtail-rs/src/transport/control_stream_handler.rs` at tag `relay@0.15.0` on 2026-10-10.
- moqtail-ts 0.13.0 answers a SUBSCRIBE with a SUBSCRIBE_OK that repeats the parameters of the SUBSCRIBE (`handlerSubscribe`, read in `dist/client-BzncAN14.mjs` of the npm package `moqtail` 0.13.0 on 2026-10-10: `const parameters = [...msg.parameters]`). A SUBSCRIBE with FORWARD therefore gets a SUBSCRIBE_OK with FORWARD, which §10.2.12 does not list for SUBSCRIBE_OK, and §10.2.1 has the receiver close the session ("If it appears in some other type of message, the receiving endpoint MUST close the connection with a PROTOCOL_VIOLATION"). The own relay closed the session of a moqtail-ts publisher for this while its SUBSCRIBE carried FORWARD ([the routing record](experiments/2026-10-10-relay-namespace-routing.md), run 10). XmoQ keeps the check; the relay's SUBSCRIBE no longer carries the parameter (row on the relay's SUBSCRIBE), and with that the same run passes ([record](experiments/2026-10-10-routing-follow-ups.md)).
