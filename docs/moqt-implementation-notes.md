# MoQ Transport implementation notes

Behaviour that the Rust (`crates/moqt`) and TypeScript (`packages/moqt`) implementations must share, where `draft-ietf-moq-transport-18` is silent, contradicts itself, or leaves a choice. Both implementations follow this table; a change here is made in both in the same pull request.

Items marked **provisional** depend on an [open question](open-questions.md).

| Case | Behaviour | Basis |
|---|---|---|
| Request that the draft defines and XmoQ does not implement, opened by the peer (FETCH, SUBSCRIBE_NAMESPACE, SUBSCRIBE_TRACKS) | Answer with REQUEST_ERROR `NOT_SUPPORTED` (`0x3`); the session stays open. SUBSCRIBE_NAMESPACE is decoded whole in both before it is refused so by the clients, and one whose prefix has more than 32 fields (§10.18) or a parameter other than AUTHORIZATION_TOKEN (§10.2.1) closes the session with `PROTOCOL_VIOLATION`; the relay serves it (row on SUBSCRIBE_NAMESPACE in the relay's table) | §10.6.2 provides the code. Closing the session would drop every other track for one unsupported request. A FETCH is decoded whole before it is refused, in both implementations, so one that is malformed (a Fetch Type other than 1, 2 and 3, a parameter §10.2 does not list for FETCH) closes the session with `PROTOCOL_VIOLATION` (§10.12, §10.2.1); of the other three only the Request ID is read. The Rust session now hands a FETCH to its caller (rows on FETCH below); the relay serves a FETCH (rows in the relay's table), and the Rust client refuses every FETCH with `NOT_SUPPORTED`, until it serves one. `@xmoq/moqt` hands a Standalone FETCH to its application where the application asked for that (`serve({ fetch })`), and refuses one with `NOT_SUPPORTED` where it did not. It serves no Joining FETCH: one that names a SUBSCRIBE of the peer that waits for its answer or was accepted is refused with `NOT_SUPPORTED`, and so is one that names a Request ID of the peer that is yet to come; one that names neither is refused with `INVALID_JOINING_REQUEST_ID` (row below, and `fixtures/joining-request-id/`). The Rust session hands the first two kinds to its caller, and the Rust client refuses them with the same code. `fixtures/peer-fetch/opened.tsv` has the FETCHes both implementations read, each with what comes of it. Between a REQUEST_UPDATE that was refused and the PUBLISH_DONE that follows, the Rust session still takes the SUBSCRIBE as open; `@xmoq/moqt` sends both at once, and a Joining FETCH behind them gets `INVALID_JOINING_REQUEST_ID`. |
| TRACK_STATUS (§10.14), in both sessions | Decoded as a SUBSCRIBE is, and a request of its own: **AUTHORIZATION_TOKEN is the one parameter it may carry**, and its REQUEST_OK (TRACK_STATUS_OK) `LARGEST_OBJECT` alone, with Track Properties; any other parameter closes the session with `PROTOCOL_VIOLATION`, as §10.2.1 has. Answered once, with REQUEST_OK or REQUEST_ERROR, after which the responder finishes the stream. A REQUEST_UPDATE on its stream closes the session with `PROTOCOL_VIOLATION`. The two clients refuse a TRACK_STATUS of the peer with `NOT_SUPPORTED` (decided on 2026-10-24: they are not relays); the relay answers it (row on TRACK_STATUS in the relay's table). The fixed bytes are moqtail's (`fixtures/moqt-18/`, capture P) | §10.14: "The TRACK_STATUS message format is identical to the SUBSCRIBE message (Section 10.7), but subscriber parameters related to Track delivery (e.g. SUBSCRIBER_PRIORITY) are not included"; "If successful, the publisher responds with a TRACK_STATUS_OK with the same parameters and Track Properties it would have set in a SUBSCRIBE_OK. Track Alias is not used"; "The bidi stream is closed with a FIN after TRACK_STATUS_OK or REQUEST_ERROR are sent"; "the subscriber cannot send REQUEST_UPDATE". §10.2.2 names TRACK_STATUS for AUTHORIZATION_TOKEN, §10.2.11 TRACK_STATUS_OK for LARGEST_OBJECT, and no other parameter of §10.2 names either; §10.2.6 has RENDEZVOUS_TIMEOUT "in a SUBSCRIBE message" alone, so a TRACK_STATUS cannot ask to be held for a publisher. **The draft is silent** on what follows from a REQUEST_UPDATE that "cannot" be sent: the session is closed, as for any message a request of its kind does not take. `moqtail` 0.15.0 answers `LARGEST_OBJECT` {0, 0} for a track it has before any Object came, and puts no Track Properties in TRACK_STATUS_OK (capture P) |
| SUBSCRIBE, PUBLISH or PUBLISH_NAMESPACE opened by the peer, received by an implementation that has no responder side (the clients) | Same answer: REQUEST_ERROR `NOT_SUPPORTED`. **A SUBSCRIBE is the exception in both clients.** The Rust client answers one for a track it announced. `@xmoq/moqt` hands one to the application once the application has said how it serves requests (`MoqtConnection.serve`), and refuses it with `NOT_SUPPORTED` until then; a SUBSCRIBE for a track this endpoint sent PUBLISH for gets `DUPLICATE_SUBSCRIPTION` either way (row below). A SUBSCRIBE is decoded whole before it is refused, so one that does not decode closes the session with `PROTOCOL_VIOLATION`, with or without `serve` | A client that does not serve a kind of request says so; the relay serves them |
| REQUEST_UPDATE for an Established subscription that the receiver publishes to (on the stream of the peer's SUBSCRIBE, or of its own PUBLISH) | **With no parameter but delivery timeouts (SUBGROUP_DELIVERY_TIMEOUT, OBJECT_DELIVERY_TIMEOUT) and NEW_GROUP_REQUEST: REQUEST_OK, and the subscription goes on.** The value of a NEW_GROUP_REQUEST is handed to whoever uses the session (row on NEW_GROUP_REQUEST). The relay acts on the Subgroup's timeout (next row); nobody acts on the Object's, in an update as in a SUBSCRIBE; the two clients act on no delivery timeout and change nothing. With any other parameter, also next to a timeout: the first such update is answered with REQUEST_ERROR `NOT_SUPPORTED`, then the subscription ends with PUBLISH_DONE `UPDATE_FAILED` (`0x8`); further REQUEST_UPDATEs that arrive before the subscription has ended get no reply. The session stays open. The parameters of every REQUEST_UPDATE are still checked against §10.2.1 first, and a parameter that is not allowed there is a `PROTOCOL_VIOLATION` | §10.9 requires exactly one REQUEST_OK or REQUEST_ERROR in reply, has "If a parameter previously set on the request is not present in REQUEST_UPDATE, its value remains unchanged", so an update without a parameter has nothing to refuse, and §13.6.1 names "REQUEST_UPDATE with no modified Message Parameters" as a way to keep a session from idling out. When the update is unsuccessful the publisher MUST also terminate the subscription with `UPDATE_FAILED`; §10.9.1: when coalesced updates fail, "only a single REQUEST_ERROR will be sent". WHY OBJECT_DELIVERY_TIMEOUT is accepted, where nothing acts on it: a SUBSCRIBE that sets it is accepted the same way, and a parameter that is taken at first and ends the subscription when it is sent again would be the worse of the two (known shortcomings, delivery timeouts). WHY NEW_GROUP_REQUEST is accepted whatever the track: it changes nothing of the subscription, so a REQUEST_OK promises nothing that then does not happen (§10.2.13: "The Original Publisher MAY delay the NEW_GROUP_REQUEST", and one that "does not support dynamic Groups ... ignores the parameter"); the session does not know whether its track has DYNAMIC_GROUPS, and a subscriber that sends the parameter for a track without it (which §10.2.13 has as MUST NOT) is answered REQUEST_OK all the same. WHY the other parameters are refused and not accepted without effect: a REQUEST_OK for a filter or a Forward State that then does not change would have the subscriber wait for Objects that do not come, or get ones it asked to stop. **The draft does not say which**: nothing in §10.9 tells a publisher that cannot apply a parameter whether to fail the update or to leave it. `moqtail`'s relay (0.15.0) answers REQUEST_OK to every update of a subscription and writes the parameters over the ones it has (`update_subscription`); nothing in its code of a subscription reads a delivery timeout (`subscription.rs` and `subscribe_handler.rs` at the tag `relay@0.15.0`, read on 2026-10-12) |
| A SUBGROUP_DELIVERY_TIMEOUT that a REQUEST_UPDATE changes, in the relay | The new time holds for every subgroup stream towards that subscriber that the relay learns the end of (the FIN of the publisher's stream) after the update, the ones that were open when it came included. **A stream whose timer runs keeps the time it was finished with**, also where the new one is shorter or none. 0 takes the timeout away; an update without the parameter leaves it. `--delivery-patience-ms` goes on as before: the smaller of the two. Never sent upstream. **Provisional** | §8 starts the timer "once it becomes aware that all of the objects on the subgroup have been published" with the SUBGROUP_DELIVERY_TIMEOUT there is, and says nothing of one that changes while a timer runs. §10.9.1 has, of a filter, "it might still receive Objects outside the new range if the publisher sent them before the update was processed", which is the same leaning: what was under way stays. §10.2.3: SHOULD NOT be forwarded upstream |
| NEW_GROUP_REQUEST (§10.2.13), and DYNAMIC_GROUPS (§12.6) | **A publisher that is one of the two clients**: the NEW_GROUP_REQUEST of a REQUEST_UPDATE is answered with REQUEST_OK and handed to the application (`PublishedTrack.onNewGroupRequest`; `SubscriptionUpdated { new_group_request }`); that of a SUBSCRIBE or a PUBLISH_OK is among the parameters the application has. Whether and when a new Group begins is the application's. The video sender of `@xmoq/media` sets DYNAMIC_GROUPS = 1 in its SUBSCRIBE_OK where it is given `dynamicGroups`, and then begins a Group for a request of 0 or of a value larger than the Group it sends: the next frame is a key frame once that Group is 500 ms long (`DEFAULT_SHORTEST_GROUP_MS`, provisional). The Rust client with `--dynamic-groups yes` sets the property, prints the request and begins nothing. **The relay** passes a subscriber's NEW_GROUP_REQUEST on, from a SUBSCRIBE that is accepted for a track with a source and from a REQUEST_UPDATE: a REQUEST_UPDATE with the same value, to every source whose PUBLISH or SUBSCRIBE_OK had DYNAMIC_GROUPS = 1 in its Track Properties, outside Immutable Properties or inside, and that has not said PUBLISH_DONE: on the stream of its PUBLISH, or of the relay's SUBSCRIBE. Not passed on: a value other than 0 that is not larger than the Group of the track's Largest Location; any value while one the relay sent, equal or larger, is outstanding (0 while any is). Outstanding ends when an Object of a Group larger than the Largest Group arrives, and when a source is added to the track (it was not asked). The subscriber's own update is answered REQUEST_OK whatever is passed on. Where the track has no source and the relay sends a SUBSCRIBE upstream, that SUBSCRIBE carries the largest NEW_GROUP_REQUEST of the subscribers that wait, and nothing else of theirs. The relay sends no NEW_GROUP_REQUEST in its PUBLISH_OK. The answer to the relay's REQUEST_UPDATE changes nothing in the relay; at most 16 of its updates wait for a publisher's answer, and one more is not sent | §10.2.13, Relay Handling: "A relay that receives a NEW_GROUP_REQUEST for a Track without an Established subscription MUST include the NEW_GROUP_REQUEST when subscribing upstream. A relay that receives a NEW_GROUP_REQUEST for an Established subscription with a value of 0 or a value larger than the Largest Group MUST send a REQUEST_UPDATE including the NEW_GROUP_REQUEST to the publisher unless: 1. The Track does not support dynamic Groups 2. There is already an outstanding NEW_GROUP_REQUEST from this Relay with a greater or equal value"; "If a relay receives a NEW_GROUP_REQUEST with a non-zero value less than or equal to the Largest Group, it does not send a NEW_GROUP_REQUEST upstream"; "After sending a NEW_GROUP_REQUEST upstream, the request is considered outstanding until the Largest Group increases." §12.6: "If omitted, the value is 0." **The draft does not say** what the "Established subscription" of a SUBSCRIBE is that the relay answers from a track it has: read here as the relay's subscription upstream, so that the parameter of such a SUBSCRIBE is treated as that of an update. Nor which publisher is meant where a track has several: each that has the property is asked. Nor what a publisher does with the parameter for a track without the property (row on REQUEST_UPDATE). A publisher's answer that comes after its PUBLISH_DONE closes its session: §10.11 has PUBLISH_DONE as "the final message", and neither client answers an update after it. A DYNAMIC_GROUPS above 1 in SUBSCRIBE_OK, PUBLISH, REQUEST_OK or FETCH_OK closes the session with `PROTOCOL_VIOLATION`, in both decoders; one inside Immutable Properties (§12.7) does so in `@xmoq/moqt`, and in the Rust decoder with the pull request the row on Immutable Properties names. **Not met**, in the known shortcomings: `@xmoq/moqt` cannot send a REQUEST_UPDATE for a subscription a PUBLISH of the peer made, since it accepts no PUBLISH of the peer. `moqtail`'s relay and test client at `relay@0.15.0` neither send the parameter nor act on it (read in `apps/` of the checkout `cargo install` made for that tag, commit dd8623d, on 2026-10-13; its libraries encode the parameter and the property), so this is run between own parts only, where both sides can share a misreading ([record](experiments/2026-10-13-a-subscriber-asks-for-a-new-group.md)) |
| REQUEST_UPDATE on any other request stream of a client | `PROTOCOL_VIOLATION` | §10.9 lets only the sender of a request, or the subscriber of a subscription created by PUBLISH, send it. A client's own SUBSCRIBE or PUBLISH_NAMESPACE stream cannot carry one from the peer |
| A request stream of the peer that ends with a FIN inside its first message | The session is closed with `PROTOCOL_VIOLATION`, whatever the request. A stream that ends without a byte is no request and nothing happens; a reset is no error either. **The two differ in what they send first**: `@xmoq/moqt` refuses a request it does not serve as soon as its Request ID is read, so a peer whose stream ends later inside that message has got REQUEST_ERROR `NOT_SUPPORTED` before the session closes, where the Rust implementation decodes the whole message first and only closes. A FETCH is decoded whole by both. `@xmoq/moqt` decodes what follows on the stream of a SUBSCRIBE it handed to the application, also after the application rejected it, after a REQUEST_UPDATE ended it, and after PUBLISH_DONE: a REQUEST_UPDATE there uses up its Request ID, and bytes that do not decode close the session. It stops when this endpoint has stopped or reset the stream: when its wait after PUBLISH_DONE is over, and after the subscriber's reset or STOP_SENDING. What follows a request the session refused by itself is still dropped without being decoded. The Rust reader decodes everything on a request stream, so bytes that do not decode close the session there in every one of these cases; the relay and the Rust client give the session what follows only after their own PUBLISH_DONE, so a REQUEST_UPDATE after a rejection uses up no Request ID there. §10.1 has every REQUEST_UPDATE consume a Request ID without a condition, which is the reading of `@xmoq/moqt`; the two are not made one yet | §10: "If the length does not match the length of the Message Payload, the receiver MUST close the session with a PROTOCOL_VIOLATION". A stream that ends inside a message is read as a length its payload does not match |
| Other message or stream type that the draft defines and XmoQ does not implement (messages that have no reply) | Close the session with `INTERNAL_ERROR` | There is no per-request answer to give. The peer follows the draft, so it is not a violation. FETCH_OK is decoded, in both implementations; one that arrives on a request stream that carries no FETCH of the receiver is a response nobody asked for and closes the session with `PROTOCOL_VIOLATION`, as any response that answers no request does. A fetch stream is read in both implementations (rows on FETCH below) and is not of this row |
| A datagram of an unknown type, received | **The session is closed with `PROTOCOL_VIOLATION` (`0x3`), in both implementations**: the relay, the Rust client and the terminal viewer by `xmoq-moqt-io`, which reads every datagram for its type (`xmoq_moqt::data::datagram_fault`), and `@xmoq/moqt`, which reads every datagram (`classifyDatagram` in `packages/moqt/src/core/datagram.ts`). The type is the varint the datagram begins with. Unknown: a type that is not of the form 0b00X0XXXX (`0x10` to `0x1F`, `0x30` and up, any type of two bytes or more, the type of a padding stream among them), one with both the STATUS bit (`0x20`) and the END_OF_GROUP bit (`0x02`), and a datagram that is empty or ends inside its type. A non-minimal encoding of a valid type is that type. An `OBJECT_DATAGRAM` of a valid type is dropped without being read further (known gap on datagrams). **A PADDING DATAGRAM (`0x132B3E29`) is discarded by both implementations, whatever follows its type** (§11.5.2). `@xmoq/moqt` reads one at a time: the next is read once the session has taken the one before, and nothing is kept, so what waits is held by the browser, which drops the oldest when its queue is full (W3C WebTransport, Editor's Draft read on 2026-10-24). Run in `mise run interop`: `xmoq-quiet-peer --quiet datagram` sends own-rust, the terminal viewer and own-browser a datagram of the type 0x30 after their SETUP (`quiet peer: ... datagram`), and as a client sends the own relay one (`--send-datagram-hex 30`) ([record](experiments/2026-10-24-datagrams-read-by-the-browser-client.md)) | §11: "All MOQT datagrams start with a variable-length integer indicating the type of the datagram", and "An endpoint that receives an unknown datagram type MUST close the session". §11.3.1: Type values "with both the STATUS bit (0x20) and END_OF_GROUP bit (0x02) set" and "that do not match the form 0b00X0XXXX" are invalid, and the endpoint "MUST close the session with a PROTOCOL_VIOLATION". §11.5.2: "The receiver MUST discard all data received in a padding datagram"; that the Padding Data "MUST all be set to zero" binds its sender, and is not checked. WHY a datagram without a type as well: such a datagram does not begin with the varint §11 says every datagram begins with |
| GOAWAY (§10.4), received | **On the control stream, after SETUP: taken, and the session opens no request after it; what is open goes on.** Both sessions close the session with `PROTOCOL_VIOLATION` for a second GOAWAY, for one without a Request ID, and, as a server, for one with a New Session URI; with `INVALID_REQUEST_ID` for a Request ID of the sender's parity; with `PROTOCOL_VIOLATION` for a New Session URI over 8,192 bytes, as they decode it. A new request is refused to the caller (`@xmoq/moqt`: `subscribe()` and the others reject; Rust: `UsageError("the peer sent GOAWAY")`), and `MoqtConnection.goAway` resolves. **What each does next**: `keepPlaying` and `keepPublishing` of `@xmoq/media` close the session with `NO_ERROR` at once and connect anew without their pause, handing the GOAWAY to `connect`, and to every `connect` after it until another comes (the pages of the interop run connect to the New Session URI where there is one, with the same certificate hash; the demo's pages ask the room again, as after any end); the terminal viewer does the same, also without a room (it keeps to the URI for as long as the room or its flags name the place it left), and also where the GOAWAY comes while it waits for the catalog; the Rust client closes with `NO_ERROR` and leaves with 0. **A request refused with `GOING_AWAY` is followed by a wait for the GOAWAY behind it**, for as long as an answer gets (10 seconds), in the three and in `keepInTheRoom` of `@xmoq/chat`: the two travel on different streams, and the refusal can be read first; without a GOAWAY in that time the refusal is a failure as before. A GOAWAY that breaks a rule closes the session with the code above, in the terminal viewer too; the relay asks a publisher that sent one for no track and no FETCH, and passes it over as one that is not there. **On a request stream: taken, for that request alone** (§10.4: "to initiate migration of that individual request"). Both sessions close with `PROTOCOL_VIOLATION` for a second GOAWAY on one request stream, for one that carries a Request ID, and, as a server, for one with a New Session URI, also on the stream of a request of the peer that was refused or ended; one that crosses the end of a PUBLISH of this endpoint is not read; the request, and the session's other requests, are as they were. The session tells it for a request of its own (Rust: `RequestEvent::GoAway`, `PeerRequestEvent::GoAway` for one of the peer; `@xmoq/moqt`: `Subscription.goAway`, which resolves also for one that came before `SUBSCRIBE_OK`), and nothing for a request of the peer in `@xmoq/moqt`, nor for its PUBLISH, PUBLISH_NAMESPACE or FETCH. **What each does next**: on the video's subscription, `playVideoTrack` ends with `moved` and `keepPlaying` with `movedBy` leaves the session as at a GOAWAY on the control stream, and so does the terminal viewer; on the sound's alone, it is cancelled and asked for again on the session (`keepTrackOnSession`, the terminal viewer's own asking again), also where a URI is named; the Rust client leaves with `NO_ERROR` (`REQUEST_GOAWAY`); the relay does nothing for one on its own SUBSCRIBE or FETCH, and nothing for one on a client's request, which that client ends. A client sends no GOAWAY; the relay sends one when it is told to stop (row on a GOAWAY the relay sends). Run in `mise run interop` (`quiet peer: ... GOAWAY`) against `xmoq-quiet-peer --quiet goaway`, which refuses every request of its first session with `GOING_AWAY` and sends the GOAWAY after the first refusal, and (`moqtail relay: goaway`) against moqtail's relay at SIGTERM, which sends one to every session, with its `--redirect-uri`, a Timeout of 10,000 ms and Request ID 0 (relay@0.15.0, `broadcast_goaway`): the pages move to the URI and play on, the Rust client leaves with 0; the byte rows are in `fixtures/moqt-18-from-libraries/` | §10.4: "Upon receiving a GOAWAY on the control stream, an endpoint SHOULD NOT initiate new requests to the peer", "The GOAWAY message does not impact subscription state", "The endpoint MUST close the session with a PROTOCOL_VIOLATION (Section 3.5) if it receives more than one GOAWAY on the control stream", "If a server receives a GOAWAY with a non-zero New Session URI Length it MUST close the session with a PROTOCOL_VIOLATION", "If the parity of the Request ID does not match the receiver's parity, the endpoint MUST close the session with INVALID_REQUEST_ID", and of the Request ID "Present only when sent on the control stream". WHY a violation where it is missing there: the field is the receiver's one way to tell which of its requests were taken. WHY the clients end their subscriptions before the new session, where §3.6 recommends that "the client waits until there are no more Established subscriptions before closing the session with NO_ERROR" and makes the new session "in the background": two sessions would play the same tracks into one playout at once, and what is lost is the time of one connection. WHY the Rust client does not move: it is a tool that is told one URL; its mode holds the session while it runs. WHY a wait after `GOING_AWAY`: §10.4 has the sender of a GOAWAY refuse "any requests that arrive after the GOAWAY ... with REQUEST_ERROR using error code GOING_AWAY", and a client that took the refusal for a failure would connect again to the URI it had, not the one named. WHY that wait is bounded: §10.6.2 has GOING_AWAY also for "The endpoint has received a GOAWAY", from a peer that may send none. WHY `keepPublishing` does not announce on the new session before it leaves the old one, as §9.5.1 has a publisher do: one publisher in two sessions is two sources of its tracks at the relay. WHY a new session for the video's subscription also without a URI, where §10.4 has it sent again "on the current session if no URI is provided": the picture's first frame and its clock begin with a session in both viewers, and the sound follows the picture. WHY the sound alone stays on the session also with a URI: the picture stays there, and the sound is played by its clock (a SHOULD not followed). WHY the relay does not send its SUBSCRIBE again: on the same session it is a second subscription to the track in the same role, refused with `DUPLICATE_SUBSCRIPTION` while the first lasts (§5.1); the subscription goes on until the publisher ends it. WHY the clients connect again at once after a GOAWAY, and only once in a row: what is played stands still until the next session, and a relay that sends GOAWAY on every session would have them connect as fast as they can. WHY the URI is decoded as bytes in Rust and as text in TypeScript: as the Connect URI of a Redirect in each |

## Known gaps against the draft

These are requirements of draft 18 that the implementations do not meet yet. Each has a `FIXME:` at the place in the code where it belongs.

**The four that could do the most harm**, as they were found on 2026-10-12, and what is left of each after the limits of 2026-10-13; looked at against the code again on 2026-10-13, and against the changes of 2026-10-14 (NEW_GROUP_REQUEST, the relay's flags to give up older Groups taken out, DYNAMIC_GROUPS, a FETCH asked of the next publisher), which change none of the four. Three of them are limited for one session and open for a sender with several sessions; the second waits for the decision on authorization. Each is in the list below, or in the rows it names; the order is by who is hurt: other viewers first, then the relay, then the one session.

1. **One subscriber could keep every other from a publisher.** Limited on 2026-10-13: of the 64 requests the relay has open on a publisher, 8 for one subscriber's session, and of its 16 FETCH requests, 4 (row "How much of a publisher one subscriber's session may take"). Before that, one session that sent 10 FETCHes a second to a publisher that answered nothing had 12 of another viewer's 14 FETCHes refused with `EXCESSIVE_LOAD`, and one that sent 30 SUBSCRIBEs a second for new track names had half of another viewer's SUBSCRIBEs refused; with the limit every request of the other viewer reached the publisher. **What is left**: a sender with several sessions has that many shares, and 8 sessions, or 4, do what one did; the relay takes 256 and does not count them by where they come from.
2. **Any client can be a further source of a track** (the two gaps on several publishers, and authorization). Without a key the relay takes a PUBLISH for a track that is being broadcast from anybody, up to 4 sources, and passes on each Subgroup from whichever source sends it first: a client that sends its own Subgroups under the Group IDs to come would have them passed on to every viewer in place of the publisher's (derived from the rule; not run with a source that sends other content). With a key, only a holder of a token for that namespace can.
3. **What a fetch stream the relay writes from its cache keeps alive was bounded by nothing.** Limited on 2026-10-13, twice: the stream has a time for the whole (30 seconds, or as long as its Objects take at 500 kbit/s), and what such streams keep of Groups the cache has let go of is counted for the relay, 256 MiB at most and an eighth of it for one session (rows "A fetch stream the relay writes from its cache" and "What the relay's fetch streams keep beyond its cache"). Before that, a reader that took 16 KiB a second on each of 16 fetch streams had none of them ended in 90 s, with the Group they carried dropped from the cache after 5. **What is left**: a sender with nine sessions or more has more than the whole, and the relay then stops the streams of whoever has the most, which may be another's (`docs/experiments/2026-10-13-a-fetch-from-the-relays-cache-that-is-read-slowly.md`).
4. **A session could announce a namespace as often as it liked.** Limited on 2026-10-13: five `PUBLISH_NAMESPACE` requests at once for a session, and one more each second (row "How often a session may announce"). Before that, one session that announced and withdrew 100 times a second, with 64 tracks or more of the namespace held or subscribed to, had the relay send 6,400 SUBSCRIBEs a second and use 0.87 of a core; with the limit the same session costs 0.02 to 0.03 of a core, and 0.14 at 1,000 a second. The Objects of the sessions beside it were not late in either case (11 cores). What is left: each session has its own allowance, so 256 sessions have 256 times as much, which was not run (`docs/experiments/2026-10-13-a-session-that-announces-a-namespace-again-and-again.md`).

A fifth was found that day and closed the same day: a session that sent its SETUP and then held nothing kept its place among the relay's 256 for as long as its connection lived (row "A session that holds nothing"). Not among them, though they stall something: the connection's flow control (a session that does not read stalls itself, not others), a subgroup stream of the peer that stays open (64 of them stop that session's own later streams), and the STOP_SENDING Chromium does not always report (a request the page believes open, on the page).

- **A subgroup stream of the peer that stays open after its header.** No requirement of the draft, and a hole in a limit, in both implementations: it holds its place among the streams read at once for as long as the peer likes, and 64 of them keep every later stream of that kind from being read. It is left so: a time would end a Group that is sent slowly, which is a way to publish. A request stream no longer does the same: once this endpoint has finished its own direction (a refusal, a FETCH that was served, PUBLISH_DONE), the peer has 3 seconds in `@xmoq/moqt` and 2 in the relay to end its direction, and is stopped then (row on what still comes on the stream of a request of the peer that was refused). The Rust client has no such time: it runs once and ends.
- **A subscription a page accepted holds a place for as long as it lasts.** No requirement of the draft. An accepted SUBSCRIBE of the peer keeps its request stream open, which is one of the 64 bidirectional streams `@xmoq/moqt` reads at once. Nothing ends a subscription whose subscriber neither ends it nor is sent anything; that is a subscription that goes on, not a stream that fails to end.
- **A STOP_SENDING for a stream the peer opened that arrives before the page has taken the stream is not always reported by Chromium** (13 of 120, [record](experiments/2026-10-11-write-abort-in-chromium.md)). A peer that cancels a request that way, without resetting its own direction, can leave `@xmoq/moqt` with a request, or an accepted subscription, it believes open. The own relay and the moqtail relay reset their direction as well when they cancel (the latter by its source, not run), and the reset is seen.
- **The relay takes a WebTransport session only from a peer that sends the older token in its CONNECT.** `web-transport-proto` 0.6.2, under `web-transport-quinn` 0.13.2, wants `:protocol` to be `webtransport` and sends that itself; a peer that sends `webtransport-h3`, the token of `draft-ietf-webtrans-http3-15` §3.2, is turned away during the handshake (`HANDSHAKE_FAILED … expected webtransport, got: Some("webtransport-h3")`). `moqlivemock`'s clients send the newer token, and connect only with one line changed ([`interop/peers/moqlivemock/`](../interop/peers/moqlivemock/README.md)). Against `moqtail`'s relay the unchanged subscriber failed as well (`http3: parsing frame failed: EOF` on its side); the relay's side was not looked at, so whether for the same reason is not known. Chromium 156 connects, so it sends the older token; its CONNECT was not looked at. When a browser changes the token, the relay stops taking it until the library does.
- **`@xmoq/moqt` and `@xmoq/msf` report a failure of a handler with the global `reportError`, unguarded.** In a runtime without it the call throws: a handler's failure is then an unhandled rejection, and `end` of a catalog publisher rejects. Not run in such a runtime.
- **A limit on the payload of an Object for one subscription holds only from its SUBSCRIBE_OK on.** `subscribe({ maxObjectPayloadLength })` sets one below the connection's (`limits.maxObjectPayloadLength`, 16 MiB by default), `@xmoq/msf` sets the catalog's 1 MiB, and `@xmoq/chat` 64 KiB for the lines of a room. An Object whose length was read while the Track Alias of its stream was unknown is under the connection's limit. The Rust implementation has the same from the same moment (`StreamStops::limit_payload` of `xmoq-moqt-io`; row "Undecoded bytes of subgroup streams"), and the terminal viewer sets the catalog's 1 MiB and the chat's `lines` 64 KiB. A fetch stream is decoded by its reader, which can give a smaller limit, and `@xmoq/msf` does. No media track sets one.
- **`@xmoq/moqt` remembers no Object it sent.** A page answers the FETCH the relay sends it for a viewer's Joining FETCH only through its application (`serve({ fetch })`), which has to have kept the Objects. §10.2.11 has "If Objects have been published on this Track the Publisher MUST include" LARGEST_OBJECT in SUBSCRIBE_OK; the library does not know, so the application has to pass it (`accept`). Without it the relay refuses a viewer's Joining FETCH for that subscription with `INVALID_RANGE`.
- **A FETCH of the peer that `@xmoq/moqt` accepted and that the subscriber neither reads nor gives up holds its two streams, and its place among `limits.maxPeerFetches`, for the session.** Behind the own relay this does not happen: the relay gives up on a subscriber that does not read and cancels upstream.
- **Through `moqtail`'s relay, what a page answers a FETCH with does not reach the viewer.** That relay sends the viewer a fetch stream that carries the Request ID of its own FETCH to the publisher, which no FETCH of the viewer has ([record](experiments/2026-10-11-a-page-answers-a-fetch.md)). The own relay writes the viewer's Request ID.
- **Authorization token structure (§10.2.2).** The token is carried as opaque bytes, so the alias types (REGISTER, USE_ALIAS, DELETE) and the rules for them in SETUP are not enforced. Left until authentication is decided.
- **Datagrams (§11).** Neither implementation delivers an OBJECT_DATAGRAM: it is dropped without notice, and its Object is lost. Both read every datagram for its type (row on a datagram of an unknown type). The rules on the fields of an OBJECT_DATAGRAM (§11.3.1: a PROPERTIES bit with a Properties Length of 0, STATUS with PROPERTIES, a Status that is not Normal; §11.2.1.1: an unknown Object Status) are checked by neither. Datagram delivery is outside the Phase 0b scope.
- **Connection flow control for control streams first (§11.4.2, MUST: "endpoints MUST allocate connection flow control to the control streams before allocating it to any data streams"). Met by the relay as a receiver (2026-10-25); not as a sender, nor by the clients as receivers in the browser.** As a receiver the relay keeps its connection window above what the unidirectional streams of the peer can hold, filled and not read, by 1 MiB (row on the QUIC windows of the relay); a real connection with the windows of before did not get a request through 64 such streams of 256 KiB, and with these it did (`a_request_gets_through_data_streams_nobody_reads_only_where_the_windows_leave_room` in `crates/moqt-io`, and the same with the relay's values, run once). The Rust client leaves quinn's connection window unbounded, so its data streams cannot take all of it. **As a sender** the relay and the Rust client cannot keep credit for the control streams: quinn-proto 0.11.19 takes the peer's connection credit for a stream when it is written to (`write_limit`, `streams/state.rs`), first come first served, and a stream's priority orders only what goes into packets. The relay's data streams stand below its control and request streams in that order. `@xmoq/moqt` opens its data streams with `sendOrder` -1 and its control stream with 0; Chromium 156 was not seen to give its credit by that order, a request behind 16 data streams took as long either way ([record](experiments/2026-10-25-send-order-of-data-streams-in-chromium.md)). **As a receiver in the browser** the windows are the browser's, and the API has no way to set them. A deadlock of the kind the draft names was seen there, for request streams where the draft speaks of control messages: the client reads 64 unidirectional streams of the peer at once and leaves the rest with the browser. With a subscription the page did not read and one Object of 100,000 bytes a stream, the relay's PUBLISH_DONE for it did not reach the page, and after the relay had ended that subscription its SUBSCRIBE_OK for another track of the same session did not arrive either (3 of 3), until the page read again. With 57-byte Objects and with 30 Objects a stream both arrived, and without the limit the second request was answered while the page held everything that was sent ([record](experiments/2026-10-10-subscription-backlog-in-chromium.md)). The likely cause, not verified with a capture, is that the streams the page has not taken hold the connection's credit. An application that reads, however slowly, frees it; one that never reads can stall its own session. Whether the client should end such a subscription itself is in [open questions](open-questions.md).
- **Stream error codes on reserved codepoints (`draft-ietf-webtrans-http3-16` §4.4, §9.5), in Rust.** The WebTransport range has codepoints of the form `0x1f * N + 0x21` that are not WebTransport codes. `web-transport-proto` 0.6.2 checks the range only, so a reset with `0x52e4a40fa8f9` is reported with the code `0x1e` where it should be a reset without a code. XmoQ gets the decoded value and cannot tell. The same goes for the code of a STOP_SENDING, which the relay and the Rust client print. A peer that maps its codes as §4.4 says never sends such a codepoint.
- **The code of a STOP_SENDING sent from a browser on a subgroup stream was not observed.** On a request stream it was: when an own-browser subscriber cancelled, the relay printed the code `0x1` that `@xmoq/moqt` puts into the `WebTransportError`, in 53 of 60 rounds; in the other 7 the relay saw the reset of the other direction first, and it prints the line only when the STOP_SENDING comes first. On a subgroup stream the relay notices a STOP_SENDING when it next writes to the stream, and no interop run has a subscriber stop a stream the relay is still writing ([record](experiments/2026-10-10-disconnects-through-own-relay.md)).
- **`PublishedTrack.ended` after a PUBLISH_DONE that could not be written, in `@xmoq/moqt`.** Not a requirement of the draft: `done()` rejects with the error of the write, and `ended` resolves only when the session ends, although the session state has ended the subscription.
- **A SUBSCRIBE that the Rust client reads before it has sent its PUBLISH gets `NOT_SUPPORTED`.** No rule is broken: the subscription §5.1 means ("an existing subscription in Pending (publisher) state") begins with the PUBLISH, and once that is sent the session answers `DUPLICATE_SUBSCRIPTION`, as `@xmoq/moqt` does. The mode that sends PUBLISH serves no SUBSCRIBE, though, and the relay waits for a PUBLISH after `DUPLICATE_SUBSCRIPTION` and not after `NOT_SUPPORTED`: a subscriber whose SUBSCRIBE reaches that client through the relay before its PUBLISH is on the way gets `DOES_NOT_EXIST`. The track is there a moment later.
- **The Rust client in a mode that publishes leaves its peer unanswered in two waits.** While a SUBSCRIBE it is about to serve waits for `--serve-delay-ms` or for the driver's line `serve`, and in the up to 3 seconds after its last PUBLISH_DONE, when its driver is done and it waits for the peer to end that stream. A request of the peer that comes in the first is answered when the wait is over; one that comes in the second gets no answer, and the session closes right after. In every other wait (the answers to its PUBLISH_NAMESPACE and PUBLISH, `--publish-delay-ms`, the driver's line `publish`, an Object under way, the end of the first stream when it publishes anew) it answers. What it holds unread meanwhile is 16 events a queue, after which its readers wait.
- **`DUPLICATE_SUBSCRIPTION` from a publisher that sends no PUBLISH (§5.1, §10.6.2), in the relay.** The code is also the answer when the publisher still holds a subscription in the same role ("If an endpoint receives a message attempting to establish a second subscription to a Track with the same role, it MUST fail that request with a DUPLICATE_SUBSCRIPTION error"): for instance one the relay cancelled a moment ago and the publisher has not let go of yet. The relay cannot tell this from an announced PUBLISH and waits; up to 64 subscribers then get `TIMEOUT` after 5 seconds, where asking the publisher again would have got them the track. Asking again is left out because §10.6.2 ties it to the publisher's Retry Interval ("If the value is 0, the request SHOULD NOT be retried"), and the own session always sends 0 (the gap on Retry Interval below).
- **A responder's FIN after its REQUEST_OK to PUBLISH_NAMESPACE: the two clients differ.** The TypeScript client ends the request (`peer-fin`); the Rust client does not read the stream of its PUBLISH_NAMESPACE after the answer and goes on as if announced. Which of the two is right is not decided; the row on a requester's FIN covers the other direction only. The own relay never finishes that stream this way.

The relay (`crates/relay-core`, `crates/relay`) adds these:

- **Several publishers of one track (§9.3, §9.5). The MUSTs are met in part.** §9.5: "Relays MUST send SUBSCRIBE messages to all matching publishers. This includes matching both Established subscriptions on the Full Track Name and Namespace Prefix Matching against published Namespaces." §9.3: "Relays MUST handle Objects for the same Track from multiple publishers and forward them to matching Established subscriptions." §9.5: "When a relay receives an authorized PUBLISH_NAMESPACE for a namespace that matches one or more existing subscriptions to other upstream sessions, it MUST send a SUBSCRIBE to the publisher that sent the PUBLISH_NAMESPACE for each matching subscription." §9.5: "When it receives an authorized PUBLISH message for a Track that has Established downstream subscriptions, it MUST respond with PUBLISH_OK." Against that stands §9.3: "An implementation can use mechanisms such as REQUEST_ERROR or unsubscribing (see Section 3.3.2) if it cannot accept an additional publisher due to implementation constraints." §9.5 again: "Relays MUST forward PUBLISH_NAMESPACE or PUBLISH messages to all matching subscribers", which is empty here because the relay refuses SUBSCRIBE_NAMESPACE. What is done: a PUBLISH for a track is accepted whatever state the track is in, up to 4 sources a track, and each Subgroup is taken from the source that sends it first (rows below). A SUBSCRIBE goes to the publishers of a matching namespace, also for a track that has a source (row on a SUBSCRIBE for a track that has no source). A publisher that announces a namespace while tracks of it are subscribed to is asked for them then. What is not done, five things, each against one of the MUSTs above. **No more publishers are asked than the track has room for**: with its sources and what is asked already, 4; the others are asked when a subscriber comes or a namespace of the track is announced, and there is room. That holds for the publisher that sends PUBLISH_NAMESPACE as well: it is asked before the ones that were left out earlier, and not at all for a track that has no room. It rests on the sentence of §9.3 above. WHY: a publisher that accepted would be cancelled at once when the track is full, having started to send. **A publisher that was passed over because the relay had 64 requests open on it is not asked when one of them ends**, but when the next subscriber of the track comes or a namespace of it is announced. **A publisher that was asked for a track and did not become a source is not asked for it again** until it announces a namespace of the track anew, though it is still a matching publisher. WHY: it would get a SUBSCRIBE with every subscriber that comes to a track it has said it does not have, and the relay would open as many requests. **A PUBLISH_NAMESPACE does not get its publisher asked for a track that has a source and no subscriber.** §9.5 has "a namespace that matches one or more existing subscriptions to other upstream sessions", and a PUBLISH the relay accepted is a subscription of the relay to an upstream session, with subscribers or without; read so, the publisher is to be asked. The relay reads the sentence as being about tracks somebody is subscribed to, and asks for those. WHY: nobody wants more of a track nobody receives, and the publisher that is asked would send it to the relay all the same. **A SUBSCRIBE for a track whose sources all drain is refused** (row below), where §9.5 has "If there are no Established upstream subscriptions for the requested Track, the Relay MUST send a SUBSCRIBE request to each publisher that has published the subscription's namespace or prefix thereof": such a track has no place for subscribers that wait.
- **Sources of a track that do not send the same thing (§9.1, §2.4.2, §9.3).** §9.1: "An endpoint that receives a duplicate Object with a different Forwarding Preference, Subgroup ID, Priority or Payload MUST treat the track as Malformed." §2.4.2, the sixth example of a malformed track: "The same Object is received more than once with different Payload or other immutable properties." §9.3: "The Relay SHOULD attempt to deduplicate Objects before forwarding, subject to implementation constraints." Of the four, the relay compares the Priority, for a Subgroup it remembers and where it can tell the priority (row on a Subgroup that comes again with another Publisher Priority, and the known gap on when a priority is compared); the Forwarding Preference, the Subgroup ID and the Payload of what two sources of a track send are not compared, so the MUST is met in part, and the relay removes duplicates by Subgroup and not by Object. A Subgroup is taken from whichever source sends it first, whole, and the other source's stream for it is stopped unread; a source whose Groups are numbered differently from another's is passed on next to it as if the Groups were different ones while the numbers are less than 8 apart, and has all its streams stopped when its numbers are the smaller ones by 8 or more (row on how long the relay remembers). Runs with two publishers were done with publishers that send the same Object under the same Group ID only.
- **A session that has as many timers running as it may gets the next one at once (relay).** The hub runs at most 1,024 timers for a session at a time. One that is asked for beyond that is not started and is reported as run out at once, so that what it guarded is let go of and not kept for good: a wait for the last streams after PUBLISH_DONE then ends as soon as it begins, an early stream is dropped at once, and a request the relay sent counts as unanswered at once. **The timer of a wait after PUBLISH_DONE is dropped when the wait is over** (the counted streams came, or the source went another way), as the timers for an answer, for a peer to end its stream and for a held SUBSCRIBE are. Before that it counted for its 2 seconds: a publisher that published a track and ended it 1,024 times, each time with its counted stream at once, had the stream of the next round, 100 ms after its PUBLISH_DONE, not waited for (the PUBLISH stream reset with 0x1 where a FIN was due; a test of the relay over a connection in memory, with the relay's own limit). So are the timers of an early stream (a stream ahead of its PUBLISH), when its PUBLISH or its SUBSCRIBE_OK comes, is refused, or the stream is given up, and of a Joining FETCH read before its SUBSCRIBE, when the SUBSCRIBE comes or the FETCH is over (since 2026-10-24); a session reaches the limit with those only by opening 1,024 such streams that stay unsettled within their time. **The timer that gives a session an announcement back is started all the same** (one for a session at most): reported as run out at once, it gave a session with as many timers as it may every announcement back at once, and the limit on announcements did not hold for it (seen in a test with a limit of 2 timers: seven announcements of seven accepted; five with the timer exempt).
- **A stream of a subscription that comes after a new subscription took its Track Alias (§10.11, §11.1).** A publisher says PUBLISH_DONE with a Stream Count, one of the streams it counted is still on its way, and a PUBLISH or SUBSCRIBE_OK that is accepted gives the alias to a new subscription. A subgroup stream carries the alias and nothing else that says which subscription it is of, so the late stream is taken for one of the new subscription: its Objects are delivered under it, and its end counts towards the Stream Count of the new subscription's PUBLISH_DONE. That wait can then end while a stream of the new subscription is open; the relay stops that stream, finishes the PUBLISH stream as if all had come, and ends the track where the source was its last. The streams of the old subscription that are open when the alias is taken are known and are not counted (row on a reused Track Alias). The draft gives a receiver no way to tell the others apart. **Such a stream is also read with the DEFAULT PUBLISHER PRIORITY of the new subscription where its header has no priority.** Where the two subscriptions have different defaults and the stream is for a Subgroup the relay remembers with the priority it really has, whether the first subscription sent that Subgroup or another source of the track did, the relay sees the Subgroup with two priorities and ends the track for every subscriber as malformed, though nothing is wrong with it. A test pins it. It takes a PUBLISH or a SUBSCRIBE_OK that gives the alias to a subscription with another default, headers without a priority, and a stream of the first subscription that arrives after it. **The same happens the other way round, with a stream of the new subscription that the relay reads before the PUBLISH_DONE of the first:** a publisher says PUBLISH_DONE, publishes anew under the alias with another default and sends a stream without a priority, the three on three streams between which QUIC keeps no order. Read first, the stream has the default of the first subscription, which to the relay still goes on. A test pins that as well. The relay cannot tell it from one subscription that sends a Subgroup again with another priority, which is what the comparison is there to find.
- **Streams a publisher sent ahead for a PUBLISH that is refused, under the Track Alias of a subscription that drains (§5.1, §10.10, §10.11).** §5.1: "Publishers MAY start sending Objects on PUBLISH-initiated subscriptions before receiving a PUBLISH_OK response". A publisher says PUBLISH_DONE, sends PUBLISH again under the same Track Alias while the streams the first one counted are awaited, and opens a stream at once. When the PUBLISH is refused, the alias means the draining subscription again, and nothing tells that stream from one of it: its Objects go to the subscribers of the draining subscription's track, and its end counts towards the Stream Count. With that the count can be reached before the streams that were counted have ended, and the first PUBLISH stream then gets its FIN early; a counted stream that comes after is stopped. The refused PUBLISH can be for another track, whose Objects then go out under the first track. The draft gives a receiver no way to tell the two apart. A PUBLISH that is refused before the session looks at its alias (`DUPLICATE_SUBSCRIPTION`, a Mandatory Track Property) and a refused SUBSCRIBE_OK leave the same behind. Before the Rust session kept the draining subscription through a refused PUBLISH, such a refusal always ended the wait at once. At the relay this takes a PUBLISH that is refused, which leaves a track that has all the sources it may have, a Mandatory Track Property, and the limit of open requests; a publisher that publishes its own track anew is accepted, under the same alias and under another.
- **A Subgroup without a Publisher Priority reaches the subscribers under the default of another source (§11.4.2, §12.4), in the relay.** Such a Subgroup has the DEFAULT PUBLISHER PRIORITY of the subscription it came on. The relay passes its header on as it came, and the Track Properties the subscribers have are those of the source that came last (§2.5). With two sources whose defaults differ, a Subgroup of the one that came first is therefore read by the subscribers with the default of the other. A test of the core pins it. With one source it does not happen. Mending it means writing the priority into the header where a track has had several sources, which goes with the question of whose Track Properties a track with several sources has.
- **Two DEFAULT PUBLISHER PRIORITY properties in one message are not refused (§12.4), in the relay.** The relay takes the first where it compares priorities, and passes both on.
- **A Publisher Priority is compared only for a Subgroup the relay remembers, and not where it cannot tell the default (§2.4.2).** The relay remembers the 8 newest Groups and 256 Subgroups of a track; a Subgroup that comes again later with another priority passes or is left like any other. A stream without a priority in its header that arrives under a Track Alias whose subscription drains is not compared either, and where the Subgroup is taken from it, the priority the relay remembered for that Subgroup is gone: a later stream is compared again only once the Subgroup has been taken from a stream whose priority is known, which a second stream of the same source does and a stream of another source, which is left, does not. All of that is on the side of not finding a difference: the publisher may have sent PUBLISH anew under the alias with another default, and the stream ahead of it (§5.1).
- **The other examples of a malformed track that reach across streams are not looked for (§2.4.2).** The fourth and the fifth, an Object past the last one of its Group or of the track, are found within one subgroup stream (row on an Object after End of Group or End of Track) and not across streams: the relay does not remember which Objects it has passed on. The seventh, another Forwarding Preference than before, cannot come about, since the relay reads no datagrams.
- **Objects past the end of a Subgroup, and a Subgroup on two streams that both end with a FIN with different last Objects, where the relay does not read the second stream (§2.4.2, the second and third example of a malformed track).** The relay finds both on a second stream of the same source for a Subgroup it delivered whole (row on a Subgroup that ends twice). It does not find them: on a stream of another source, which is stopped unread (decided on 2026-10-25); on a second stream whose header is read before the FIN of the first, which takes the place of the first as any second stream of the same source while the first is open, so that nothing is compared and the subscribers get the Subgroup on a new stream after the first was reset; on a stream past the 4 read at once or the 10 s; and for a Subgroup the relay has forgotten. Since QUIC keeps no order between streams, which of the first two happens depends on what the relay reads first.
- **A second stream for a Subgroup the relay has forgotten (§2.2).** It passes, so the subscribers can get a Subgroup on two streams of which neither was reset, which §2.2 has as MUST NOT. The relay forgets a Subgroup when its Group is 8 or more behind the newest, and when the track has more than 256 Subgroups in those Groups: then the smallest Subgroup IDs of the oldest Group go, also ones whose stream is still open, and a second stream for one of those is opened downstream next to the first, which is not reset. That takes more than 32 Subgroups a Group on average over 8 Groups, or more than 256 in one; a publisher that sends every Object as a Subgroup of its own gets there. With one source per track it takes a publisher that sends a Subgroup twice. Once a track has had several sources, a stream of a Group that is 8 or more behind the newest is stopped and not passed on (row on how long the relay remembers), so a source that is merely behind another does not cause it, whether the other is still there or not; what is left is the limit of 256.
- **Which of two open streams for a Subgroup the source goes on with (§11.4).** The relay keeps the one whose header it read later (row on a second stream, below). It knows the order in which the headers were read and not the QUIC stream IDs. When a source resets a stream and sends the Subgroup again, and the header of the first stream is read after that of the second, the relay stops the second and keeps the first, which ends with the reset; §11.4.3 has "A publisher that receives a STOP_SENDING on a Subgroup stream SHOULD NOT attempt to open a new stream to deliver additional Objects in that Subgroup", so the Subgroup is lost for every subscriber. No subscriber gets a wrong Object. Whether this happens with real peers was not looked at.
- **A Subgroup that a subscriber stopped reaches it again on another stream of its source (§11.4.3).** "SHOULD NOT attempt to open a new stream to deliver additional Objects in that Subgroup". Since 2026-10-24 the relay keeps that for the source's stream: a subscription whose stream was stopped with `STOP_SENDING` gets no other stream for it while it goes on, and one closed otherwise (a reset at its delivery timeout, a stream that never opened) gets another with the next Object. Where the Subgroup is taken anew from another stream of the source, the subscriber gets a stream for it again (the gap on a second stream for a Subgroup above). A `STOP_SENDING` is seen when the relay next writes on the stream, so a stop that comes after the last Object is not marked, and nothing more comes to open. A test of the core pins it; the case was not run with a peer that sends `STOP_SENDING` on a subgroup stream.
- **A SUBSCRIBE whose End Group is over already, or whose filter has no Location to start at, is accepted, in the relay (§5.1.2, SHOULD).** "If the publisher cannot satisfy the requested Subscription Filter ... or if the entire End Group has already been published it SHOULD send a REQUEST_ERROR with code INVALID_RANGE." The relay answers SUBSCRIBE_OK. It does not know that an End Group is published whole, and a Group at or before the End Group that reaches it late is still sent, so such a subscription can get Objects. What the MUST NOT of that paragraph asks ("A publisher MUST NOT send objects from outside the requested range") the relay keeps: the Start Location and the End Group of a filter (row on the Subscription Filter of a SUBSCRIBE).
- **A subscription is not ended when the End Group of its filter has passed, in the relay.** No PUBLISH_DONE with `SUBSCRIPTION_ENDED` (0x3, §10.11: "The publisher reached the end of an associated subscription filter") is sent; the subscription stays until the subscriber ends it or the track does. The draft does not ask it of a relay (§9.4: "A subscription with a filter can reach a state where all possible Objects matching the filter have been delivered to the subscriber. Since tracking this can be prohibitively expensive, Relays are not required or expected to do so").
- **A Subscription Filter that a REQUEST_UPDATE brings is not applied, in the relay (§10.2.9).** An update that carries one is refused, and the subscription ends (row on REQUEST_UPDATE for an Established subscription).
- **A publisher that is one of the two clients does not look at the Subscription Filter of a SUBSCRIBE (§5.1.2, MUST NOT).** `@xmoq/moqt` hands the SUBSCRIBE of a peer to its application with the filter in it, and sends what the application writes; the Rust client in the mode that serves a SUBSCRIBE sends every Object from the next one on. The own relay asks a publisher without a filter (row on the relay's SUBSCRIBE to a publisher), so neither is asked for one behind it.
- **NEW_GROUP_REQUEST (§10.2.13), DYNAMIC_GROUPS (§12.6). Met in part (2026-10-14).** The relay passes the request on (row on NEW_GROUP_REQUEST). **Only the video sender of `@xmoq/media` begins a Group for a request**, and only where its caller gives `dynamicGroups`; the demo does not. `playVideoTrack` sends the parameter only with `newGroupRequest`, and joins with a Joining FETCH when left alone; which of the two is the default is open. The terminal viewer sends neither, and waits for the next key frame. `@xmoq/moqt` refuses every PUBLISH of the peer with `NOT_SUPPORTED`, so a page has no subscription a PUBLISH made to ask for; the Rust session accepts one and can ask (`Session::update_published`), and only the relay does.
- **Delivery timeouts (§8, §10.2.3, §10.2.4). Met in part (2026-10-12).** *As the draft has it*: the relay acts on the `SUBGROUP_DELIVERY_TIMEOUT` of a SUBSCRIBE. The timer of a subgroup stream towards that subscriber starts when the relay knows that the Subgroup has no more Objects (the FIN of the publisher's stream; §8, "once it becomes aware that all of the objects on the subgroup have been published"), and a stream the subscriber's transport has not acknowledged whole when it is over is reset with `DELIVERY_TIMEOUT` (0x2), written out or not ("If the timer expires before the underlying transport stream reaches \"all data committed\" state ..., the implementation MUST reset the stream"); the subscription goes on. 0 is no timeout. The timeout is never sent upstream (§10.2.3, SHOULD NOT). *The relay's own, off unless a flag asks (decided on 2026-10-13: what the relay gives up is what a subscriber's timeout says, and this flag for those that say nothing)*: `--delivery-patience-ms` is a time for the subscribers that set none, **which leaves §8's "if none of the timeouts are set to a non-zero value, all Objects ... are delivered"** for them, and where a subscriber set a longer one the smaller of the two holds. WHY NOT also "give the older Groups of a track up when a newer one begins", which the relay had as a flag until 2026-10-13: it held for every track and every subscriber alike and had nothing to do with the time a subscriber asks for; with a sound of one piece a Group and no grace, 204 to 375 of about 985 pieces sounded on a link of 2 and 2.5 Mbit/s ([record](experiments/2026-10-12-a-page-behind-a-link-with-too-little-room-and-a-relay-that-gives-groups-up.md)); and a viewer that asks for 100 ms on its video alone has the picture that flag gave with 100 ms of grace, and its sound whole ([record](experiments/2026-10-12-the-relay-follows-the-delivery-timeout-a-viewer-asks-for.md)). The ground for the flag that stays is §8, "Publishers can, at their discretion, discontinue forwarding Objects before either of the timeouts occurs", and not the draft's "smaller of the two", which is of a publisher's Track Property and a subscriber's parameter. **Not met**: the Track Properties `SUBGROUP_DELIVERY_TIMEOUT` and `OBJECT_DELIVERY_TIMEOUT` of a publisher are not read, so the smaller of the publisher's and the subscriber's (§8) is not taken; `OBJECT_DELIVERY_TIMEOUT` is read as a parameter and not acted on (§8 has it checked "before attempting to pass [the Object] to the underlying transport", and the relay hands every Object to a send window of 4 MiB as it comes, so the check would never fail; "SHOULD minimize the amount of data buffered at the underlying transport layer" is not followed); a REQUEST_UPDATE that sets `OBJECT_DELIVERY_TIMEOUT` is answered with REQUEST_OK like a SUBSCRIBE that sets it, and not acted on either. A REQUEST_UPDATE that sets `SUBGROUP_DELIVERY_TIMEOUT` is applied (row on a SUBGROUP_DELIVERY_TIMEOUT that a REQUEST_UPDATE changes). The two clients are not senders that take a timeout: they hand a peer's SUBSCRIBE to the application with its parameters, and neither acts on them.
- **How often the sessions together may announce is not bounded (§13.1), in the relay.** One session is: five `PUBLISH_NAMESPACE` requests at once and one more each second, the others refused with `EXCESSIVE_LOAD` (row "How often a session may announce"). A session that announces again is still asked before the publishers that announced earlier and wait for room, which is what §9.5 asks for, and each announcement that is accepted still makes the relay forget that the session declined the tracks of the namespace and ask it for up to 64 of them. Every session has its own allowance, and the relay takes 256 sessions. §13.1: "Relays SHOULD implement rate limiting on subscription requests"; the sentence is about the subscription requests of a subscriber, for which the relay has no rate limit, and does not name announcements. **What a subscriber that asks for a new track name each time costs, measured on 2026-10-13**: the relay sends one SUBSCRIBE to every session that announced a namespace of the track for each such request, so with four of them 1,000 requests a second became 4,000 a second upstream, 1,000 to each publisher; the relay took 0.44 of a core (0.2 with one publisher), and the Objects of the sessions beside it were not late (95th percentile 0.7 to 1.2 ms, on 11 cores). A session that does not end its requests is stopped by the 256 it may have open. **With a publisher that does not answer, one session keeps the others from it**: 30 SUBSCRIBEs a second for new track names kept the relay's 64 requests towards that publisher taken, and about half of another viewer's SUBSCRIBEs for tracks of the namespace that were not published yet got `EXCESSIVE_LOAD` at once; 10 FETCHes a second took the 16 FETCHes, and 12 of 14 FETCHes of another viewer got `EXCESSIVE_LOAD` (gap 1 of the list at the top, seen in a run). A track that is published was not touched. A rate limit on a session's requests would not stop it, since a viewer sends 5 requests in its first second and this needs 13, or 3; a share of a publisher's places for one session would. More than four publishers and a machine with one core were not run (`docs/experiments/2026-10-13-a-session-that-asks-for-a-new-track-again-and-again.md`).
- **Retry Interval (§10.6.2).** Where several publishers were asked, the subscribers get the Retry Interval of the answer that came last (row on the publisher's answer). What an implementation gives a REQUEST_ERROR it makes up itself is in the row "The Retry Interval of a REQUEST_ERROR"; **0, which reads as "do not retry", is still given where a retry could succeed a moment later** with `DUPLICATE_SUBSCRIPTION`: to a publisher whose PUBLISH is read before its own PUBLISH_DONE for the track (row on a PUBLISH for a track the relay knows already), and to a viewer that asks anew before it was sent PUBLISH_DONE. The values are fixed numbers and not what the relay knows of the case: `EXCESSIVE_LOAD` says "after a second" whatever the limit, and nothing is randomized. The relay passing on a publisher's REQUEST_ERROR which keeps the publisher's Retry Interval unless it replaces the Error Code, where it gives its own for the code it puts in place (row on the publisher's answer and the table of codes, below). The relay does not honour a Retry Interval either. It remembers a publisher that declined a track and does not ask it again until that publisher announces the namespace anew (row on which publishers the relay asks), whatever the Retry Interval was: a publisher that refused with a wait is not asked again when the wait is over, and one that announces anew is asked at once, also after Retry Interval 0 ("If the value is 0, the request SHOULD NOT be retried"). That memory goes with the track. Where the last refusal ended a track that had no source, the next subscriber makes the relay ask every matching publisher again at once, also the ones that answered 0 or a wait that is not over. The SHOULD NOT that keeps the relay from asking again after `DUPLICATE_SUBSCRIPTION` applies there as well.
- **REQUEST_UPDATE** is applied for one thing: the SUBGROUP_DELIVERY_TIMEOUT of a subscription, in the relay (2026-10-12). Every other update of a subscription is refused, so the Forward State, the filter and the priority of a subscription cannot change; a NEW_GROUP_REQUEST is accepted and, in the relay, passed on (row on NEW_GROUP_REQUEST). For a FETCH it is accepted and changes nothing (row on REQUEST_UPDATE for a FETCH). The two clients send one for a SUBSCRIBE of their own (`Subscription.update`, `Session::update_subscription`); none for a FETCH or a PUBLISH_NAMESPACE, and for a subscription a PUBLISH of the peer made only the Rust session, for the relay's NEW_GROUP_REQUEST. **A REQUEST_UPDATE that gets no answer leaves the subscription as it is**: after the time a request gets (row on a request the peer does not answer), the browser client rejects the call and the Rust client prints `ANSWER_TIMED_OUT request=update`; neither ends the subscription, and an answer that comes later is still read. WHY not given up like a request: an update is on the stream of its SUBSCRIBE and cannot be cancelled alone.
- **A Joining FETCH for a subscription that a PUBLISH made is refused (§5.1, §10.12.2).** §5.1 gives such a subscription a Joining Location ("communicated in ... PUBLISH"), and the change log of draft 18 has "Allow joining FETCH for PUBLISH and REQUEST_UPDATE with forward=1"; the Joining Request ID is then the Request ID of the publisher's PUBLISH. The Rust session takes only a SUBSCRIBE of the peer and answers `INVALID_JOINING_REQUEST_ID` for the rest. It is met when a viewer that got a track by PUBLISH, and not by its own SUBSCRIBE, sends a Joining FETCH to the publisher or relay that published it: the own browser publisher sends PUBLISH, and so does the relay to no one yet. The sender's side is the same: the Rust session does not send a Joining FETCH that names a PUBLISH of the peer.
- **The Forward State of the subscription a Joining FETCH names is not looked at by the session (§10.12.2, MUST).** "A Joining Fetch is only permitted when the associated subscription has Forward State 1; otherwise the publisher MUST respond with a REQUEST_ERROR with error code INVALID_RANGE." Whoever answers the FETCH has to check it. The relay does (row on a Joining FETCH in the relay); the Rust client refuses every FETCH.
- **Priorities (§7.2, §7.3). Met in part (2026-10-13), in the relay.** The relay gives each stream it opens to a subscriber a priority of the transport from the SUBSCRIBER_PRIORITY of the SUBSCRIBE (128 without one) and the stream's Publisher Priority (its header's, or the default of its source, or 128): §7.2's first two steps. Every such stream is below the control stream and the request streams, which have the transport's own priority (§7.2: "the control streams SHOULD be prioritized highest, followed by the bidi request streams and then all subscribed Objects"). **Not met**: the third and fourth steps, the Group by the GROUP_ORDER and the lowest Subgroup ID. The transport takes one number for a stream and does not know which subscription it is of, so a Group in the number would order the streams of different tracks as well, where §7.2 has "the expectation is that all subscriptions will be able to send some data"; `moqtail`'s relay (0.15.0, `compute_stream_priority`) has the Group in it. Streams with the same two priorities take turns, old Groups with new. GROUP_ORDER is decoded and not used; a SUBSCRIBER_PRIORITY in a REQUEST_UPDATE of a subscription is refused; **a fetch stream** the relay writes or passes on stands by the SUBSCRIBER_PRIORITY of its FETCH, or of the REQUEST_UPDATE for it that came last (128 without one, §10.2.7: "relative to other subscriptions and fetch responses in the same session") and a Publisher Priority of 128, whatever the Objects in it have (§7.1: "FETCH responses however can contain objects with different publisher priorities"; a fetch stream is one stream and the transport takes one number for it), and a Joining FETCH is not put before the subscription it joins; the relay's own subscriptions upstream name no priority. **The clients** write each stream as its bytes come and give the transport no priority; the audio publisher of `@xmoq/media` can name a Publisher Priority for its streams and names none by default. A priority is strict: a publisher that puts its sound below its video has the sound not sent on a link without room for both ([record](experiments/2026-10-13-the-sound-behind-the-video-on-a-narrow-link-and-priorities.md)). **Three things a priority does not reach** (the mechanism of each was read in the code on 2026-10-13; what it does to a broadcast was not measured): (1) the first bytes of every stream, its type of WebTransport, are written by `web-transport-quinn` 0.13.2 with the highest priority there is before the relay's number is set (`Session::open_uni`: "Max priority for the header so the application cannot queue lower-priority data in front of it"), so a track that opens a stream for every small Object may be ordered less than its priority says; (2) the order holds for what the transport has buffered and not sent, which is at most the send window of the connection (4 MiB), and a writer that waits for room there waits whatever its priority; **seen on 2026-10-15** behind a link of 2 Mbit/s with a video of 2.65 and no timeout on the video: the window was full from about 52 s, writes waited from then on, and the sound came later and thinner from then, with a priority above the video as without; a window of 1 MiB brought it at about 20 s ([record](experiments/2026-10-15-what-the-sound-waits-behind-on-a-narrow-link.md), the relay's `--stats-every-ms`). Not to be built, decided on 2026-10-21: a relay that sends from its writers of the highest priority first, and the sound above the video by default. The demo's viewer asks for 150 ms on its video, and with that the send window does not fill; (3) the relay's limit on what waits for one subscriber (`SendBudget`) is one for the session and not one for each subscription. Since 2026-10-14 the subscription that is ended when it is used up is the one whose open streams carry the most bytes, and not the one that went over (row on a subscriber that does not take what is sent to it); before, a subscriber whose video filled it could have its sound's subscription ended instead. Seen on 2026-10-14, before that change, behind a link of 2 Mbit/s with a video of 2.65 ([record](experiments/2026-10-14-three-minutes-behind-a-narrow-link-and-the-relays-limit-for-one-viewer.md)): with the demo's viewer as it is, which asks for 150 ms on its video, nothing was ended in 3 minutes; with no timeout on the video a subscription was ended at about 106 to 109 s, the sound in one run of two (the video a moment after) and the video alone in the other, and the sound came late and thin from about 55 s on, before either.
- **Not verified against a real connection: what the relay does when it gives a fetch stream up before it is open.** A subscriber that takes nothing has its fetch stream reset with `TOO_FAR_BEHIND`. Where the relay was writing the stream this is tested, over loopback as well (`xmoq-moqt-io`: a writer that resets while its write waits). Where it gave up while the FETCH_HEADER was not all written, the reset is tested on an in-memory connection whose streams hold one byte, and on no real one: there the wait is more likely inside the opening of the stream, where there is nothing to reset. The relay's own clocks (10 seconds for the opening, and 10 for each piece it writes) run in tests on in-memory connections only. So does the stopping of a fetch stream the relay writes itself, when its FETCH is cancelled or its track is found malformed: the stream is a few bytes, which a real transport takes before a cancellation can arrive, and no run stopped one.
- **The relay does not look into a fetch stream it passes on (§2.4.2, §11.4).** It reads the FETCH_HEADER, writes one with the subscriber's Request ID, and moves the rest as bytes. So it does not find what breaks the object model there: Properties that are malformed, an Object after the end of its Group, a duplicate that differs. §2.4.2: "If a relay detects a Malformed Track, it MUST immediately terminate downstream subscriptions with PUBLISH_DONE and reset any fetch streams with Status Code MALFORMED_TRACK"; the relay detects none on a fetch stream, so a publisher's malformed fetch stream reaches the subscriber as it is, and the subscriptions to the track go on. A stream that ends with a FIN inside an Object (§11.4, a protocol violation) is passed on with its FIN as well; the subscriber is the first to decode it. Nothing of a fetch stream raises the largest Location the relay knows for the track.
- **The relay leaves the range of a FETCH to the publisher (§10.12.3, §10.13).** It checks that a Standalone FETCH does not end before it starts, and passes the Start Location and End Location on. Whether the range starts after the largest Object (`INVALID_RANGE`), where it is cut when it ends beyond it (the End Location of FETCH_OK), and the order of the Groups are what the publisher answers; the relay passes the answer and the stream on and compares neither with what it knows of the track. The `moqtail` test client as a publisher answers some of these otherwise than the draft has them ([record](experiments/2026-10-11-standalone-fetch-through-own-relay.md)), and so does what its subscriber gets through the relay.
- **Several sessions of one sender can keep every other from a publisher.** The relay asks one publisher for 16 FETCHes at once and has 64 requests open on it in all; one subscriber's session gets 4 and 8 of them (row "How much of a publisher one subscriber's session may take"), so it takes 4 sessions to have all 16 FETCHes, and 8 to have all 64 requests, and any other subscriber's request for that publisher is then refused with `EXCESSIVE_LOAD`. The relay takes 256 sessions and does not count how many come from one place. **What follows in this entry was run before the share of one session, when one session could have all 16.** A FETCH has no time limit as a whole, so a subscriber that reads fast enough not to be cut, and no faster, holds the 16 for as long as its FETCHes last. Subscriptions are not touched by this: the publisher keeps 48 of its streams for them. Nothing here is authorized, so any client that reaches the relay can do it. Whether a session gets fewer than a publisher is asked for, and whether a FETCH gets a time limit as a whole, is open with the other limits. Run against real connections ([record](experiments/2026-10-11-rust-client-fetch.md)): a subscriber that read 16 KiB of each of its 16 fetch streams every half second held them, and another subscriber's FETCH was refused meanwhile; one that read the same every 2 seconds was cut as taking nothing, so on a real connection the slowest a subscriber may read is faster than the 1 KiB in 10 seconds the relay counts by. Where that lies was not measured.
- **The Rust client answers a FETCH only with `--answer-fetch`, and then only a Standalone one.** Without the flag: `NOT_SUPPORTED`, in every mode, which drivers count on to see what a relay makes of the refusal. With it, in the modes that publish: row on a publisher that answers a Standalone FETCH from what it published. A Joining FETCH is refused with `NOT_SUPPORTED` in either case; behind a relay a publisher gets none. It sends Standalone and Joining FETCH requests and reads their fetch streams.
- **A FETCH_OK with a Mandatory Track Property that comes after the fetch stream was passed on whole resets nothing (§2.5.1).** "If the relay has already forwarded data on a fetch stream, it MUST reset the stream": while the stream is passed on the relay does, with `UNSUPPORTED_EXTENSION`. When the publisher's stream ended with a FIN before its FETCH_OK came, the FIN has gone to the subscriber and there is no stream left to reset; the subscriber gets REQUEST_ERROR `UNSUPPORTED_EXTENSION` after a fetch stream that looked complete.
- **The relay's cache is the latest Group of a track, and nothing a FETCH brought (§9.1).** A FETCH for anything else is asked of a publisher, also for Objects that passed through the relay a moment ago (row on the relay's cache). The answer a publisher gives to a FETCH the relay passes on is not cached: the relay does not look into a fetch stream. So a publisher that sent an Object once, long before, and to no subscription that reached the relay, is asked for it every time; a publisher that pushes its Objects with PUBLISH, as the browser publisher does, has its latest Group in the cache. With FILL_TIMEOUT 0 the answer is still one End of Unknown Range indicator for the whole range, where the cache could give what it holds (row on FILL_TIMEOUT 0).
- **The relay finds an Object that comes again with other content, and a Group that contradicts itself, only in the Group its cache holds (§9.1, §2.4.2, §12.9; MUST).** What it compares an Object with is the latest Group of the track, as far as the cache has it (row on an Object that comes again). Nothing is found in an earlier Group, in a Group the cache gave up (over the limits, with an End of Track, with a stream whose default priority the relay cannot tell, after an Object was taken back, after an Object came at the Object ID of an End of Group, or after a second status came above one), or in a track that is not cached at all (MAX_CACHE_DURATION or Immutable Properties among its Track Properties): there a second Object goes out to the subscribers as it comes. Nor is an Object of a fetch stream the relay passes on from a publisher compared with anything: the relay hands those streams on as bytes and does not read the Objects in them. A Forwarding Preference cannot differ, since the relay takes no datagrams. What is compared in every track is the Publisher Priority of a Subgroup the relay remembers (row on a Subgroup that comes with another Publisher Priority).
- **The end of a track that a FETCH says is taken from its FETCH_OK, not from its fetch stream (§2.4.2, §10.13).** Since 2026-10-24 the relay ends a track as malformed for an Object past one with the status END_OF_TRACK on a subgroup stream (row on a malformed track), and takes the End Location of a publisher's FETCH_OK with End Of Track 1, less one, for the final Object of the track (§10.13: "the End Location is the final Object in the Track"); an End Location with Object 0 says the whole Group, whose last Object is then not known. Where a larger Object or another final Object is known, that FETCH alone is refused with `MALFORMED_TRACK` and the track goes on; §2.4.2 would have the track malformed, which would end every subscription of it over one answer. "The last Object sent in a FETCH whose response indicated End of Track" is not looked for on the fetch stream: the relay does not read into a fetch stream it passes on.
- **An Object that comes where the relay recorded that none exists is sent on (§9.1, SHOULD NOT).** "As described in Section 2.1, an endpoint can receive an Object after it has already recorded that the Object does not exist. A caching relay SHOULD NOT cache or forward the Object in this case." The relay does not cache it, and forwards it (row on an Object that comes again, for why).
- **The application gets Immutable Properties as one property with its bytes.** Both sessions look inside them for what they check (row on Immutable Properties), and the readers of LOC look inside as well, in both implementations: `@xmoq/media` (`locProperties` of `src/moqt/loc-properties.ts`, with `propertiesToSearch` of `@xmoq/moqt/properties`) and the Rust client and the terminal viewer (`searched_properties` of `xmoq_moqt::immutable` with `Of::Object`, which the relay uses as well), before `readLocTiming` of `@xmoq/loc` and `read_timing` of `xmoq-loc`, which read the list they are given. A Timestamp both outside and inside is two, which both take for invalid, as §12.7 lets a property be in both only where it allows multiple values. Any other reader of a property above the session has to open them itself (§12.7, MUST).
- **FETCH_OK from the relay's cache has End Of Track 0 where no Object with the status END_OF_TRACK came**, also where the track's publisher has sent PUBLISH_DONE with TRACK_ENDED and the relay waits for its last streams; a publisher asked for the same range might say 1. PUBLISH_DONE names no Location (§10.11), and it comes before the streams its Stream Count names have ended, so the largest Object the relay has received when it comes need not be the last: an Object that comes after it on one of those streams can be larger, and taking the earlier one as the end would make such a track malformed (§2.4.2). The last Object is known once every stream the Stream Count names has ended, and the relay removes the track of its last source then, with its cache. Answering from the cache with End Of Track 1 needs the relay to keep a track that has ended, and a decision on how long; that touches the decision of 2026-10-11 not to keep the cache after the last publisher has gone (`crates/relay-core/src/cache.rs`).
- **A Descending FETCH with FILL_TIMEOUT 0 whose range reaches beyond the Group the relay's cache keeps gets no Object (§10.2.5).** The whole range is one End of Unknown Range indicator, where an Ascending one gets the cache's Objects (row on FILL_TIMEOUT 0). Giving them needs the Group Order in what the relay hands its I/O side to write, and a reading of where an indicator begins in a Descending stream, which §11.4.4.2 does not give.
- **Several sessions of one sender can use up what the relay's fetch streams may keep beyond its cache.** The relay counts it and has 256 MiB for all and 32 MiB for one session (row "What the relay's fetch streams keep beyond its cache"). Eight sessions that each keep their share have the whole; a FETCH the cache could answer is then refused with `EXCESSIVE_LOAD` for everybody, and a Group the cache lets go of is taken from the session that has the most kept, which need not be one of the eight. The relay takes 256 sessions and does not count how many come from one place. A fetch stream that is passed on from a publisher has no time for the whole, and is not counted: its bytes are the publisher's.
- **A Joining FETCH that has no FETCH_OK yet ends when its subscription does, in the relay (§10.12.2).** The draft has "Changing the Forward State of the associated subscription to 0 after the Joining Fetch has been accepted has no effect on the Joining Fetch" and says nothing of a subscription that ends. The relay refuses the FETCH with `INVALID_JOINING_REQUEST_ID` and cancels what it asked of the publisher, also where the publisher's fetch stream is already passed on ahead of its FETCH_OK. A FETCH that has its FETCH_OK goes on to its end. What ends a subscription: the subscriber cancels its SUBSCRIBE; the track ends with PUBLISH_DONE or is found malformed (then the code is `MALFORMED_TRACK`); the subscriber falls behind on the subscription and the relay ends it with `TOO_FAR_BEHIND`; the subscriber sends a REQUEST_UPDATE for the subscription, which the relay refuses and ends the subscription for with `UPDATE_FAILED`. Only the first is the subscriber's wish. A viewer whose publisher ends the track, or that is slow at the moment it joins, loses the Groups before as well, if the publisher has not answered the FETCH by then.
- **The relay passes an Object on only once it is whole (§5.1: "A publisher SHOULD begin sending incomplete objects when available").** A subscriber gets an Object that is under way when its last byte has reached the relay, and a FETCH whose range has one is held until then (row on a FETCH for an Object the relay is receiving). Passing Objects on as they arrive is what would take the place of that hold.
- **What a Joining FETCH and a subscription that starts at or before the Joining Location deliver can overlap, in the relay.** Such a subscription is one without a filter, or with an `AbsoluteStart` or `AbsoluteRange` filter whose Start Location is not after the Joining Location. The FETCH ends at the Joining Location (§10.12.2.1), and a subscription with the Largest Object filter starts right after it, so the two are "contiguous and non-overlapping"; the draft states that as what follows from the Joining Location, for no filter in particular, and has no word on a subscription that starts before it (row on the Subscription Filter of a SUBSCRIBE). A subscription without a filter passes "all Objects published or received via upstream subscriptions" (§5.1.2), and one with an `AbsoluteStart` filter everything from its Start Location: an Object at or before the Joining Location that reaches the relay after the SUBSCRIBE, on a stream that was behind, goes out on it and is in the fetch stream as well. That is the subscriber's choice of filter, and nothing the relay keeps apart. With a Next Group Start filter nothing overlaps, and the rest of the Group of the Joining Location is in neither. `@xmoq/moqt` sends the filter its application gives it, and none without one; the Rust client sends Largest Object unless `--subscription-filter` says otherwise. The `moqtail` relay 0.15.0 showed an overlap of another origin, a range counted from the largest Location at the time of the FETCH ([record](experiments/2026-10-11-moqtail-relay-fetch.md), a).
- **A Joining FETCH can miss Objects where a track has several sources, in the relay (§10.12.2.1).** The Joining Location is the largest Location the relay knows of the track, from any source, and the FETCH is asked of the first source first (row on whom a FETCH is asked of). A publisher that is behind the others is asked for a range it has not reached: where it answers `INVALID_RANGE`, the next one is asked; where it answers with what it has, and what lies between its largest Object and the Joining Location is neither on the fetch stream nor on the subscription, which begins after the Joining Location. Which publisher a FETCH should go to where several publish a track is not decided. Seen in a test of the relay core (a source with the largest Location {5, 2} is asked for {9, 0} to {9, 1}); not run against real publishers.
- **The Rust client answers a Joining FETCH that is read before its SUBSCRIBE with `NOT_SUPPORTED`.** Its session takes such a FETCH now (row on a Joining FETCH that names a Request ID the peer has not used yet), and the client, which answers no FETCH, refuses it like any other. `@xmoq/moqt` refuses it with the same code by itself.
- **A Joining FETCH for a SUBSCRIBE with Forward State 0 that the relay has not answered is held, and refused when the SUBSCRIBE is accepted (§10.12.2).** The Forward State is in the SUBSCRIBE, so `INVALID_RANGE` could be said at once; the relay says it where it works the range out.
- **The publisher does not learn the priority of the relay's FETCH.** The relay's FETCH names no SUBSCRIBER_PRIORITY (row on the parameters of the relay's FETCH), and a REQUEST_UPDATE for a FETCH is answered by the relay and moves only the fetch stream to the subscriber (row on the priority of a FETCH). Where the publisher's link to the relay is the narrow one, the publisher orders the relay's fetch streams by its own defaults.
- **Messages the relay does not implement (§4, MUST: "Relays MUST implement all MOQT messages defined in this document, as well as processing rules described in Section 9").** SUBSCRIBE_TRACKS and datagrams are refused or not read, as the rows at the top say, TRACK_STATUS is answered (row on TRACK_STATUS in the relay's table), SUBSCRIBE_NAMESPACE is served (row on it in the relay's table) without a REQUEST_UPDATE of it, and GOAWAY is taken from a client, and sent when the relay is told to stop (rows on GOAWAY); REQUEST_UPDATE is applied for one parameter of a subscription, passes a NEW_GROUP_REQUEST on, and is refused for the others (the gap on REQUEST_UPDATE above).
- **Authorization (§9.4, §9.5).** Off unless the relay is given a key (row on the relay's authorization); without one nothing is checked. A publisher's `UNAUTHORIZED`, `MALFORMED_AUTH_TOKEN` or `EXPIRED_AUTH_TOKEN` to the relay's SUBSCRIBE reaches the subscribers as it is, although it is about a token the subscriber did not send there and cannot mend. The relay copies nothing of a subscriber's SUBSCRIBE into the SUBSCRIBE it sends a publisher, so a publisher behind the relay does not see a subscriber's AUTHORIZATION_TOKEN. Any session can announce any namespace, the one with no fields included (§2.4.1 allows "between 0 and 32 Track Namespace Fields"), which matches every track: whoever announces it first gets the SUBSCRIBE for every track that nobody has published. With several sources of a track, any session can also become a source of any track that has one, by sending PUBLISH for it, and then: end the track for every subscriber by sending something that breaks the object model (§2.4.2 has the relay end the subscriptions with `MALFORMED_TRACK`, and the other sources are cancelled with it), for which one subgroup stream with another Publisher Priority than the Subgroup had is enough; take a Subgroup from the other sources by sending it first; keep the other sources from being heard, by sending one stream with a Group ID far ahead of theirs, after which their Groups count as too old and their streams are stopped; make the relay forget which stream it took a Subgroup from, by sending more Subgroups than it remembers, after which the same Subgroup can reach the subscribers on two streams (§2.2); raise the largest Location of the track, with the LARGEST_OBJECT parameter of its PUBLISH or with an Object on a stream that is passed on, so that a subscriber that comes gets a LARGEST_OBJECT the other publishers never sent; and send so many streams that a subscriber runs into the limit of what waits to be written and loses its subscription. The newest Group of a track is kept for the track and not for each source, on purpose: a share for each source needs to know who a source is. Any session can also ask any publisher for a FETCH of any track, and hold every FETCH that publisher is asked for (item on one subscriber that keeps every other from fetching).
- **Nothing bounds how many requests of `@xmoq/moqt` wait for a stream at once, nor what is kept for a stream that is being opened.** Each waits 10 seconds at most (row "A request that waits for a stream"), and the caller is what keeps their number down: every request is a call of the application.
- **A write on a stream of `@xmoq/moqt` that could not be opened closes the session, where the failure to open it did not.** The session of the library has forgotten the stream by then in every path it has (a request is cancelled, a Subgroup is told to be not opened), so no such write is made; a caller of the stream layer alone could make one.

## Relay

Choices of the relay where the draft leaves one. The limits are **provisional**, but for those marked as decided. Why each value is what it is, and the draft's words for it, are at the constant or the function a row names; a row says only what the code does not.

## Encodings the draft does not give

- `RENDEZVOUS_TIMEOUT` (`0x04`) and `FILL_TIMEOUT` (`0x0A`): the value is a variable-length integer in milliseconds. The draft (§10.2.5, §10.2.6) gives no encoding. This follows `moqtail` 0.15.0, read in `libs/moqtail-rs/src/model/parameter/message_parameter.rs` at tag `relay@0.15.0` on 2026-10-10 (lines 510–515 build the pair, line 733 writes it; only FORWARD, SUBSCRIBER_PRIORITY and GROUP_ORDER are written as one fixed byte). The basis is source reading only: no captured bytes carry these parameters.

## Other observations about the draft

- The variable-length integer of draft 18 is not the QUIC (RFC 9000) varint: the number of leading one bits gives the length, up to 9 bytes.
- **A browser page that is closed without `close()` ends differently at the relay by browser** (observed, [record of browser support](experiments/2026-10-10-browser-support-webtransport-webcodecs.md)). With Chromium 156 the relay sees the session end first (`ClosedByPeer { code: 0 }`). With the Firefox 157.0 build of Playwright it sees the page's control stream end first, and closes the session itself with `PROTOCOL_VIOLATION` ("the peer closed its control stream"), which is what §3.3 asks for: "A control stream MUST NOT be closed at the underlying transport layer during the session's lifetime. Doing so results in the session being closed as a PROTOCOL_VIOLATION." The subscribers of a track that page published get the same in both cases, PUBLISH_DONE `TRACK_ENDED` with the Stream Count, and the other sessions go on. The relay has a wait of 200 milliseconds for the like case of a STOP_SENDING on its own control stream (row in the relay's table) and none for this one. Nothing was changed.
- The second example in §11.6 does not add up (a 14-byte value under `Length = 21`). It is not used as a test fixture.
- **§10.2.2 has a message rejected with a code that only ends sessions.** "The receiver of a message referencing an Alias that is not currently registered MUST reject the message with UNKNOWN_AUTH_TOKEN_ALIAS" (lines 3163 to 3165 of the text), where the sentences around it have "close the Session with". The code of that name is among the Session Termination Error Codes (§3.5, 0x17; lines 1744 and 6818) and not among the codes of REQUEST_ERROR (§10.6, the table from line 6838), which has UNAUTHORIZED, MALFORMED_AUTH_TOKEN and EXPIRED_AUTH_TOKEN. **XmoQ closes the session with 0x17**: the one code of that name there is, which a peer can read.
- **§12.9 calls malformed what §2.1 and §9.1 allow.** §2.1 has of an Object that is known to exist "From this state, it can transition to not existing, but not vice versa", and §9.1 lists among the fields of a cached Object that can be updated "Object can transition from existing to not existing in cases where the object is no longer available". §12.9 has "A Track is considered malformed ... if ... An endpoint receives an Object with a Prior Object ID Gap covering an Object it previously received", which is such a transition, said with the property. XmoQ follows each where it applies: the gap is malformed, a status in the place of an Object is not (row on an Object that comes again).
- **§2.1 says "not malformed" where §2.4.2 and §12.9 say malformed.** §2.1: "an endpoint can receive an Object after it has already recorded that the Object does not exist (e.g., via a FETCH gap from one source and later delivery via a subscription). This is not a protocol error and the Track is not malformed", with no condition. §2.4.2 has as an example of a malformed track "An Object is received in a Group whose Object ID is larger than the final Object in the Group", and §12.9 "An endpoint receives an Object with an Object ID within a previously communicated gap": both are Objects that come where the endpoint recorded that none exists. Where XmoQ puts the border is in the row on an Object that comes again.
- **Prior Object ID Gap has a type from the range §2.5 leaves to applications.** §2.5 has "Certain Property type ranges are reserved for application-specific use and will never be allocated by IANA in future MOQT specifications: 0x38 to 0x3F (1-byte encoding)", and §12 "Property types in ranges reserved for application-specific use (0x38-0x3F, 0x3800-0x3FFF) are not defined by MOQT". §12.9 defines Prior Object ID Gap with the type 0x3E, and §12.8 Prior Group ID Gap with 0x3C; the table of Properties among the IANA considerations lists both. XmoQ reads 0x3E as §12.9 has it, so an application that uses 0x3E for something of its own makes its track malformed or leaves holes in what the relay's cache answers.
- `moqtail` 0.15.0 clients omit `MOQT_IMPLEMENTATION` in SETUP (§10.3.1.5 is a SHOULD); its relay sends it. The relay's control-message log prints the raw bytes received and sent, checked in `libs/moqtail-rs/src/transport/control_stream_handler.rs` at tag `relay@0.15.0` on 2026-10-10.
- **`moqtail` 0.15.0 keeps the prior Group ID and Object ID of the last Object after an End of Range indicator on a fetch stream**, where §11.4.4.2 has those of the indicator (row above). Read in the crate `moqtail` 0.15.0, `src/model/data/fetch_object.rs` on 2026-10-11 ("Returns None for EndOfRange markers — they MUST NOT update prior state"). For the same reason it takes an Object that follows an indicator, with no Object before, for the first of the stream: its Group ID and Object ID have to be there and are absolute (lines 166 to 186 of that file), which is the reading of §11.4.4.1 the row on the first Object does not follow. An Object that follows an indicator and leaves out its Group ID or Object ID is read as another Object by the two. Not run: no stream with an indicator was obtained.
- **`moqtail` 0.15.0 has a third Group Order, `Original` = 0x0** (`src/model/control/constant.rs`, read on 2026-10-11), and reads a GROUP_ORDER of 0 as it. §10.2.8 has "Ascending (0x1) or Descending (0x2)" and for any other value a `PROTOCOL_VIOLATION`. XmoQ closes the session for 0.
- **The `moqtail` relay 0.15.0 refuses a Relative Joining FETCH whose Joining Start is larger than the Group of the Joining Location** (its log: "Joining fetch start location is larger than the track's largest location", seen on 2026-10-24 with the terminal viewer's FETCH for the 16 latest lines of a room of 1 or 2). §10.12.2.1 has the Start Location "{Joining Location.Group - Joining Start, 0}" and does not say what it is when that cannot be subtracted; the own relay starts at Group 0 (row on a Joining FETCH in the relay).
