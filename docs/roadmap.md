A Phase keeps its number, and a new one is added at the end: the records in [experiments](experiments/README.md) name the Phase they were for by its number, and their index files them by it.

## Phase 0b — Own MoQ Transport implementation (draft 18)

Each step replaces one `moqtail` component with an own one, so that one side of every run is a known-good peer.

- [x] Rust wire codec and session for SETUP, PUBLISH_NAMESPACE, PUBLISH, SUBSCRIBE and subgroup streams, with byte fixtures captured from `moqtail`. The session covers the side that opens requests; answering a peer's requests comes with the relay. See [`fixtures/moqt-18/`](../fixtures/moqt-18/README.md).
- [x] Own Rust client against the `moqtail` relay and the `moqtail` browser client. See the [record](experiments/2026-10-10-own-rust-client-vs-moqtail.md).
- [x] Own Rust relay against the `moqtail` browser client and the own Rust client. See the [record](experiments/2026-10-10-own-relay-vs-moqtail-peers.md). The relay of that run was the minimal one: no cache, WebTransport only, no authorization. What the draft requires of a relay and is not implemented is listed in [implementation notes](moqt-implementation-notes.md).
- [x] Own TypeScript browser client against the `moqtail` relay. See the [record](experiments/2026-10-10-own-ts-client-vs-moqtail.md). Done ahead of the relay, because it needs only `moqtail` peers.
- [x] Own TypeScript browser client against the own relay. It runs in the interop matrix below; neither side needed a change.
- [x] One interop runner for every pairing (`interop/`), including the own Rust client, and a CI job that runs it. See the [record](experiments/2026-10-10-own-rust-and-ts-through-moqtail-relay.md). Every pairing runs through the `moqtail` relay and through the own relay, with one-to-many pairings on the own relay.
- [x] Route by namespace in the relay: a SUBSCRIBE for a track that was announced with PUBLISH_NAMESPACE and not yet published (§9.5 of the draft, a MUST for relays). The relay sends its own SUBSCRIBE to the publisher whose matching namespace was announced first. See the [record](experiments/2026-10-10-relay-namespace-routing.md).
- [x] Several publishers of one track in the relay, before Phase 1: send the SUBSCRIBE to every matching publisher, take and deduplicate the Objects of one track from several of them, and subscribe to a publisher that announces a namespace later (§9.3 and §9.5 of the draft, MUSTs for relays). See the records on [a second publisher](experiments/2026-10-10-relay-several-publish-sources.md), on [asking every publisher](experiments/2026-10-11-relay-ask-every-publisher.md) and on [a Subgroup that comes with two priorities](experiments/2026-10-11-relay-subgroup-priority-mismatch.md), and the pairings with two publishers in the [interop matrix](experiments/2026-10-10-two-publishers-in-the-interop-matrix.md). The MUSTs are met in part: what is left short of them, and why, is listed under "Several publishers of one track" and "Sources of a track that do not send the same thing" in the [implementation notes](moqt-implementation-notes.md). Duplicates are removed by Subgroup, not by Object, and of what two sources send only the Publisher Priority is compared.
- [x] Put the runs in which a publisher or a subscriber disconnects mid-transfer into the interop matrix, so that CI runs them. See the [record](experiments/2026-10-10-disconnects-through-own-relay.md). The defect of `@xmoq/moqt` these runs found, a browser client that could neither cancel nor reset, is fixed; see the [record](experiments/2026-10-10-webtransport-error-in-chromium.md).

**Exit:** one Object between browser and Rust through the own relay with own clients, and the same Object exchange against `moqtail` peers. Reached on 2026-10-10. The item on several publishers was not part of the exit and was closed on 2026-10-11.

## Phase 1 — Video

The browser Phase 1 is built for and judged in is Chromium (Chrome, Edge) on desktop; decided on 2026-10-10. WHY NOT Firefox as well: its Playwright build connected to the own relay and exchanged video with Chromium in every codec tried, but one build on one machine is all that was measured, and a second engine doubles what each step of Phase 1 has to be checked in. WHY NOT Safari: nothing could be run in it ([record of browser support](experiments/2026-10-10-browser-support-webtransport-webcodecs.md)). Which browsers are supported beyond Phase 1 stays an [open decision](open-questions.md).

Media is packaged as LOC says and tracks are described by an MSF catalog, in full; decided on 2026-10-10 (`draft-ietf-moq-msf-01`; of LOC the numbers of `draft-ietf-moq-loc-04` on draft 18, decided on 2026-10-11, with the reasons in [`packages/loc/README.md`](../packages/loc/README.md); a Group of video goes onto one stream, decided the same day, with the reasons at `DEFAULT_MAPPING` in `@xmoq/media`; a catalog names H.264 `avc3`). That puts FETCH into Phase 1: MSF has "Subscribers accessing the catalog MUST use SUBSCRIBE with a Joining FETCH (offset = 0)", and the own implementation has no FETCH. It settles how Groups are numbered: a publisher that restarts "MUST ensure the new starting Group ID is greater than any previously published Group ID for that track" (MSF §6.1), for which MSF suggests the wall clock time. WHY NOT only the shape of LOC and MSF with a fixed track name and no catalog: it would start sooner, and would leave the players of other MoQ implementations unable to find the tracks. What following these drafts takes, and which peers speak them, is in the [survey](experiments/2026-10-10-loc-msf-fetch-survey.md). It left open whether every Object goes onto a stream of its own, which MSF §6 asks for and the nearest peer does not do; a Group goes onto one stream, decided on 2026-10-11 (`DEFAULT_MAPPING` in `@xmoq/media`).

The video codec is H.264, in Annex B format; decided on 2026-10-11. WHY H.264: in Chromium it is the one codec with a hardware encoder, which took about a tenth of the CPU time of the software encoders at 1280x720 and 30 frames a second (4% of a core, against 33% for VP8, 54% for VP9, 55% for AV1 and 71% for H.264 in software), and where no hardware decoder is used it was the cheapest to decode ([record of browser support](experiments/2026-10-10-browser-support-webtransport-webcodecs.md)). WHY Annex B and not `avc` with a `description`: every key chunk carries the parameter sets, so a viewer that joins late decodes from the next key frame with the codec string alone, where WebCodecs emits the `description` once ([WebCodecs loopback record](experiments/2026-10-10-webcodecs-loopback.md)). WHY NOT VP9: it has no choice of format to get wrong and its decoder reports a missing frame, which H.264 decoders do not (they show corrupt pictures without an error); it costs over ten times the CPU time to encode. What the decision rests on is one Mac, a generated picture and CPU time, not power or picture quality. One thing is not settled by it: in one run of the shipped Chrome 155 the hardware encoder's queue reached 91 frames, about three seconds of picture, and whether it keeps up in real time was not looked at further. That is to be measured when the publisher exists.

The relay gets a cache of the latest Group of each track in Phase 1; decided on 2026-10-11. Neither draft 18 nor MSF asks for one (§9.1: "Relays MAY cache Objects, but are not required to"), and the relay answers a FETCH without it, by sending a FETCH of its own to one publisher ([implementation notes](moqt-implementation-notes.md)). WHY a cache all the same: what building that relay showed it cannot do. A browser publisher has to answer every FETCH itself, and once it is gone nobody can get the catalog. A FETCH with FILL_TIMEOUT 0, which asks for what the relay holds, gets nothing. The relay cannot keep the end of a Joining FETCH and the start of the subscription from overlapping, since the publisher answers the one and the relay said where the other begins. With several publishers of a track a gap can open between the two: the relay tells a subscriber the largest Location of all of them and fetches from the first one only. WHY the latest Group and not more: it is what a Joining FETCH with offset 0 asks for, the form MSF has a subscriber get the catalog with, and one of the ways a viewer that joins late can get its first picture; a FETCH for older Groups still goes to the publisher. WHY NOT leave it for later: the browser publisher would be built to answer FETCHes that a cache then takes from it, and the gaps above would be in the first demo. The publisher still answers a FETCH the cache cannot. How much it holds is provisional (`crates/relay-core/src/cache.rs`).

- [x] FETCH and Joining FETCH in the Rust and the TypeScript session, against peers: `moqlivemock` and the `moqtail` relay, from the [Rust client](experiments/2026-10-11-rust-client-fetch.md) and from [a page](experiments/2026-10-11-fetch-from-a-page.md), in the interop run.
- [x] The relay answers a FETCH, from the publisher or from a cache. A Standalone FETCH is passed on to one publisher ([record](experiments/2026-10-11-standalone-fetch-through-own-relay.md)), and a Joining FETCH as a range the relay works out ([record](experiments/2026-10-11-joining-fetch-through-own-relay.md)). From the cache: the item below.
- [x] The relay keeps the latest Group of each track and answers a FETCH from it where it can. Done for a FETCH whose range lies in that Group while the track has a publisher ([record](experiments/2026-10-11-the-relay-answers-a-fetch-from-its-cache.md), and the row on the relay's cache in the [implementation notes](moqt-implementation-notes.md)). The interop matrix has a page read a Group in two Subgroups from it, and a page cancel a Group of 7 MB that the relay then stops writing ([record](experiments/2026-10-11-fetch-runs-with-the-relays-cache.md)). An Object that comes again is compared with what the cache holds, and a track or a Group that contradicts itself is ended or given up ([record](experiments/2026-10-11-the-relay-compares-an-object-that-comes-again.md)). Not built: a FETCH with FILL_TIMEOUT 0, and keeping the Group for 30 seconds after the last publisher has gone, which was decided and then left out because no client here could read anything with it (`crates/relay-core/src/cache.rs`).
- [x] MSF catalog track: published by the browser publisher, read by the viewers. `@xmoq/msf` reads and writes the catalog, follows a catalog track and publishes one; a page's catalog is read through the own relay by another page and by `moqlivemock`'s subscriber, and a page reads the catalog of `moqlivemock`'s publisher ([reading](experiments/2026-10-11-a-page-reads-a-catalog.md), [publishing](experiments/2026-10-11-a-page-publishes-a-catalog.md)). What is short of the draft is in [`packages/msf/README.md`](../packages/msf/README.md): delta updates are not applied, GZIP is not read, and a catalog cannot be had once its publisher is gone, as the relay keeps a Group only while its track has a publisher.
- [x] Browser WebCodecs publisher. `createVideoTrackEncoder` of `@xmoq/media` encodes H.264 in Annex B and publishes it as a LOC track; a page's video is played by another page through the own relay and through the `moqtail` relay, in both mappings, with what each frame shows read from its pixels, and with Groups of several MiB ([record](experiments/2026-10-11-pages-send-and-play-video.md)). A key frame of more than 1,000,000 bytes is not sent; the caller is told at the third in a row (`onKeyChunksNotSent`), and nothing makes the frames smaller ([`packages/media/README.md`](../packages/media/README.md)).
- [x] Rust relay fan-out to browser viewers. In the demo (`mise run demo`) two viewers played one publisher in a headless Chromium, the second coming three seconds later and beginning at the next key frame, and a person watched one publisher with one viewer in Chromium. With viewers of the Rust client, a small picture reached 1,000 of them with every frame, and 1280x720 fell behind from 500, on one Mac ([record](experiments/2026-10-11-one-video-track-to-many-viewers.md)); on Linux 1280x720 reached 1,000 with every frame ([record](experiments/2026-10-24-one-video-track-to-many-viewers-on-linux.md)). Several browser viewers are not in the interop run.
- [x] Decode and render video. `playVideoTrack` of `@xmoq/media` decodes and hands each `VideoFrame` to its caller; the demo's page draws them on a canvas after a buffer for playback (150 ms unless told otherwise, decided on 2026-10-21; 50 ms before), which a person saw play smoothly ([delay](experiments/2026-10-11-where-the-delay-of-the-demo-comes-from.md), [a tab in the background](experiments/2026-10-11-demo-in-a-background-tab.md)). The drawing and the buffer are in `demo/`, not in a package.
- [x] Test late join, keyframes, reconnect, cancellation and slow subscribers. Done: a viewer that comes late begins at the next key frame or with a Joining FETCH of the latest Group; the interop run has publishers and subscribers that are killed, cancel or do not read ([record](experiments/2026-10-10-disconnects-through-own-relay.md)); a subscriber is told when its publisher leaves ([record](experiments/2026-10-11-a-publisher-leaves-and-the-subscriber-is-told.md)); the demo's pages connect again after a break of 8 seconds ([record](experiments/2026-10-11-demo-over-a-lossy-link.md)). The reconnect is in `@xmoq/media` (`keepPublishing`, `keepPlaying`) and in the interop run, where the relay is stopped and started anew ([record](experiments/2026-10-12-pages-connect-again-when-the-relay-comes-back.md)). Left open: what a viewer does with a chunk that is missing is undecided.

**Exit:** reproducible one-publisher/multiple-viewer video demo, on loopback. Reached on 2026-10-11 with `mise run demo`. A run over real links waits for the hosting decision.

## Phase 2 — Audio and quality
- [x] Build the audio pipeline. The codec is Opus, decided on 2026-10-10: it is the one audio codec Chromium, Firefox and Safari all encode and decode ([record of browser support](experiments/2026-10-10-browser-support-webtransport-webcodecs.md)). Audio was kept out of Phase 1. WHY NOT earlier: a second track brings the question of what a slow viewer's limit is counted by into Phase 1, where one video track does not raise it. Built in its smallest form: `createAudioTrackEncoder` and `playAudioTrack` of `@xmoq/media`, Opus at 48,000 Hz, mono, page to page through the own relay ([record](experiments/2026-10-11-opus-audio-page-to-page.md)) and in the demo, where a person heard it, with crackles. The seams that crackled were mended afterwards, and the person found the sound smooth on 2026-10-12. No unit test, and no `description` is sent.
- [x] Add playback buffers and A/V synchronization. In `@xmoq/media` (`createPlayout`, with the demo's values): picture and sound are played by one clock after one buffer (0, 50, 150 ms or one that follows the link; 150 by default since 2026-10-21, 50 before), and the page shows where the delay comes from ([sync](experiments/2026-10-11-demo-sync-and-delay.md), [delay](experiments/2026-10-11-where-the-delay-of-the-demo-comes-from.md)). `playAudioTrack` can hold a piece of sound for the ones before it (`holdForOrderMs`). Left open: video does not wait for a Group that is late (tried and not taken, [record](experiments/2026-10-12-a-later-group-of-video-waits-for-the-one-before-it.md)), every value is provisional and from one machine, and nobody judged the sync by eye and ear.
- [x] Measure latency, drops, stalls and recovery under loss. Measured on one machine through a proxy that delays, drops and limits, and gathered in [the A/V demo and its limits](av-demo.md): the delay on loopback is the buffer; with delay and loss the relay's congestion control decides (Cubic falls behind, BBR does not); on a link with less room than the video it is the other way round, and what helps there is leaving frames out (the relay's `--delivery-patience-ms`, an experiment) or a smaller version of the video (`?ladder=1` and `?abr=1`, a trial); a viewer that comes late and a session that ends are measured as well. **Left open, and not measurable on one machine**: what a viewer's path is like, two machines, a real network; and whether the relay gives Groups up and whether a publisher offers several versions.

**Exit:** documented A/V demo and limitations. Reached on 2026-10-12 with [the A/V demo and its limits](av-demo.md), for one machine: a person watched it and found the sound smooth on 2026-10-12, and a run over real links waits for the hosting decision, as in Phase 1.

**After the exit, on the same demo and still one machine** (2026-10-12 and 13; none of it is a roadmap item of its own, and each is a first version behind what its record says is missing):

- The watching page asks the relay to give late video up (a delivery timeout of 150 ms by default, decided on 2026-10-21), and can change it while it plays ([timeout](experiments/2026-10-12-which-delivery-timeout-a-viewer-asks-for-on-its-video.md), [update](experiments/2026-10-12-a-viewer-changes-its-delivery-timeout-with-request-update.md)).
- Two versions of the video and a viewer that changes between them, a trial behind flags ([try first](experiments/2026-10-12-a-try-before-going-up-that-comes-again-as-soon.md)).
- The relay sends by priority; the sound on a narrow link is late by the link's queue all the same, and the buffer of 50 ms, the default then, is too short for it there; the default is 150 ms since 2026-10-21 ([record](experiments/2026-10-13-the-sound-behind-the-video-on-a-narrow-link-and-priorities.md)).
- A viewer can come before the publisher ([relay](experiments/2026-10-13-a-viewer-that-comes-before-the-broadcast.md), [page](experiments/2026-10-13-a-page-that-waits-for-the-broadcast-at-the-relay.md)).

## Phase 3 — Ghostty CLI
- [x] Rust MoQ subscriber. The Rust client subscribes to a LOC video track and writes its frames as an H.264 byte stream that `ffprobe` reads, from `mlmpub` directly and from a page that encodes video, through the own relay ([record](experiments/2026-10-11-rust-subscriber-writes-loc-video-as-annex-b.md)). - [x] Video decoding and Kitty Graphics experiment. Spikes decode the client's byte stream with the `openh264` crate and write the frames as Kitty graphics, 100 of 100 frames of a page's video ([record](experiments/2026-10-11-video-in-a-terminal-with-kitty-graphics.md)). - [ ] Native audio output and terminal controls. Done so far: `spikes/terminal-player/play.sh` plays picture and sound with one command, the sound through ffmpeg's `audiotoolbox`, on macOS alone and at volume 0 in the run ([record](experiments/2026-10-11-a-broadcast-in-a-terminal-picture-and-sound.md)). - [ ] Measure FPS, CPU and memory. Done so far, with the picture written to /dev/null: 30 frames a second at 360, 720 and 1080 lines, 16%, 25% and 36% of a core, 28 to 74 MB ([record](experiments/2026-10-12-the-terminal-viewer-at-720p-and-1080p.md)). Open: what a terminal that draws the picture adds, and how many frames a second it shows.

**Exit:** reproducible terminal demo with compatibility notes.
