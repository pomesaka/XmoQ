# moq-dev: one MoQ object between Chromium and Rust

- Date: 2026-10-10
- Commit SHA: uncommitted working copy on top of `af05a7d9b8759afa8e92d64527ddcf2b2f187e21`
- Roadmap item: Phase 0, "Establish browser ↔ Rust WebTransport/MoQ connectivity" and "Transfer one MoQ Object and document reproducible commands"

## Objective

Send one object through a local `moq-relay` between a real Chromium and a Rust client built on `moq-net`, and check that the received bytes equal the sent bytes. Do it first with the library default (moq-lite-06), then with relay and both clients pinned to an IETF MOQT version.

## Environment

| Item | Value |
|---|---|
| OS | macOS 14.4, arm64 |
| Browser | Chromium 151.0.7922.34 ("Google Chrome for Testing"), headless, driven by `playwright-core` 1.64.0 |
| Rust toolchain | rustc 1.92.0 |
| Relay | `moq-relay` 0.17.2, prebuilt `aarch64-apple-darwin` release binary, SHA-256 `bace64f7…a8cca4ca` checked |
| Rust client | `moq-net` 0.3.10, `moq-tokio` 0.19.23 (pulls `web-transport-moq` 1.3.4) |
| Browser library | `@moq/net` 0.4.2, bundled with Bun 1.3.12 |
| Transport | WebTransport over QUIC on `127.0.0.1:4443`. WebSocket fallback disabled on both clients |
| Certificate | Self-signed, generated by the relay at start. Both clients fetch its SHA-256 from `http://127.0.0.1:4443/certificate.sha256` and pin it. No browser flag, no root CA |
| Auth | Anonymous, `--auth-public "**"` |

The certificate, auth and logging settings are provisional and exist only for this run.

`moq-relay` 0.17.2 declares `rust-version = 1.95`, so it was not built from source. Nothing was installed system-wide.

## Commands

From `spikes/moq-dev/`. `CHROMIUM_PATH` pointed at the Chromium binary above.

```bash
bash scripts/fetch-relay.sh
cargo build --manifest-path rust-client/Cargo.toml
bun install --cwd web

# Default offer
bash scripts/relay.sh
bash scripts/transfer.sh b2r lite-default-b2r
bash scripts/transfer.sh r2b lite-default-r2b
bash scripts/transfer.sh b2b lite-default-b2b

# Pinned to moqt-22
bash scripts/relay.sh moq-transport-22
bash scripts/transfer.sh b2r ietf22-b2r moq-transport-22     # repeated, see below
bash scripts/transfer.sh r2b ietf22-r2b moq-transport-22
bash scripts/transfer.sh b2b ietf22-b2b moq-transport-22

# Repeats, one relay per version
bash scripts/matrix.sh 4 moq-lite-06 moq-transport-20 moq-transport-18 moq-transport-16
TAG=live LIVE_INTERVAL_MS=500 bash scripts/matrix.sh 4 moq-lite-06 moq-transport-22
```

`b2r` = browser publishes, Rust subscribes. `r2b` = the reverse. `b2b` = browser to browser. Each run uses a fresh random payload and passes only when the subscriber reports the same string.

## Observed results

### moq-lite-06

With no version given, every session negotiated `moq-lite-06`. The relay log shows the browser's CONNECT offering `moq-lite-06 … moqt-15` and the relay answering `protocol: Some("moq-lite-06")`, `transport=quic`.

```text
[console.log] [spike] published payload="xmoq-lite-default-b2r-561118313"
INFO moq_tokio::client: connected version=moq-lite-06
RECEIVED payload="xmoq-lite-default-b2r-561118313"
MATCH
```

### IETF MOQT, pinned

Pinning works in all three places: `--listen-version` on the relay, `--connect-version` on the Rust client, `webtransport: { protocols: [...] }` in `@moq/net`. The relay logs `negotiated version=moq-transport-22 transport=quic` for browser and Rust sessions alike.

```text
[console.log] [spike] connecting relay=http://127.0.0.1:4443/spike protocols=moqt-22
INFO moq_tokio::client: connected version=moq-transport-22
RECEIVED payload="xmoq-ietf22-b2r-1048320602"
MATCH
```

### Browser-to-browser late join fails

In a failed b2b run the subscriber connects, sees the announcement and gets `subscribe ok`, then no group arrives before the 12 s timeout. For `moqt-22` the relay log shows the difference from a passing run in the browser publisher's answer:

```text
# fail
received subscribe ok SubscribeOk { …, largest: None, … }
# pass
received subscribe ok SubscribeOk { …, largest: Some(Location { group: 0, object: 0 }), … }
serving group subscribe=2 track=object sequence=0
```

The browser subscriber sends `filter: Relative(1), fill: None`; the Rust subscriber sends `filter: NextObject, fill: Some(Relative(1))`. The Rust publisher serves both. On `moqt-22` the browser publisher served the Rust form in every run and the browser form in 2 of 10. The failures on moq-lite and on drafts 20, 18 and 16 show the same symptom on the subscriber side; their relay logs were not analysed.

### `moqt-22` here is not draft-22 on the wire

`draft-ietf-moq-transport-22` section 9.20.9 defines `LOCATION_FILTER` with a leading `Location Filter Type`, and Appendix A.1 lists this as the change since draft-21. The pinned libraries do not implement it:

- `@moq/net` 0.4.2 `ietf/filter.js` encodes drafts 20, 21 and 22 identically (`isDraft20`), with no type field. `ietf/version.js` calls draft 22 "unpublished, wire-identical to draft-21".
- `moq-net` 0.3.10 `src/ietf/version.rs` says "Draft-21 and draft-22 are editorial" and tests that both encode like draft-20.

So the `moqt-22` runs above negotiated the draft-22 ALPN and exchanged the draft-20/21 `LOCATION_FILTER`. The two sides agree with each other, which is why the transfer works. `moq-dev/moq` `main` already carries a Rust test for the draft-22 form; it is not in the released crate.

### Other observations

- With `http://localhost:4443`, the Rust client dialled `[::1]:4443` first, the relay was bound to `127.0.0.1` only, and after 200 ms the client connected over the WebSocket fallback instead. It logged `using WebSocket fallback` at WARN and still reported `connected version=moq-lite-06`. All recorded runs use `127.0.0.1` and disable the fallback.
- Starting a relay immediately after killing the previous one failed with `failed to bind UDP socket: Address already in use`. `matrix.sh` waits 2 s.

## Limitations and blockers

- No blocker for Phase 0: an object crosses browser ↔ relay ↔ Rust in both directions on moq-lite-06 and on IETF ALPNs 16, 18, 20 and 22.
- A browser subscriber that joins late does not reliably get an already-closed group from a browser publisher. This affects any browser-to-browser path that depends on the latest group being replayed, for example a viewer joining between keyframes.
- True draft-22 wire compatibility is not available at these versions. The newest draft whose wire format this pair actually implements is draft 21, which the draft's own changelog describes as editorial relative to draft 20. Draft 21 itself was not run.
- Chromium only. One machine, loopback only, no packet loss.
- Not run: drafts 14, 15, 17, 19, 21; moq-lite 01–05; datagrams; FETCH; any peer that is not moq-dev.
- The relay TOML config form was not exercised; the relay was configured by flags.
- Small sample sizes. The b2b rates are indications, not measurements.

## Open questions raised

- Is the browser-to-browser late-join failure a defect in `@moq/net` 0.4.2, or a consequence of how the spike publishes (one closed group, track left open, subscriber with default options)? It needs a minimal reproduction against `moq-dev/moq` `main` and possibly an upstream issue.
- Does XmoQ rely on late joiners receiving the current group from the relay cache? Phase 1 lists late join and keyframes as test items.
- If the wire must be IETF MOQT, which draft is the target? `moqt-22` on this pair is not interoperable with a conformant draft-22 peer for filtered `SUBSCRIBE`. The parallel moqtail spike validated draft 18.
- Should clients keep the WebSocket fallback? It hid a QUIC connectivity failure in this run.
