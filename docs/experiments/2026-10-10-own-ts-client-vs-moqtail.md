# Own TypeScript MOQT client against moqtail peers (draft 18)

- Date: 2026-10-10
- Commit SHA: the commit that adds `packages/moqt` and `interop/` together with this record. The runs were made on its working copy on top of `b7a5cc4`
- Roadmap item: Phase 0b, "Own TypeScript browser client against the own relay and against the `moqtail` relay". Only the `moqtail` relay half was run; the own relay does not exist in this working copy.

## Objective

Check the own MoQ Transport implementation in TypeScript (`packages/moqt`, `@xmoq/moqt`) against peers it did not write: move one Object through the moqtail relay between the own browser client and a moqtail client, in both directions, in a real Chromium, and compare the received payload with the sent one.

Names used below: the **own browser client** is `interop/page.ts` on `@xmoq/moqt`; the **moqtail Rust client** is `interop/peers/moqtail/rust-client` on the `moqtail` crate; the **moqtail-ts client** is `interop/peers/moqtail/browser/page.ts` on the `moqtail` npm package.

### Bytes compared with moqtail

The moqtail bytes come from the hex the relay logs for every control message. That log is the wire, not a re-encoding: the relay prints what it read from the stream and what it is about to write (`libs/moqtail-rs/src/transport/control_stream_handler.rs` at tag `relay@0.15.0`, lines 84-90 and 175-179, read on 2026-10-10).

- The SUBSCRIBE the own browser client sent in run 2 is byte for byte the SUBSCRIBE the moqtail Rust client sent in [the Phase 0 run](2026-10-10-moqtail-object-transfer.md) (34 bytes, shown there as `Subscribe (34 bytes)`), for the same track and parameters.
- The PUBLISH_NAMESPACE the own browser client sent in run 1 is byte for byte the one the moqtail-ts client sent in the Phase 0 run (18 bytes, shown there as `PublishNamespace (18 bytes)`).
- The PUBLISH the own browser client sent in run 1 (above) and the PUBLISH the moqtail Rust client sent in run 2 differ only in the Request ID. The latter is `1d 00 19 00 02 04 78 6d 6f 71 06 70 68 61 73 65 30 06 6f 62 6a 65 63 74 01 01 10 01` in the relay log of run 2 and is pinned as the fixture "PUBLISH with a 1-byte Track Alias". The own browser client uses Request ID 2 because it sends PUBLISH_NAMESPACE first.
- The relay forwards the SUBGROUP_HEADER Type of the publisher and rewrites the Track Alias. The own browser client therefore decoded three header shapes as a subscriber: `0x5d` from the moqtail Rust client (explicit Subgroup ID, PROPERTIES with length 0), `0x58` from the moqtail-ts client (Subgroup ID mode 0b00) and `0x5c` from itself.

Fourteen byte sequences produced by moqtail are pinned in `packages/moqt/test/core/moqtail-fixtures.test.ts`, each checked in both directions (decode to the expected message, encode back to the same bytes): twelve control messages and two whole subgroup streams. Eight control messages come from the Phase 0 record, the rest from runs of this experiment.

### Draft 18 text against moqtail behaviour

No difference on the wire was found in the messages these runs exercised. What the draft says and what moqtail does, for the points that were looked at:

| Topic | Draft 18 | moqtail 0.15.0 / moqtail-ts 0.13.0 |
|---|---|---|
| MOQT_IMPLEMENTATION in SETUP | "An endpoint SHOULD send" it (§10.3.1.5) | The relay sends it. The moqtail Rust client and the moqtail-ts client send a SETUP with no Setup Options. The own browser client sends `xmoq-moqt/0.0.0` |
| Filter Type 0x2 | "Largest Object" (§5.1.2) | Logged and named `LatestObject`. Same value on the wire |
| Response to PUBLISH | REQUEST_OK, 0x7 (§10.5) | The relay sends 0x7, with FORWARD and GROUP_ORDER, both allowed in PUBLISH_OK |

Points where the draft text itself is inconsistent or silent. They are not moqtail deviations. The choice made is in the code next to each one. The Rust implementation in `crates/` is meant to make the same choices, which are listed for both in [the implementation notes](../moqt-implementation-notes.md); the two were not run against each other here.

| Topic | Text | Choice in `@xmoq/moqt` |
|---|---|---|
| PUBLISH_OK type | Table 5 lists `0x1E PUBLISH_OK (Section 10.5)`; §10.5 defines PUBLISH_OK as a REQUEST_OK (0x7) and gives 0x1E no format | REQUEST_OK is the answer to PUBLISH. A 0x1E message is treated like the other listed types that are not implemented: the session closes with INTERNAL_ERROR |
| Error code for an unknown message type or stream type | §10 and §3.4 say "MUST close the session" without a code | PROTOCOL_VIOLATION |
| Value encoding of RENDEZVOUS_TIMEOUT | §10.2.6 gives a meaning in milliseconds and no encoding, unlike the other parameters | A varint, because moqtail 0.15.0 writes it so (`libs/moqtail-rs/src/model/parameter/message_parameter.rs` at tag `relay@0.15.0`, lines 510-511, read on 2026-10-10). The source is the only evidence: no peer sent this parameter in a run |
| An Object after End of Group or End of Track on the same stream | §2.4.2 (conditions 4 and 5) makes the Track malformed; §11.4.3 calls it "a protocol violation" in passing | Malformed Track, decided at the first byte that follows: the subscription is cancelled and the session stays open |
| One Object that breaks more than one rule | No order is given | The fields are judged in the order they arrive. Properties that make the Track malformed are found before the Object Status, so an Object with such properties and a status other than Normal is a malformed Track, not the PROTOCOL_VIOLATION of §11.2.1.2 |
| Stream Reset Error Code when the subscriber lets go of a stream | §3.3.3 words MALFORMED_TRACK (0x12) for a relay publisher and names no code for a subscriber | MALFORMED_TRACK for a malformed Track, INTERNAL_ERROR (0x0) for a local limit, CANCELLED (0x1) otherwise |
| A gap in the peer's Request IDs | §10.1 asks the receiver to check parity and duplicates only | Never an error |
| A stream that ends inside its stream type; a FETCH_HEADER stream without a FETCH | No rule found | The first is dropped. The second closes the session with INTERNAL_ERROR, as a listed type that is not implemented |
| Second example of §11.6 | `Length = 21` for the 14-byte value `traceID:123456`, and `Properties Length = 33` | Not used as a fixture; the test builds its own bytes for the same structure |

### Other observations

- **STOP_SENDING in Chromium 156.** Against a `wtransport` 0.7.2 server that accepted a bidirectional stream and only stopped the client's send direction (code 7), `writer.closed` rejected at once with `WebTransportError: Received STOP_SENDING` and `source=stream`, a later write rejected with the same error, and a read on the same stream stayed pending. `streamErrorCode` was 0, not the 7 the server sent; why was not looked into. The connection therefore watches `writer.closed` to learn of a STOP_SENDING, and reports the code the browser gives. It acts only on an error whose `source` is `stream`: the end of the session fails every stream as well, and that case was tested with the fake transport only, not in Chromium. The server was a throwaway program and is not in the repository.
- **`controller.error()` drops unread chunks.** Failing a `ReadableStream` discards what its internal queue holds, so a subscription that was cut off lost the Objects its reader had not read yet, the last ones among them. The Objects of a subscription are therefore kept in a list of their own and handed to the stream one per read; the stream fails only after the last of them. Found in review, not in a run.
- **playwright-core 1.64.0 hides a rejection.** `page.evaluate` resolved with `undefined` when the page promise rejected with an `Error` that has a `bigint` own property, which `RequestFailedError` has (`errorCode`). Reproduced in isolation under `bun` 1.3.12; with a `number` property the same call rejects. Before the fix, run 6 went on to send the Object as if `subscribe()` had succeeded. `interop/page.ts` now rethrows plain errors. Whether this happens under Node was not checked.
- `WebTransportOptions` in the DOM library of `typescript` 6.0.3 has no `protocols` and `WebTransport` has no `protocol`. `connect.ts` declares a local interface that extends `WebTransportOptions` for the first and reads the second with `Reflect.get`; no type assertion is used. Chromium 156 reported `moqt-18`.
- The relay sent PUBLISH_DONE (TRACK_ENDED, Stream Count 1, "Publisher disconnected") to the moqtail Rust client of run 1 when the publisher's page closed. The own browser client did not receive a PUBLISH_DONE in any run, because the driver closes the subscriber's page first.
- The relay logs `ERROR ... Failed to accept bi-stream: ApplicationClosed` and `Failed to accept unidirectional stream: ApplicationClosed` when a client closes its session. In every run these lines came after the Object was delivered.

## Limitations and blockers

No blocker for the `moqtail` relay half of the roadmap item.

Implemented in `@xmoq/moqt`: SETUP, PUBLISH_NAMESPACE, PUBLISH, SUBSCRIBE, SUBSCRIBE_OK, REQUEST_OK, REQUEST_ERROR (with Redirect), PUBLISH_DONE, SUBGROUP_HEADER and subgroup Objects, the client side of the session, and a connection on top of `WebTransport`.

Not implemented, on purpose:

- The server role and relay behaviour.
- Requests opened by the peer. Each is answered with REQUEST_ERROR NOT_SUPPORTED after its Request ID is checked (§10.1), so a publisher that only sent PUBLISH_NAMESPACE cannot serve a SUBSCRIBE forwarded by the relay. Only the Message Type and the Request ID are read; the rest of the request is not validated.
- REQUEST_UPDATE. One for a subscription made with PUBLISH is refused with REQUEST_ERROR NOT_SUPPORTED, and the subscription ends with PUBLISH_DONE UPDATE_FAILED, as §10.9.1 requires of a failed update. Its parameters are decoded only to hold them to §10.2.1. Anywhere else it is a PROTOCOL_VIOLATION.
- GOAWAY, FETCH_OK, NAMESPACE, NAMESPACE_DONE and PUBLISH_BLOCKED. On a request stream this endpoint opened and on the control stream, receiving one of these messages closes the session with INTERNAL_ERROR, also where Table 5 does not allow the message on that stream. As the first message of a bidirectional stream the peer opened, each of them is a PROTOCOL_VIOLATION (§3.3). For GOAWAY that turns a legitimate message into the end of the session; the code has a `FIXME:` there.
- Datagrams. They are not read at all, so the MUST of §11 to close the session on an unknown datagram type is not met, and an Object sent in a datagram is lost. The connection has a `FIXME:` there.
- The content of AUTHORIZATION_TOKEN. The parameter is carried as bytes and not decoded, so the MUSTs of §10.2.2 (malformed Token, alias registration and lookup, token cache limit, uniqueness of repeated tokens) are not enforced. Authentication is an open question and was not touched; the code has a `FIXME:` at the parameter.
- FILL_TIMEOUT and TRACK_NAMESPACE_PREFIX, which belong to messages that are not implemented. In any message decoded here they are a PROTOCOL_VIOLATION (§10.2.1).
- Every Property of §12 except the two checks below. Properties are carried as Key-Value-Pairs, and a SUBSCRIBE_OK with any Mandatory Track Property cancels the subscription.
- Malformed Track detection (§2.4.2) beyond what one stream shows: a Mandatory Track Property on an Object, an Object after End of Group or End of Track on the same stream, more than one Prior Group ID Gap or Prior Object ID Gap on an Object, and a gap larger than its Group ID or Object ID (§12.8, §12.9). Conditions that compare Objects across streams or with earlier Objects are not checked.
- Timers inside `src/core`. The connection has two: it closes the session with CONTROL_MESSAGE_TIMEOUT when no SETUP arrives, and it ends a subscription whose PUBLISH_DONE Stream Count is not reached, after a fixed time and not the delivery timeouts §10.11 names. There are no delivery timeouts and no timeout for a request without a response.
- Buffering data that arrives before the peer's SETUP (§3.3 SHOULD). It is processed at once; the reason is in `session.ts`.
- The §10.6.1 rule about a non-zero Connect URI Length, which binds a server that receives a Redirect.
- Delivery of an Object before it is complete: a subscriber gets an Object once all of its payload arrived.
- Reopening a subgroup after a reset; FIRST_OBJECT is always set by the publisher.
- Reopening a subgroup stream the peer stopped. A STOP_SENDING on a subgroup stream resets it (§11.4.3), and a STOP_SENDING on the request stream of an established PUBLISH ends that subscription (§5.1). On any other request stream it only stops this endpoint from sending: the response, PUBLISH_DONE and late Objects are still read.

Not covered by these runs:

- One Object on one subgroup stream per run. Several Objects or Groups, cancellation, PUBLISH_DONE at the own browser client, a Track Alias used again after PUBLISH_DONE, REQUEST_UPDATE, FORWARD 0, slow subscribers and backpressure were exercised only by unit tests, with a transport played by the test. Whether the moqtail relay sends REQUEST_UPDATE to a publisher, or uses a Track Alias again, is not known.
- A subgroup stream that arrives before SUBSCRIBE_OK. The runs always subscribed before the Object was sent.
- Session errors raised by the own browser client against a real peer: every close path is unit tested with bytes, none was triggered against the relay.
- Only headless Chromium 156 on one macOS arm64 host over loopback.

No bytes from another implementation are pinned in this package for the following, so the tests for them use bytes built by hand from the draft and would not catch a misreading made in both directions. The Rust implementation is reported to have captured some of them (LARGEST_OBJECT, Object Properties with content, a second Object); this list is to be redone when the fixtures move to a shared place.

- REQUEST_ERROR with a Redirect, and REQUEST_UPDATE.
- The parameters OBJECT_DELIVERY_TIMEOUT, SUBGROUP_DELIVERY_TIMEOUT, EXPIRES, LARGEST_OBJECT, NEW_GROUP_REQUEST, RENDEZVOUS_TIMEOUT and AUTHORIZATION_TOKEN; Subscription Filters other than Largest Object; GROUP_ORDER Descending; FORWARD 0; Track Properties with content.
- On subgroup streams: SUBGROUP_ID_MODE 0b01, the DEFAULT_PRIORITY bit, Object Properties with content, End of Group and End of Track, and the Object ID Delta of a second Object.

## Provisional settings

Chosen only to make this check run. None is a project decision.

- No authentication or authorization on the relay.
- Self-signed certificate, 13 days, pinned by hash.
- Namespace `xmoq/phase0`, track `object`, Track Alias 1, one Object at group 0 / object 0, subscriber priority 128, Largest Object filter.
- Limits an application can set, with their defaults: 16 MiB per Object payload, 64 KiB per Object Properties block, and 1 MiB held for subgroup streams that precede SUBSCRIBE_OK (each held Object counts its payload, its properties and 64 bytes).
- Limits fixed in the code, with the same numbers as the Rust implementation: 64 Key-Value-Pairs in one list (Setup Options, Track Properties, Object Properties), 64 Message Parameters in one message (repeated authorization tokens included), 64 Track Aliases of ended subscriptions remembered, and 64 unknown Track Aliases for which streams that ended early are counted. Request IDs of the peer are remembered up to 1024 above a gap; beyond that the lowest remembered ones are forgotten and the session goes on.
- The draft sets no maximum for any of these. An Object over a limit ends its stream only, and a control message over one closes the session with INTERNAL_ERROR; this is provisional too.
- Connection defaults: 16 Objects queued per subscription before the connection stops reading its streams, 10 s for the peer's SETUP, 5 s for late streams after PUBLISH_DONE.

## Open questions raised

- Where the byte fixtures live so that the Rust and TypeScript implementations are pinned to the same bytes. They are in the test file for now, marked `FIXME:`.
- What a subscriber should do when the application reads slower than Objects arrive. The connection stops reading the subgroup streams of that subscription and leaves the rest to QUIC flow control; whether to drop, reset or cancel instead is undecided.
- Whether the limits and timeouts above should be configuration, and with which values.
- Whether the browser client has to accept requests from the peer (a SUBSCRIBE forwarded to a namespace publisher) before Phase 1.
