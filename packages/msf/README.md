# @xmoq/msf

The MOQT Streaming Format, written from the text of `draft-ietf-moq-msf-01`. Section numbers below are of that draft.

Status: partly implemented. The catalog (§5) is read and written as bytes, and read over a connection: `followCatalog` was run in Chromium against the publisher of `moqlivemock`. Nothing publishes a catalog yet.

## Scope

Implemented: `readCatalog`, which says what the payload of a catalog Object is, and `encodeCatalog`, which makes the payload of an independent catalog. Both apply the same check.

Implemented as well: reading the catalog track. `followCatalog(connection, { namespace })` subscribes to the track `"catalog"` of the namespace, sends a Joining FETCH with offset 0 once it has the SUBSCRIBE_OK, and gives what is known of the catalog each time that changes, as a `CatalogState`: `current`, the last whole catalog with where it was, and `outdated` when something came after it that could not be used. A state nobody read is replaced by the next, so a slow reader gets the newest and one state is held at most. `joiningFetch` of the result says what became of the FETCH: served, failed, or not sent. `catalogStateAfter` is the rule behind it, without I/O; `namespaceTuple` and `trackNamespaceOf` make the namespace of a track out of the string a catalog has.

Not implemented: publishing the catalog track (next), delta updates (told apart, not applied), compression (§12.1), timelines, encryption, authorization, URLs, log and metrics tracks, tracks the subscriber publishes (`publishTracks`, §5.1.5), initialization data (`initDataList`, §5.1.7; `initRef`), variable substitution (§5.4). LOC, the packaging of the media Objects, is not part of this package.

## Layer rules

`src/core` is JSON and bytes: it uses no I/O and does not import `@xmoq/moqt`. `src/moqt` is the part that uses a `MoqtConnection`, through the public entry of `@xmoq/moqt` alone. The entry `@xmoq/msf/catalog` is `src/core/catalog.ts` by itself, for code that is type-checked without the types of a browser. `tsconfig.core.json` type-checks it without the DOM library, and `noRestrictedImports` in the root `biome.jsonc` keeps the import out. `@xmoq/moqt` does not depend on this package (`scripts/ci/check-layers.sh`).

## How the draft is read

| Point | What is done | From |
|---|---|---|
| The value of `version` | `"draft-01"` is written, and nothing else is read: another value is `unsupported-version` | §5.1.1: "follow the convention of specifying the version as "draft-XX"", and "A subscriber MUST NOT attempt to parse a catalog version which it does not understand." **Every example of a whole catalog in the draft (§5.6; the two of a delta update, §5.6.4 and §5.6.5, have no version) has `"version": "1"`**, which is not read. Provisional |
| A field with "Required: Yes" that is missing or of another JSON type (`version`, `tracks`, and `name`, `packaging`, `isLive` of a track) | The catalog is `invalid` | §5: "At a minimum, a catalog MUST provide all mandatory fields." The examples are "non-normative" (§5.6) and are not followed where they differ: the timeline tracks of §5.6.9, and the event timeline track of §5.6.14, have no `isLive`, and are `invalid` here |
| `codec` and `bitrate` of a track | Required where `packaging` is `"loc"`, optional elsewhere | §5.2.18 asks for a codec on "tracks which have an inherent codec associated with them (e.g., audio and video tracks)" and §5.2.22 for a bitrate on "audio and video tracks". No field says which tracks those are; a LOC track holds an encoded audio or video sample an Object (§4.1). The LOC video track of the example in §5.6.14 has neither, and is `invalid` here |
| `samplerate` and `channelConfig` | Not looked at | §5.2.28 and §5.2.29 ask for them on "tracks for which audio codecs are specified". Telling an audio codec string from a video one takes the WebCodecs registry |
| A field this package reads that has another JSON type than the draft gives it (`generatedAt`, `width`, ...), **`null` among them** | `invalid` | The draft gives each field a JSON type and says nothing of a value of another one, nor of `null`. `null` is never read as "the field is absent": a serializer that writes `null` for an empty field exists, and so does a parser that reads `null` as absent (`Option` of Rust's serde), so two readers could take one document in two ways |
| A number that is too large for a double (`1e999`) | `invalid`, as no number | RFC 8259 §9: "An implementation may set limits on the range and precision of numbers." `JSON.parse` reads such a number as Infinity, which could not be written back |
| A payload of more than 1 MiB, or of more than the caller says | `invalid`, and not parsed. A number of the caller that is no length (NaN, Infinity, a negative one, one that is no integer) is a `RangeError` | The draft sets no size; RFC 8259 §9: "An implementation may set limits on the size of texts that it accepts." The payload is parsed whole, so the reader sets one; **the number is provisional** (`DEFAULT_MAX_CATALOG_LENGTH` has the reasoning) |
| A byte order mark before the document | `invalid` | RFC 8259 §8.1: "Implementations MUST NOT add a byte order mark (U+FEFF) to the beginning of a networked-transmitted JSON text", and "implementations that parse JSON texts MAY ignore the presence of a byte order mark rather than treating it as an error." Ignoring is a choice, and parsers differ (`serde_json` of Rust refuses one): refused, so that a Rust reader of ours gives the same answer to the same bytes |
| A string with half of a surrogate pair (`"\ud800"`), in a field that is read | `invalid`, as no string | JSON can spell it (RFC 8259 §8.2 calls the behaviour of software that receives one "unpredictable"). It cannot be written as UTF-8, so a track of that name would be subscribed to under another name; `serde_json` refuses it |
| A key that comes twice in one object | Not noticed: the later one is read | RFC 8259 §4: "The names within an object SHOULD be unique", and what a parser does with a second one differs. `JSON.parse` keeps the later one and does not say so. **A reader in Rust has to be made to do the same, or both to refuse** |
| A field this package does not read | Ignored, and not written | §5: "A parser MUST ignore fields it does not understand." |
| Two tracks of one name | `invalid` when both have the same `namespace`, or neither has one | §5.2.3: "track names MUST be unique per namespace". A track without `namespace` is in the namespace of the catalog track (§5.2.2), which the check does not know: one track with that namespace spelled out and one without are not found |
| `isComplete` that is `false` | `invalid` | §5.1.3: "This field MUST NOT be included if it is FALSE." That is a rule for the one who writes; the draft does not say what a reader does. It is applied to what is read as well: a document that breaks a MUST is not guessed at |
| `deltaUpdate` | Absent: a whole catalog. An array with at least one entry, in a document with neither `tracks` nor `version`: `delta-update`. Anything else (`null`, `false`, a string, an empty array, a document that also has `tracks` or `version`): `invalid` | §5.1.6: "JSON Type: Array", "If this field is present, the catalog represents a delta (or partial) update ... If this field is absent, the catalog is independent." §5.3: "A delta update MUST include the Delta Update ... field with at least one operation. It MUST NOT contain an instance of a Tracks ... field or an MSF version ... field." A document that is neither clearly the one nor the other is read as neither. The operations are not looked at |
| A document with `deltaUpdate` that also has `tracks` or `version` | `invalid`, as above. **Not seen from another implementation**: the one publisher that was run, `mlmpub` of moqlivemock, never sends a delta update, so this rule was checked against the text alone. **A delta update made with the catalog type of moqlivemock v0.16.1 would be `invalid` here, by a reading of its source that was not run**: its `version` field is written also when it is empty (`internal/catalog.go` has no `omitempty` on it), and a document with `"version":""` and `deltaUpdate` is `invalid` (the row `delta-update-with-an-empty-version`) | §5.3, whose rules are for "constructing and processing" a delta update |
| A payload that begins `1f 8b` | `invalid`, with a reason that says it looks like GZIP | RFC 1952 §2.3.1. Whether a payload is compressed is said by a property (§12.1) whose number the draft does not give; the first bytes are only a hint for a log |
| `encryptionScheme` of a track | Read, and handed on with the track. A catalog that has one is not written | §4.3.1: "subscribers MUST decrypt the object payload using the specified scheme before processing." Nothing here decrypts, so whoever uses the catalog has to leave such a track alone. §5.2.39 asks for a cipher suite with it, which is not written |
| The string of `namespace` as the tuple of MoQ Transport | Split at "/", empty fields left out (`namespaceTuple`) | **The draft has no rule**; §11.1.2 has an encoding for URLs only. Its examples have "conference.example.com/conference123/alice", and `moqlivemock` splits at "/" and drops empty fields (`internal/namespace.go`, v0.16.1). A namespace with a field that has a "/" in it, or that is no UTF-8, cannot be named in a catalog this way; a track in such a namespace has to be in that of the catalog track, without `namespace`. **The result is not checked against MoQ Transport**: it can have more than the 32 fields, or more than the 4,096 bytes of a Full Track Name, that draft 18 §2.4.1 allows, and `subscribe` of `@xmoq/moqt` then rejects. `""` and `"/"` are a namespace of no field, which draft 18 allows, and not "no namespace": a track that has `"namespace": ""` is not in the namespace of the catalog track (§5.2.2 has a track inherit when the namespace "is not declared", which is read as: the key is absent) |
| Which catalog a reader has (`catalogStateAfter`) | Object 0 of a Group later than any seen: the catalog. Anything of a Group before the latest, and the catalog that is held: ignored. A delta update, an Object that is not read, a whole catalog at an Object after the first, a delta update at Object 0: the catalog that was read stays, marked `outdated` by the one of them with the largest Object ID | §5: "The first Object (with Object ID 0) in any Group in a catalog track MUST hold an independent copy of the catalog. All subsequent Objects within that Group ... MUST hold a delta update", and "Any catalog updates that precede the first Object of the latest Group MUST be ignored." **Keeping the catalog of an earlier Group is not that sentence in two cases**: when the first Object of a later Group cannot be read, and when a later Object of a later Group comes before its first (or the first never comes). A viewer that plays would lose every track for one update it cannot read, and `outdated` tells whoever uses the state. Provisional |
| An Object at a place that was seen, with another content | Not looked at | An Object is known by its Location. **A publisher that starts again at the same Location while the subscription lasts is not noticed**: behind a relay that keeps the subscription of a viewer while the publisher is replaced, the new catalog of a publisher like `mlmpub`, which is always at {0, 0}, would be dropped. §6.1 has such a publisher use a larger Group ID. To be looked at with the run through a relay |
| Locations of two subscriptions | Not compared: every `followCatalog` starts from nothing | §6.1 has a publisher that starts again use a larger Group ID; the catalog of `mlmpub` is Object 0 of Group 0 after every start |
| The Joining FETCH | Sent after the SUBSCRIBE_OK, and only where that has a LARGEST_OBJECT. Given up after 15 seconds, or when it is refused; the reading goes on with the subscription, and `joiningFetch` says what became of it | §5: "Subscribers accessing the catalog MUST use SUBSCRIBE with a Joining FETCH (offset = 0)", with no condition. **Not sending one without a LARGEST_OBJECT is not that sentence to the letter**, and follows from draft 18: §10.2.11, "If omitted from a message, the sending endpoint has not published or received any Objects in the Track", and §10.12.2, "If no Objects have been published for the track the publisher MUST respond with a REQUEST_ERROR with error code INVALID_RANGE": the FETCH would be refused. The draft does not say what a subscriber does when the FETCH fails. 15 seconds is longer than the own relay waits for the publisher it asks ([implementation notes](../../docs/moqt-implementation-notes.md), "A FETCH that does not come to its end"). Provisional |

## Known gaps

- **`readCatalog` sees one payload, so the rules that hold between catalogs are not checked here.** `followCatalog` has the two of §5 about where an Object stands (the table above). The others belong to whoever compares two catalogs, and to the part that publishes, which does not exist yet:
  - `isLive`: "A True value MUST never follow a False value" (§5.2.7);
  - `isComplete`: "This field MUST NOT be removed from a catalog once it has been added" (§5.1.3);
  - the attributes of a track "MUST NOT be modified after being declared" (§5.3);
- **Nothing decrypts.** `encryptionScheme` of a track is read and handed on, and §4.3.1 has "subscribers MUST decrypt the object payload using the specified scheme before processing": whoever uses a catalog has to leave a track that has one alone. The other fields of encryption (`cipherSuite`, the keys) are not read.
- **A catalog with an audio track cannot be written as the draft asks**: `samplerate` and `channelConfig` (§5.2.28, §5.2.29) are not among the fields that are written. Needed when audio is added.

- **A catalog Object that comes on the subscription is received whole before its length is looked at.** `readCatalog` reads 1 MiB at most, but `@xmoq/moqt` takes an Object of a subscription of up to `limits.maxObjectPayloadLength` (16 MiB by default): that limit is one for the connection, and a track cannot have a smaller one. On the fetch stream of the Joining FETCH the limit is the one of the catalog: an Object over it ends the FETCH, and `joiningFetch` says that it failed.
- `followCatalog` does not look at the track properties of the SUBSCRIBE_OK or at the properties of an Object, where compression is said (§12.1).
- **Delta updates are not applied.** A publisher that sends one (§5.3) cannot be followed past it; a reader has to wait for the next Group, whose first Object is a whole catalog (§5).
- **Compressed catalogs are not read**, which §12.1 asks for: "All MSF implementations MUST support both uncompressed payloads (value 0 or property absent) and GZIP compressed payloads (value 1)." The property that says a payload is compressed has no number in the draft (§14, the table of MSF properties: `MSF_COMPRESSION`, "TBD"), so no two implementations can agree on one from the text. A compressed payload is `invalid` here.
- Where `initDataList` stands in the document (§5.1.7: "MUST be located after the tracks array") is not looked at; the field is not read.
- The JSON type of a field is all that is checked of its value: a `bitrate` of -1 and a `name` that is empty are read. An integer beyond 2^53 loses its last digits, as in every number of JSON read as a double.
- `encodeCatalog` does not limit the length of what it writes, and lets the `TypeError` of `JSON.stringify` through for a value that is no `Catalog` by its type (one that contains itself, a BigInt).
